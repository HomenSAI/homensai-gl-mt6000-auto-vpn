# HomenS.AI Auto VPN 2.0.0-beta1 (Lua line, stable candidate)

**Runtime:** Lua 5.1 runs the monitor and the Auto supervisor as two services (default). Inside Lua, the C module `canon_c.so` does the canonical JSON; if it cannot load or fails its self-probe, the same code runs in pure Lua. Python 3.9 is the base and the fallback layer: it takes over after `LUA-AUTO-FALLBACK`, when no Lua interpreter is present, or with `option lua_monitor '0'` / `option lua_auto '0'`. The one-process `hv-core` (`option lua_core_process '1'`) stays optional and is not part of the acceptance.

This is the first candidate for the stable 2.0.0. It is a pre-release: install it on a router you can reach by a second path, and read **Known limits** first. The Python line (1.0.0-beta15 and older) stays available under its own tags.

## What changed since 2.0.0-alpha16 (alpha17 - alpha26)

**Power cut and restarts**
- Power cut during a switch: in the first 600 s of uptime the recovery rollback failures `KERNEL-POLICY-UNVERIFIED` and `ROLLBACK-UNVERIFIED` are retried every 20 s and not counted (`ROLLBACK-BOOT-RETRY`), because the vendor still reloads the firewall after boot. Before, the result was `ROLLBACK-GIVEN-UP`, a `RESTORING` journal and a refused Start (alpha17).
- Stopping the service reaches the Lua Auto supervisor at once, also during a restart (alpha17, alpha18).
- Faster return after a power cut (alpha26): the boot rollback retries every 5 s and the boot resume tries Start every 5 s; if the pair start queued by the resume Start fails, Start is pressed again (at most twice in 240 s). In the 3 h soaks before alpha26, Auto stayed off after every idle power cut until Start was pressed. Each boot recovery step is logged as `BOOT-RECOVERY-STEP`.
- A damaged Lua module on the Auto supervisor's load path now hands over to the Python supervisor at once (`LUA-AUTO-LOAD-FAILED`). Before, 22 of 56 truncated modules made the daemon exit before its crash counter existed, so procd restarted it every 5 s without falling back (integrity matrix, `docs/architecture/INTEGRITY-MATRIX-2026-11-01.ru.md`).
- Instant reboot (`sysrq-b`) in the middle of a manual switch recovered 2 of 2 on the MT3000: journal `ROLLED-BACK` with `SUPERVISOR-RECOVERY`, Start not needed, Auto `OBSERVING` on the primary 255 s after boot, LAN with internet, "VPN only" guard in place (alpha22).

**Switching speed (GL-MT3000)**
- Manual switch: traffic moved 3.7 s and done 7.2-7.4 s on alpha16; 1.4-1.6 s and 2.5-2.9 s on alpha19 (the history is encoded once per event, not 4-5 times); 0.49-0.59 s and 0.71-0.81 s on alpha22 with the journal and the C module.
- The page answers during switches: slower than 1 s in 6 of 40 calls on alpha19, 0 of 46 on alpha20, longest 0.12-0.14 s on alpha22 (a child process builds the history projection in alpha20).
- Automatic failover (alpha24 defaults; fast detection measured on alpha23): suspicion 2.6-3.1 s after the fault, Auto decision 26-28 s after the fault at probe level 1 (58-88 s without fast detection), traffic on the reserve 1.3-1.6 s after the decision. The remaining time is the 3 failed checks in a row required by the safety rules. Fast detection is on by default (`option lua_fast_detect '0'` turns it off).
- alpha24 shortens the HTTPS wait of a dense confirmation to 3 s and caps the vendor settle period at 45 s (variant B); alpha26 applies the cap also in the Auto diagnostic, the fault check and the candidate ranking. Measured in the alpha26 3 h soak: a cut primary is decided 17-25 s after the fault (alpha23/24 baseline without these changes: 58-88 s; up to 62 s right after a reboot; a DNS-only failure is not seen by the heartbeat and is caught by the regular pass, 37-90 s); blocks after a firmware rebuild 49-67 s (alpha23/24: 119-149 s).

**History and data**
- Switch history is an append-only journal (schema 2): a ~130 KB state file plus `native-history.events.jsonl` with one checksummed line per event, instead of rewriting a ~1 MB file. Python and Lua write byte-identical files; a power cut at any step is repaired at the next write. The first write migrates the old file and keeps it as `native-history.v1.json`. Rollback to an older package: restore that file (see the install guide); events recorded after the migration are lost.
- An oversized history file is `HISTORY-CORRUPT`, never replaced by an empty one (alpha22). On 31.10.2026 an old 1 MB read limit made a Lua writer start a new history over a 1.27 MB file (1288 events lost); the limit is now 4 MiB and the path is closed.
- The journal survived an instant reboot in the 3 h C soak: state and archive agree (332 events, no gaps).

**C module and cache**
- `canon_c.so` (Lua 5.1 module for the router's OpenWrt Lua): output is byte-identical to `canon.lua`, with the same accept/reject decisions; 3000 random checks gave 0 differences. On real router files: JSON parse x10-12, build x4-7. On the MT3000 a manual switch is 0.5/0.7 s with C against 0.6-0.8/1.05-1.3 s in pure Lua; Auto CPU 7.8 % against 10.1 %.
- A fingerprint cache for the Auto diagnostic reuses file-derived results while inode, size, mtime and ctime are unchanged (at most 30 s, never for a file changed in the last 2 s); routes are still read on every pass.

**Monitor**
- Passes every 10 s while the firmware rebuilds a tunnel of the Auto pair (variant A, alpha23); the safety rules (two equal observations, full settle period) are unchanged.
- Server address, ping and the response cards work in the Lua monitor (alpha15, alpha16).
- In-app Help, "Program core", and the documentation match the installed pyramid (alpha25).

## Numbers per layer (GL-MT3000, firmware 4.11.0)

| Layer | Manual switch: traffic / done | Auto decision after a fault | Power cut mid switch |
|---|---|---|---|
| C + Lua (default) | 0.49-0.59 s / 0.71-0.81 s (alpha22) | 26-28 s with fast detection, level 1 | recovered 2 of 2, steady in 255 s after boot (simulated) |
| Pure Lua (`HOMENSAI_CANON_C=0`) | 0.6-0.8 s / 1.05-1.3 s (alpha21) | not measured | not measured on alpha21 |
| Python fallback | 4.1 s / 5.5 s (1.0.0-beta13) | 129-136 s fault to reserve (1.0.0-beta5, beta7) | not measured |

Two services against the one-process `hv-core` (alpha22, two rounds each): done 0.71-0.81 s against 0.81-0.94 s; longest `status` during a switch 0.12-0.14 s against 0.13-0.26 s; CPU 15.9-16.0 % against 16.9-18.2 %; memory about 20.5 MB against about 15.5 MB. The default stays two services.

## Tested on the GL-MT3000 (01.11.2026)

- Normal install over the previous version with Auto on, Auto resumed by itself (alpha22-alpha26).
- 3-hour fault soaks, slot 180 s, 12 fault kinds in rotation, instant reboot every 12th cycle. Lua (alpha20): 46 cycles, 39 ended steady. With the C module (alpha21): 49 cycles, 33 steady, all 33 outside a window of an external outage of the primary server (01.11.2026, 04:00-04:55); inside that window Auto moved to the reserve correctly and the guard held. Fault to done: 4.4-8.0 s. Reports: `docs/architecture/SOAK-LUA-VS-C-2026-11-01.ru.md`.
- **3 h fault soak on alpha26 (the beta1 code without the load guard), slot 180 s:** 45 cycles at the time of release, every non-power fault ended with Auto steady on the primary (41 of 41), and every instant reboot (4 of 4: two idle, two mid-switch) recovered by itself without pressing Start, steady 168-242 s after boot (alpha24 and older needed a manual Start after an idle cut, 495 s). The alpha24 run was stopped after 25 cycles once it showed the 45 s cap was not applied in the Auto diagnostic (fixed in alpha26).
- Static analysis and fuzzing on the PC (`docs/qa/EXTERNAL-TOOLS-2026-11-01.md`): luacheck, shellcheck, bandit, ruff, cppcheck, clang analyzer, eslint, semgrep, gitleaks, hypothesis; libFuzzer with ASan/UBSan on the C JSON module: 2 million inputs, 0 crashes, 0 differences from the Lua decoder. Six low-severity findings, scheduled for the next build.
- Integrity matrix (`docs/architecture/INTEGRITY-MATRIX-2026-11-01.ru.md`): damaged and missing modules, `canon_c.so` damage; the load guard of this release came from it.
- **Not done at release time:** 24 h soak, physical power cut (planned during the owner's live test), the LAN client kit and the IPv6 check on the router, the rehearsal of the Python fallback; this exact package was not yet installed on the router when it was published (the alpha26 package differs only by the version and the load guard).

## Known limits (not accepted yet)

Nothing below is a defect found; each item is simply not evidenced for this release.

- **Hardware:** continuous-mode Auto is evidenced only on the GL-MT3000 with firmware 4.11.0. MT6000 continuous mode is not accepted. Other models and firmware may refuse Auto (readiness checks); do not bypass the refusal.
- **Checks by the router itself:** router-probed IPv4 only. An independent LAN client (DNS, HTTPS, exit IP from a PC behind the router) is not accepted yet (the LAN client kit is written, not run). IPv6 (owner decision: to be tested) and KillSwitch failure behaviour are not accepted yet.
- **Power:** only instant-reboot simulations (`sysrq-b`); a physical power cut is not accepted yet.
- **Duration:** the longest completed fault soak is 3 hours; a 24-hour soak is not done.
- **Waits after a firmware rebuild:** Auto may wait for the firmware (`VENDOR-SETTLING`, 49-67 s measured on alpha26, 119-149 s before) after a killed Auto, a killed monitor or an unreachable server. Variant C (not stopping healthy tunnels during recovery after an Auto kill) is not done.
- **Not measured:** the Python fallback layer with fast detection, the hand-over time of `LUA-AUTO-FALLBACK`, pure Lua automatic failover.
- **Not in this release:** the C core reading and writing the history journal, the event-driven route cache, replacing the GL VPN client by own tunnels (a proposal only).
- Intermittent OpenVPN `AUTH_FAILED` and the firmware's own tunnel rebuilds can delay Auto; they are recorded in the evidence rather than hidden.
- Terms version 2 apply (license transition of 31.10.2026): an earlier acceptance does not count, and Auto does not start (also not automatically after a power cut) until the owner accepts on the page.
- This exact package was not installed on the router before publication (see "Tested").

## Install

Choose this exact tag, download the `.ipk` and its `.sha256` from this release, and take `router-test-kit` from the source archive of the same tag. Follow `docs/INSTALL.ru.md` / `docs/INSTALL.en.md`; a step-by-step owner guide is `docs/OWNER-LIVE-TEST.ru.md`. Do not mix the kit of another tag with this package. The `.ipk` is an application package, not firmware; Auto is never started by installation.
