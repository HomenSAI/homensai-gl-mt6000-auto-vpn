# HomenS.AI Auto VPN 2.1.0-alpha2 (Lua line, server pick stage 2)

**Runtime:** as 2.1.0-alpha1 (Lua by default, Python as the fallback; the same logic and shared test cases).

**Changes since 2.1.0-alpha1:** the router check of 02.11.2026 on the MT3000 (design and measurements: `docs/architecture/SERVER-PICK-DESIGN-2026-11-02.ru.md`):
- **Only Auto changes a server now.** In alpha1 the server check changed the server of the idle channel from outside Auto. Auto saw an outside change of its settings, rebuilt the pair (`PAIR-READOPTED`), and the working channel stopped for 7.1 s for the devices of the network. After three such changes in 15 minutes Auto was held.
  - The server check only measures and decides. It hands the change to Auto (`SERVER-PICK-REQUESTED`).
  - Auto makes the change itself, inside its own lock, and updates its own record of the network, the route order and the reserve to the new server. It is not an outside change any more: no rebuild of the pair, the working channel is not touched.
  - Auto takes the request only when the pair is at rest: the traffic is on the primary channel by the kernel check, the request is for the reserve, no switch is in progress, no manual hold, the reserve is chosen by its tunnel. Otherwise the request waits (`SERVER-PICK-DEFERRED`).
  - While it waits for the new server (at most 60 s), Auto shows `SERVER-CHANGING` and makes no switch decision. The new server must pass the usual channel check through the tunnel (DNS and HTTPS). If it does not, Auto puts the previous server back the same way and logs `SERVER-PICK-FAILED` ("rolled back").
  - Every request is carried out once, also after a rollback. The limit stays: at most 4 changes per hour per channel.
- Still **off by default** ("Pick the best server" on the Channels page).
- Not yet: changing the server of the failed primary channel while the traffic is on the reserve. That request waits for a later stage.

Not yet verified on the router: the stall of the working channel during a server change made by Auto (expected 0 s instead of 7.1 s), the rollback, and that the monitor picks up the new server within 90 s.

**Что изменилось по сравнению с 2.1.0-alpha1:** проверка на MT3000 02.11.2026 (замысел и замеры: `docs/architecture/SERVER-PICK-DESIGN-2026-11-02.ru.md`):
- **Сервер теперь меняет только Auto.** В alpha1 проверка серверов меняла сервер простаивающего канала снаружи Auto. Auto видел чужую правку своих настроек и пересобирал пару (`PAIR-READOPTED`), а работающий канал у устройств сети замирал на 7,1 с. После трёх таких смен за 15 минут Auto удерживался.
  - Проверка серверов только меряет и решает. Смену она передаёт Auto (`SERVER-PICK-REQUESTED`).
  - Auto делает смену сам, внутри своей блокировки, и сразу переписывает свою запись о сети, порядке правил и резерве под новый сервер. Это больше не чужая правка: пара не пересобирается, работающий канал не трогается.
  - Auto берёт заявку, только когда пара в покое: по проверке ядра трафик идёт по основному каналу, заявка — на резервный, переключение не идёт, ручного удержания нет, резерв выбран по туннелю. Иначе заявка ждёт (`SERVER-PICK-DEFERRED`).
  - Пока новый сервер подключается (не больше 60 с), Auto показывает `SERVER-CHANGING` и не принимает решений о переключении. Новый сервер должен пройти обычную проверку канала через туннель (DNS и HTTPS). Не прошёл — Auto тем же способом возвращает прежний сервер и пишет `SERVER-PICK-FAILED` («rolled back»).
  - Каждая заявка исполняется один раз, в том числе после отката. Предел прежний: не больше 4 смен в час на канал.
- По-прежнему **выключено по умолчанию** («Подбирать лучший сервер» на странице «Каналы»).
- Пока нет: смены сервера упавшего основного канала, пока трафик на резерве. Такая заявка ждёт следующего этапа.

Ещё не проверено на роутере: обрыв у работающего канала при смене сервера самим Auto (ожидается 0 с вместо 7,1 с), откат, и что монитор подхватывает новый сервер за 90 с.
