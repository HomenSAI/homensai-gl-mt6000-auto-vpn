# HomenS.AI Auto VPN 2.1.0-alpha3 (Lua line, server pick stage 3)

**Runtime:** as 2.1.0-alpha2 (Lua by default, Python as the fallback; the same logic and shared test cases).

**Changes since 2.1.0-alpha2:** the owner's main scenario of the server pick (design: `docs/architecture/SERVER-PICK-DESIGN-2026-11-02.ru.md`):
- **The failed primary channel gets a new server while the traffic is on the reserve.** The primary fails, Auto moves the traffic to the reserve, and then Auto itself puts the best live server (measured by the server check) into the failed primary.
  - Only after a completed automatic switch to the reserve. Never during a switch or a return, never with a manual switch or a manual hold, never while the reserve is held after a failed return.
  - The reserve that carries the traffic is never touched.
  - The new server must pass the usual channel check through its tunnel (DNS and HTTPS) within 60 s. If it does not, Auto puts the previous server back the same way (`SERVER-PICK-FAILED`, "rolled back").
  - Auto rewrites its own records of the switch to the new server: the route order, the reserve-and-primary roles and the open switch record that the return uses. The return to the primary then follows the usual rules, now on the new server: it checks the new server's own results (its own run of good checks, not the old server's), with no outside-change code and no rebuild of the pair.
  - Both channels must be chosen by their tunnel on the Auto page (as for the reserve in alpha2).
- **WireGuard:** after a server change GL's own switch script also refreshes the provider settings (`update_provider_config`). Auto now does the same step, in the same way. The WireGuard settings it may rewrite are not treated as an outside change.
- **Power cut in the middle of a server change:** after the reboot Auto recognises its own unfinished change and adopts the server that is actually set. Before, this looked like an outside change of the settings.
- **New check round after a repeated failure:** a channel that recovered and failed again within 10 minutes did not start a new server check (found on the MT3000 router on 02.11.2026). Fixed in both monitors.
- **Merged from the branch `fix/f2-f5-resets-20261102`:**
  - QA F2 and F5: the fast JSON reader checks skipped fields exactly like the full reader and handles an empty buffer safely.
  - Two new resets: "Reset statistics" for the monitor's check samples (Monitoring page) and for the transition-test history (next to its table). Both are archived first, like every reset.
- Still **off by default** ("Pick the best server" on the Channels page).

The server change of the reserve (stage 2) was checked on the MT3000 router on 02.11.2026: a stall of 0 s and 0.2 s for the devices of the network instead of 7.1 s, no rebuild of the pair. Not yet verified on the router: the server change of the failed primary while the traffic is on the reserve, the return to it, the WireGuard provider step and a power cut during a change.

**Что изменилось по сравнению с 2.1.0-alpha2:** главный сценарий владельца для подбора сервера (замысел: `docs/architecture/SERVER-PICK-DESIGN-2026-11-02.ru.md`):
- **Упавший основной канал получает новый сервер, пока трафик на резерве.** Основной канал упал, Auto перевёл трафик на резерв, и затем Auto сам ставит упавшему основному лучший живой сервер (по замерам проверки серверов).
  - Только после законченного автоматического переключения на резерв. Никогда во время переключения или возврата, при ручном переключении или ручном удержании, и пока резерв удерживается после неудачного возврата.
  - Резерв, который везёт трафик, не трогается никогда.
  - Новый сервер должен за 60 с пройти обычную проверку канала через свой туннель (DNS и HTTPS). Не прошёл — Auto тем же способом возвращает прежний сервер (`SERVER-PICK-FAILED`, «rolled back»).
  - Auto переписывает свои записи о переключении под новый сервер: порядок правил, роли основного и резерва и открытую запись переключения, по которой идёт возврат. Возврат на основной идёт по обычным правилам, уже на новый сервер: он смотрит результаты самого нового сервера (его собственную серию удачных проверок, не старого), без кода чужой правки и без пересборки пары.
  - Оба канала должны быть выбраны по туннелю на странице Auto (как резерв в alpha2).
- **WireGuard:** после смены сервера собственный скрипт GL ещё обновляет настройки провайдера (`update_provider_config`). Теперь Auto делает этот шаг так же. Настройки WireGuard, которые он может переписать, не считаются чужой правкой.
- **Сбой питания посреди смены сервера:** после перезагрузки Auto узнаёт свою незаконченную смену и принимает сервер, который реально стоит. Раньше это выглядело как чужая правка настроек.
- **Новый круг проверки после повторного сбоя:** канал, который ожил и снова упал в пределах 10 минут, не запускал новую проверку серверов (найдено на роутере MT3000 02.11.2026). Исправлено в обоих мониторах.
- **Влито из ветки `fix/f2-f5-resets-20261102`:**
  - QA F2 и F5: быстрый разбор JSON проверяет пропускаемые поля так же, как полный, и безопасно обрабатывает пустой буфер.
  - Два новых сброса: «Сбросить статистику» для замеров проверки каналов (страница «Мониторинг») и для истории проверок перехода (рядом с её таблицей). Оба сначала сохраняются в архив, как и любой сброс.
- По-прежнему **выключено по умолчанию** («Подбирать лучший сервер» на странице «Каналы»).

Смена сервера резерва (этап 2) проверена на роутере MT3000 02.11.2026: обрыв у устройств сети 0 и 0,2 с вместо 7,1 с, пара не пересобиралась. Ещё не проверено на роутере: смена сервера упавшего основного, пока трафик на резерве, возврат на него, шаг провайдера WireGuard и сбой питания во время смены.
