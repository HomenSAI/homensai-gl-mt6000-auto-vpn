# HomenS.AI Auto VPN 2.0.0-alpha18 (Lua line, test build)

**Runtime:** as 2.0.0-alpha17. The default stays two Lua processes (monitor and Auto). The one-process `hv-core` still loses to it on the MT3000 (measured below).

- **hv-core no longer falls back at once (MT3000 finding on alpha17):** the event loop starts Auto's commands outside the Auto coroutine. The loop's own lock protection therefore closed Auto's lock descriptors in Auto's own lock helpers. The result was three `CONTROL-LOCK-UNAVAILABLE` errors and `HV-CORE-FALLBACK` within a minute. Auto's commands are now never wrapped.
- **The service stop reaches the old Lua Auto during a restart:** in alpha17, `start` removed `service-stop.flag` before the old process saw it, so procd killed the old process only after 300 s. Now only a flag written after the process started counts, and `start` no longer removes it.

**hv-core on the MT3000** (two manual switches and a status call every 1 s, same script on both builds):

| | two processes (alpha16) | hv-core (alpha17 + fixes) |
|---|---|---|
| Traffic moved / switch done | 3.7 / 7.2–7.4 s | 7.1–8.3 / 15.5–16.9 s |
| `status` slower than 1 s during switches | 8 of 49 | 24 of 50 (max 2.5 s) |
| CPU (process + children) | 47.6 % | 53.0 % |
| RSS | 17.6 + 18.2 MB | 25.0 MB |

All commands ran as loop children (707, none synchronous), but pure Lua steps of 1.4–2.5 s remain (`slow_auto_steps` 35, loop lag up to 2.8 s). hv-core stays an option, not the default; the next step is to split these Lua steps or move them to C.

2.0.0-alpha18 — отдельная линия Lua, тестовая сборка.

Исправлены две ошибки, найденные на роутере в alpha17: один процесс ядра (hv-core) сразу откатывался на два процесса — его собственные команды теряли блокировку; при перезапуске службы старый процесс Auto не видел команду остановки.
