# Целостность при внезапном отключении питания (линия 2.0.0-lua)

Дата: 31.10.2026 · Ветка: `lua/agent-power-20261031` (от `feat/lua-core-20261030` = 2.0.0-alpha11) · ROADMAP «Still separate», п. 3.

Пометки: **[Ф]** — факт (код, тест на ПК), **[О]** — оценка, **[П]** — проверить на MT3000.

Цель владельца: роутер обесточили в любой момент (в покое, посреди переключения канала, посреди записи файла). После включения: роутер доступен; интернет в LAN работает и не остаётся перекрыт нашей защитой; приложение запускается или отказывает с понятным кодом; повреждённый файл не вызывает цикла перезапусков.

На роутере не проверялось. Всё ниже — код и тесты на ПК; план проверки на MT3000 — в разделе 6.

## 1. Что на чём лежит

MT3000 (GL 4.11 / OpenWrt 21.02): `/etc` — оверлей UBIFS на NAND; `/var/run` → `/tmp` — tmpfs (теряется при каждой загрузке); таблицы nft и iptables — в ядре (теряются при каждой загрузке). Часов с батарейкой нет: при загрузке `sysfixtime` ставит время по самому новому файлу в `/etc`, до NTP часы могут отставать на время простоя.

Порядок загрузки: сеть и VPN-клиенты производителя стартуют раньше; наш `/etc/init.d/homensai-vpn` — `START=99`, два экземпляра procd (`monitor`, `native`), `respawn 3600 5 0` (перезапуск через 5 с без ограничения числа). Правила ядра `ROUTE_POLICY` (iptables mangle) при загрузке строит `rtp2.sh` производителя из UCI `route_policy`, а не из нашего журнала.

## 3. Что исправлено

1. **Один примитив записи** `lua/durable.lua` (без зависимостей, кроме `canon`; `sys.write_atomic`, `runner.fs.write_atomic`, `monitor_io.write_atomic/write_ram` вызывают его). Шаги как у Python `atomic_json`: временный файл в том же каталоге → запись → 0600 → fsync файла → rename → **fsync каталога** (`nixio.open(dir,'r'):sync()`; на ПК nixio нет — проверяется самопроверкой на роутере `durable_write_dir_sync_sweep`). Без nixio — `sync` до и после rename. Ошибка на любом шаге удаляет временный файл, цель не меняется. Пути в ОЗУ (`/tmp`, `/var/…`) — без fsync. Отдельный модуль вместо кода внутри `sys.lua`: `runner.lua` и `monitor_io.lua` не тянут `sys.lua` (и его `control`/`runner`) в процесс монитора и не образуют цикл `runner ↔ sys`; `sys.lua` реэкспортирует его.
2. **Повреждённый файл состояния — известное состояние, а не падение**: `auto_control.read_json` превращает ошибку разбора в отказ `STATE-FILE-DAMAGED` (с копией в `<каталог>/quarantine/<имя>.<sha8>.damaged`, не более 8 копий, не более 256 КБ каждая, и строкой `logread -e homensai`). Все места, которые ловят отказы, уже его обрабатывают; Lua-супервизор больше не уходит в перезапуски и на Python из-за одного битого файла.
3. **Загрузка с журналом COMMITTED / незавершённым переключением**: `auto.recover` сначала ждёт хотя бы одно устройство туннеля (до 60 с, по 2 с; пока ждёт — защиты нет, LAN не перекрыт). Раньше VPN-клиенты не успевали подняться к старту службы → `UNSAFE-GUARD-DEVICE` → падение на каждом старте → переход на Python. Если туннель так и не поднялся: COMMITTED восстанавливается без VPN-only защиты (строка `GUARD-DEVICE-UNAVAILABLE` в журнале системы), дальше решает обычный проход.
4. **Ядро после загрузки следует за откатом** (`rollback.lua`, ветка «RTP не вызывался»): если отпечаток ядра отличается от записанного до перестановки (`kernel_before_fingerprint`), после возврата UCI вызывается обычная перестройка (`apply`, как при любой смене route policy). Без этого обрыв на шагах 9–13 автоматического переключения оставлял трафик на резерве при журнале «ROLLED-BACK, основной» [Ф: тест падал до исправления]. Ошибка перестройки — прежнее поведение (журнал откатан, `kernel_policy_verified=false`, проход блокирует по аттестации).
5. **Битый журнал**: перед единственной временной блокировкой — копия в `quarantine/` (сам журнал остаётся на месте: только в нём записаны порядки `before/after`; закрывает его оператор).
6. **Остатки `.pending`**: `durable.sweep` / `agent.sweep_pending` при старте каждой из четырёх служб.
7. **Python**: `switch_timing.record` пишет как `atomic_json`; добавлен `agent.sweep_pending`; init-скрипт сообщает `HOMENSAI-CONFIG-UNREADABLE`.

## 4. Тесты на ПК [Ф]

`router/tests/lua/test_power_cut.lua` (21) и `router/tests/test_power_cut_integrity.py` (5):

- **Модель флеша** для `durable.write`: у каждого inode флаг «данные на флеше», у каталога — записанное и «на флеше» (после fsync каталога) содержимое; обрыв после каждого шага перебирает все пессимистичные исходы (старая/новая запись каталога; несинхронизированные данные — как есть, пусто или нули). Итог: только старый или новый файл, после возврата из `write` — только новый. Контрольный тест: писатель без fsync файла даёт пустой/нулевой файл — модель это ловит. Отказы записи/rename/fsync: цель прежняя, `.pending` нет.
- `sweep`: удаляет только старые (в обе стороны часов) `.pending`, не трогает чужие имена, свежие и каталоги; `quarantine`: одна копия на содержимое, предел 8.
- **Читатели**: журнал — каждая длина обрыва (все ~1800 смещений), нули той же длины, 4 КБ нулей, один изменённый байт → `JOURNAL-INTEGRITY-FAILED`, отсутствует → `{}` (Lua и настоящий Python `journal_read`); `native-stop.json` — `STATE-FILE-DAMAGED` и копия; состояние пары — отказ с кодом для каждого обрыва и `pair.recover` без исключения; история — битый основной → резервный, оба → `HISTORY-CORRUPT` с кодом; учёт — резервный/`STORAGE-001`; ping-история — `-UNAVAILABLE`.
- **Обрыв питания перед каждым шагом записи** (запись файла на флеш или изменение UCI) пяти сценариев, затем «загрузка» (флеш — снимок на момент обрыва, ядро перестроено из UCI, защиты nft нет, ОЗУ пусто) и `auto.recover`, затем ещё одна загрузка:

| Сценарий (шагов) | Итог после загрузки по точкам обрыва |
|---|---|
| автопереключение на резерв (16) | 1–3: журнала нет, основной; 4–13: ROLLED-BACK, основной; 14–17: COMMITTED, резерв, VPN-only |
| переключение с ошибкой записи ядра (18) | 1–3: журнала нет; 4–19: ROLLED-BACK, основной |
| ручное мгновенное на резерв (16) | 1–3: журнала нет; 4–13: ROLLED-BACK, основной; 14–17: HELD-ON-RESERVE, резерв |
| возврат на основной из COMMITTED (8) | 1: COMMITTED, резерв; 2–9: ROLLED-BACK, основной |
| возврат оператора из HELD-ON-RESERVE (11) | 1: HELD-ON-RESERVE, резерв; 2–12: ROLLED-BACK, основной |

  Во всех точках: `recover` без ошибки, журнал завершён, ядро = UCI = порядок журнала, оставшаяся защита — только VPN-only, вторая загрузка ничего не меняет. Плюс **второй обрыв внутри самого восстановления** на каждом его шаге (для каждой точки первого обрыва автопереключения) — итог тот же.
- Загрузка с COMMITTED до подъёма туннелей: ожидание, затем VPN-only; без туннелей — без защиты и без ошибки. Битый журнал: копия, `full` → сразу `vpn-only`, тревога.

## 6. План проверки на MT3000 (сопровождающему)

Только по указанию владельца, при свободном `private/ACTIVE-EXECUTOR.local.json`, только MT3000 (не MT6000). Перед началом: резервная копия `/etc/homensai-vpn` и `/etc/config`, пакет этой ветки, обе службы на Lua.

`echo b > /proc/sysrq-trigger` — мгновенная перезагрузка без `sync`: всё, что не дошло до флеша, теряется (модель обрыва для ФС; не модель обрыва записи блока NAND). Перед первым разом: `echo 1 > /proc/sys/kernel/sysrq`.

### 6.0 Подготовка (один раз)
```sh
lua /tmp/hvlua/router_sys_selftest.lua /usr/lib/homensai-vpn/lua /tmp/hvself   # все "ok", в т.ч. durable_write_dir_sync_sweep
strings /usr/lib/libuci.so* | grep -c 'uci-'      # [6.1] есть имя временного файла libuci (".%s.uci-XXXXXX")
```

### 6.1–6.6 Обрывы по фазам

Скрипт обрыва по фазе журнала (запускать в фоне перед действием на странице):
```sh
cut_at() {  # $1 = фаза журнала на флеше
  while ! grep -q "\"phase\":\"$1\"" /etc/homensai-vpn/native-transaction.json 2>/dev/null; do :; done
  echo b > /proc/sysrq-trigger
}
```

| № | Когда обрывать | Как |
|---|---|---|
| 6.1 | покой (OBSERVING) | `echo b > /proc/sysrq-trigger` |
| 6.2 | APPLYING | `cut_at APPLYING &`, затем ручное переключение со страницы (или тест сбоя) |
| 6.3 | WAIT-CLIENT | `cut_at WAIT-CLIENT &`, затем автосбой (тест сбоя) |
| 6.4 | COMMITTED / HELD-ON-RESERVE | после переключения на резерв подождать 30 с, `echo b > …` |
| 6.5 | запись истории | `while ! ls /etc/homensai-vpn/.native-history.json.*.pending >/dev/null 2>&1; do :; done; echo b > /proc/sysrq-trigger &`, затем ручные переключения туда-обратно; так же учёт: тот же цикл на `.checkpoint.json.*.pending` и `ubus call homensai-vpn-lua checkpoint` |
| 6.6 | установка пакета | `opkg install /tmp/<пакет>.ipk & sleep 3; echo b > /proc/sysrq-trigger` |

После каждой загрузки (через 3 мин) проверить и сохранить вывод:

## 8. Находки настоящего обрыва на MT3000 (sysrq-b, 31.10.2026) и решение владельца о перезапуске супервизора

Доказательства: `private/soak-24h/evidence-alpha13-powercut-held.json`, `soak-log.jsonl` (2.0.0-alpha13, обе службы на Lua).

### 8.1 Удержанный журнал после загрузки — тупик (исправлено)

**[Ф] Что было.** До обрыва: Auto включён, журнал `HELD-ON-RESERVE` (`OPERATOR-MANUAL`), пара `RUNNING`. После загрузки: намерение (ОЗУ) пропало; туннели `wgclient1`/`ovpnclient2` лежат (подготовка роутера выключает автозапуск VPN производителя — клиенты поднимает только пара); `native-status` = `BLOCKED`, `UNSAFE-GUARD-DEVICE`; журнал навсегда `HELD-ON-RESERVE`; Start (и автоматический возврат после загрузки) — `TRANSACTION-IN-PROGRESS`. После ручного `ifup` обоих клиентов супервизор сам за ~80 с довёл уборку до `ROLLED-BACK`/`STOPPED`.

**Причина в коде.** `auto.recover` для `HELD-ON-RESERVE` ничего не делает, дальше `pair.recover` → `pair.cleanup` → `finish_committed(..., 'PAIR-STOPPED')`; и удержание (`guard(devices())`), и откат (`rollback` заканчивается `guard(devices())`) требуют хотя бы одно устройство туннеля, а `backend.guard` пустой список отвергает (`UNSAFE-GUARD-DEVICE`). Ошибка ловится в `pair.recover`/`pair.tick` → `publish_failure`, пара `HELD`, каждый следующий проход повторяет то же. Клиентов не поднимает никто: пара поднимает их только в `begin` (нужен Start) и `revive` (только при включённом намерении). Ожидание туннеля в `auto.recover` (§3.3) есть только для `COMMITTED`/незавершённых фаз, и оно только ждёт, а не поднимает.

**Исправление** (Lua `pair.ensure_devices`/`pair.boot_devices`, Python `pair_auto.ensure_devices`/`boot_devices`). Когда уборке пары (`COMMITTED`/`HELD-ON-RESERVE` или откат порядка) или восстановлению при старте (`auto.tunnel_devices`; Python `serve` перед откатом и защитой `COMMITTED`) нужны устройства, а ни одного нет, супервизор поднимает собственных клиентов пары (интерфейсы из состояния пары) по тем же правилам, что `begin`/`revive`: только клиент с `disabled='0'`, который netifd показывает остановленным; только если сетевая идентичность и защищённые конфиги совпадают с сессией (чужое изменение — не трогаем, прежний отказ); `ifup` через `forward_dispatch` с текущей ревизией управления (Stop его отсекает); общий бюджет `pair-revive.json` (пауза 120 с, не более 4 за 15 мин); затем ожидание устройства до 60 с. Пока ждём, защиты нет — LAN не перекрывается. Каждый `ifup` — строка `PAIR-RECOVERY-REVIVE` в `logread`. Поднятый клиент записывается в `owned`, и уборка возвращает его в состояние до сессии. Прежние проверки (хэш политики, внешние изменения, аттестация отката) не тронуты. Итог: журнал доходит до `ROLLED-BACK`, пара `STOPPED`, Start и возврат после загрузки проходят без действий владельца.

### 8.2 Окно возврата после загрузки мерилось стенными часами (исправлено)

**[Ф]** Часов с батарейкой нет: сразу после загрузки chrony перевёл часы вперёд («time sync success»), а окно 10 мин в `boot_resume.lua` считалось по `now()` (стенные) — `FAILED` после 4 попыток. Теперь окно и интервал попыток — по монотонным часам (`/proc/uptime`; Python — `time.monotonic`), стенные — только время в опубликованной строке. Окно: не меньше 10 мин от первой попытки и не раньше 15 мин работы роутера (уборка из §8.1 занимает 1–2 мин после подъёма туннелей).

### 8.3 Решение владельца (расширение): Auto возвращается и после непреднамеренного перезапуска супервизора

**[Ф] Находка soak:** `kill -9` простаивающего Lua-супервизора → procd перезапустил его → восстановление отозвало намерение (прежний замысел «перезапуск никогда не возобновляет Auto») → Auto выключен, пока кто-нибудь не нажмёт Start.

**Решение владельца 31.10.2026:** включённый владельцем Auto должен продолжать работать после непреднамеренных перерывов. Правило метки владельца (`auto-resume.json`, новее защёлки Stop) распространено на перезапуск супервизора без перезагрузки:

- сам супервизор по-прежнему намерение не возобновляет (ограждение при восстановлении осталось);
- каждый старт супервизора, закончивший восстановление, пишет новый токен `/var/run/homensai-vpn/supervisor-start.json` (Lua `auto.recover`, Python `native_switch.serve`) — после ограждения намерения, так что нажатый за владельца Start им уже не отзывается;
- монитор (Lua `boot_resume.lua`, Python `boot_resume.watch`) на каждый ещё не обработанный токен один раз выполняет тот же возврат: та же проверка метки и защёлки, тот же Start со всеми проверками, монотонное окно 10 мин; в `boot-resume.json` — `trigger: supervisor-restart` и токен;
- преднамеренный Stop и любой give-up пишут защёлку новее метки и побеждают (`SKIPPED`, `AUTO-RESUME-STOPPED`);
- защита от цикла падений: не больше 3 возвратов за 15 мин (`FAILED`, `AUTO-RESUME-RESTART-LIMIT`);
- перезапуск самого монитора не повторяет возврат для уже обработанного токена (он записан в `boot-resume.json`).

Следствие: перезапуск службы (`/etc/init.d/homensai-vpn restart`, обновление пакета) при включённом владельцем Auto тоже возвращает Auto — так же, как обрыв питания; выключить — Stop.

### 8.6 Второй настоящий обрыв (2.0.0-alpha14, покой, Auto включён) — снова тупик; исправлено

**[Ф] Доказательства** `private/soak-24h/evidence-alpha14-powercut-committed.json`: журнал до обрыва `COMMITTED` (reason null); после загрузки в `logread` только `GUARD-DEVICE-UNAVAILABLE`, строки `PAIR-RECOVERY-REVIVE` нет; `native-status` `BLOCKED`/`UNSAFE-GUARD-DEVICE`; пара `HELD`, `owned: []`, `before_flags {ovpnclient2:'0', wgclient1:'0'}`; оба клиента лежат (`up false`, `pending false`); `pair-revive.json` нет; `boot-resume.json` `WAITING`, 40 попыток, `TRANSACTION-IN-PROGRESS`.

**Причина в коде.** Подъём из §8.1 молча выходил до первого `ifup` (ни ленты бюджета, ни строки в журнале): сравнивал *весь* сетевой конфиг с сессией (`network_identity`) и *все* защищённые конфиги (беспроводной, dhcp, DNS). Производитель переписывает часть из них при загрузке (на MT3000 — репитер `wwan`), поэтому проверка сработала как «чужое изменение» и клиенты пары не поднимались. `owned: []` (клиенты были подняты ещё до сессии) — то же следствие: уборка ничего не останавливает и не проверяет. Ветка `COMMITTED` в `auto.recover` вызывает тот же подъём (`auto.tunnel_devices` → `pair.boot_devices`) и только поэтому лишь ждала. Start закрыт для `COMMITTED` по замыслу: он открывается, когда журнал завершён.

**Исправление (Lua `pair.ensure_devices`, Python `pair_auto.ensure_devices`).**
- Интерфейсы — два клиента пары из её состояния (`interfaces`), а не только `owned`.
- Проверки — как у `begin`: строка интерфейса есть, протокол её, `auto='0'`, `disabled='0'`; netifd показывает клиента остановленным; определения профилей (`wireguard`, `ovpnclient`) совпадают с сессией. Отличие всего сетевого конфига и других защищённых конфигов только записывается в журнал: от них не зависит, какой профиль поднимет `ifup`.
- Каждый пропуск пишется в `logread` строкой `PAIR-RECOVERY-REVIVE-SKIPPED: <причина>`, не чаще раза в 5 мин на причину (причины: `PAIR-EXTERNAL-CONFIG-CHANGE`, `PAIR-PROFILES-UNVERIFIED <if>`, `REVIVE-BUDGET <if>`, `NOT-STOPPED <if>`, `NETWORK-SIDE-UNAVAILABLE`).
- Клиент, которым сессия не владела, после уборки остаётся поднятым, как было до сессии. Клиент, которым владела, уборка возвращает, как раньше.
- Остальное без изменений: `ifup` отсекается Stop (ревизия управления), общий бюджет, ожидание до 60 с без защиты, все проверки уборки и отката.

**Тесты [Ф]:** `test_boot_held.lua`/`.py` — точно это состояние (`COMMITTED`, пара `HELD`, `owned []`, `wgclient1`+`ovpnclient2` лежат, ленты нет, беспроводной конфиг и сеть переписаны производителем). Контроль: прежний подъём — журнал `COMMITTED`, `UNSAFE-GUARD-DEVICE`, Start `TRANSACTION-IN-PROGRESS`. С исправлением: подняты оба клиента, защита `COMMITTED` ставится, журнал `ROLLED-BACK`/`PAIR-STOPPED`, пара `STOPPED`, клиенты остаются поднятыми, возврат/Start проходит. Изменённый профиль, выключенная строка и чужой протокол — клиента не трогаем, пропуск записан.

**[П] На MT3000:** тот же обрыв в покое. Через 2–3 мин должны быть `PAIR-RECOVERY-REVIVE: ifup ovpnclient2` и `PAIR-RECOVERY-REVIVE: ifup wgclient1`, журнал `ROLLED-BACK`, `boot-resume.json` `RESUMED`. Если опять тупик — строки `PAIR-RECOVERY-REVIVE-SKIPPED: …` покажут причину.
