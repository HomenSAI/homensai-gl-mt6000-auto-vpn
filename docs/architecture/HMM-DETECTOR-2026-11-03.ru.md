# Детектор сбоя канала: модель HMM вместо «3 подряд» / Channel-failure detector (HMM)

Дата: 03.11.2026. Ветка `feat/hmm-detector-20261103` от `0c8b6400` (запись 2.1.0-alpha7). Без работы с роутером. Основание —
офлайн-исследование `private/math/detection/REPORT.ru.md` (раздел 6 — спецификация) и решение владельца: модель HMM
(Гилберт–Эллиотт, 6 состояний) по умолчанию, оба пресета выбираемы, прежнее правило сохранено. Обе среды (Python и Lua)
решают одинаково; общие случаи — `router/tests/hmm_detector_cases.json` (генерируются из Python
`router/tests/gen_hmm_detector_cases.py`).

## Что изменилось

Решение «канал, по которому идёт трафик, отказал» больше не «N неудачных проб подряд», а вероятность: **сбой продлится ещё
не меньше 20 с (цена переключения) с вероятностью ≥ θ**. Ради блэкаута короче цены переключения Auto не уходит, на
настоящем долгом обрыве уходит примерно через 25 с, при потере ≤ 20 % не уходит, при ≥ 40 % уходит, при постоянной потере
~30 % больше не «качается» между каналами.

Настройка `option failure_model` (секция `main`, читает `inventory.lua`):

| значение | в странице | θ | короткий блэкаут, средняя длительность | смысл |
|---|---|---|---|---|
| `hmm` (по умолчанию) | «Стандартный» | 0,8 | 4 с | долгий обрыв ~25 с; сбои 15–20 с не уводят |
| `hmm-fast` | «Быстрый» | 0,7 | 3 с | долгий обрыв ~21 с; уходит на ~70 % сбоев длиной 20 с |
| `consecutive` | «Прежнее правило: сбои подряд» | — | — | `recovery_failures` (3–10) неудачных проб подряд, как в 2.1.0-alpha7 |

Выбор — в мастере «Настройки → Правила переключения Auto» (`router/recovery_panel.inc.js`, поле «Детектор сбоя»; RPC
`setup_recovery` с необязательным полем `failure_model`, `recovery_settings.payload`, `setup_save.lua`). Старая страница поле
не шлёт — значение не меняется. Поле «Сбоев подряд» действует только для прежнего правила. Страницы пересобираются при
следующем повышении версии (здесь версия не повышалась).

Вернуться к прежнему правилу (или выбрать пресет) по SSH:
```
uci set homensai_vpn.main.failure_model='consecutive'   # или 'hmm' / 'hmm-fast'
uci commit homensai_vpn
```
Auto берёт настройки в каждой итерации (`backend.policy()`); мастер, как и для остальных правил, просит
остановить Auto перед сохранением.

## Модель

Модули-близнецы: `router/files/usr/lib/homensai-vpn/channel_model.py` и `.../lua/channel_model.lua` — только чистые функции.

Состояния: **G** здоров · **L** лёгкая потеря (5–20 %, оставаться) · **M** тяжёлая потеря (40–60 %, уходить) · **B** короткий
блэкаут (переходный) · **X** долгий обрыв (уходить) · **N** мёртвый DNS при работающем HTTPS (уходить).

Цепь с непрерывным временем, «звезда»: G → s с интенсивностью λ_s, s → G со средней длительностью dur_s.
λ (1/с): L 1/7200, M 1/21600, B 4/21600, X 1/21600, N 1/604800; dur (с): L 1800, M 1800, B 4 (быстрый — 3), X 900, N 1800.

Наблюдение пробы монитора (тот же код, что у продукта):
- **O** — кода нет, DNS ок, ≥ 2 из 3 HTTPS;
- **D** — `DNS-001`;
- **H** — `VPN-003`, `VPN-001`, `VPN-MTU` (чёрная дыра больших пакетов — жёсткий отказ пользовательского трафика);
- любой другой код (`CHECK-001`, `ROUTE-001`, `PROFILE-INACTIVE`, `CHECK-LIMIT`, `VENDOR-…`) — не наблюдение: состояние не
  двигается.

Ритм пробы: монитор теперь пишет в каждую пробу `dense: true/false` (проход плотного подтверждения, ожидание HTTPS 3 с);
без поля — `dense = (промежуток до предыдущей пробы канала ≤ 7 с)`. Правдоподобия P(O, D, H | состояние, ритм) — таблица
`EMIS` из исследования (раздел 2.3), каждая ≥ 0,002 (одна проба никогда не даёт уверенности).

Часы модели: момент, когда результат пробы стал известен, `known = time + delay`: `VPN-003` — всё ожидание HTTPS (6 с,
в плотном 3 с), `DNS-001` — ожидание DNS 3 с, остальное — обычная задержка публикации 2,5 с. Так считало откалиброванное
исследование (по времени публикации); если брать время начала пробы, первая плотная проба после обычной кажется на 3 с
«дальше», и модель уходила на 30 % блэкаутов длиной 20 с (замер на симуляции до этого исправления).

Шаг (на каждую пробу по возрастанию времени), `dt = clamp(known − known_prev, 0, 600)`, первая проба `dt = 10`:
```
g = exp(-Λ·dt), Λ = Σλ_s;   e_s = exp(-dt/dur_s)
π'_G = π_G·g + Σ_s π_s·(1 − e_s);   π'_s = π_s·e_s + π_G·(λ_s/Λ)·(1 − g)
π'_s ← π'_s · EMIS[s][ритм][наблюдение];  нормировка;  π'_s ← max(π'_s, 1e-9);  нормировка
```
Решение: `persist = Σ_{s∈M,B,X,N} π_s · e^(−20/dur_s)` — вероятность, что сбой продлится ещё ≥ 20 с;
**уход, если persist ≥ θ**, новейшая проба-наблюдение не старше `valid_for` (3 интервала, как у `streak`) и самая
новая проба канала — наблюдение (если последний проход дал `CHECK-001`/`ROUTE-001` и т. п., решения нет — как у `streak`).
B (средняя 4 с) сохраняет e^−5 = 0,7 % своей массы, X — 97,8 %, M и N — 98,9 %: модель сама выясняет, что сбой длинный, по
тому, сколько он уже длится.

Публикуется также `P(bad) = 1 − π_G − π_L` (≥ 0,2 — «подозрение») и ожидаемый остаток сбоя `Σ_{bad} π_s·dur_s` (для
показа; для решения не годится — малая вероятность долгого обрыва даёт большое среднее).

Численная устойчивость: перенормировка на каждом шаге и пол 1e-9 (нет underflow и «невозможных» состояний); 100 000
случайных шагов с dt от 0 до 600 с — всегда распределение (сумма 1 ± 1e-12), без NaN (тест `test_numerically_stable…`).

## Состояние канала и перезапуск

Состояние канала — 6 вероятностей + время новейшего наблюдения. Отдельно оно **не хранится**: каждый раз
воспроизводится из проб этого канала в `status.json` за последние 600 с (тот же поиск по поколению профиля
`scoped_samples`, что у `streak`), начиная с G. Поэтому:
- перезапуск Auto, переход Lua ↔ Python (`LUA-AUTO-FALLBACK`), смена процесса hv-core дают **ровно то же** состояние;
- после перезагрузки роутера `status.json` (RAM) пуст — модель стартует с «здоров», как и `streak` (нужны новые
  доказательства; безопасно: «здоров» никогда не уводит с канала, а свежие пробы за ~25 с восстанавливают картину);
- новое поколение профиля (перестройка туннеля поставщиком) начинает с G, как `streak`;
- две пробы одного времени с разным здоровьем — доказательства нет (как `failure_diagnosis.scoped_samples`).

Чтобы не пересчитывать каждый такт Auto (2 с), результат воспроизведения одинакового окна запоминается в процессе (ключ —
число, сумма времён и «форма» проб; опубликованные пробы не меняются), новый пересчёт — с каждой новой пробой.

## Где решает модель (Python / Lua одинаково)

- Уход с основного: `pair_auto.tick` (`pair_auto.py:1489`) / `pair.lua M.tick` (`lua/pair.lua:1265`):
  `failed = unstable or channel_failed(...)`. `consecutive` → прежний `streak`.
- Прогноз `failover_plan.plan` (`failover_plan.py:69`): то же; в рекомендации поле `failure_model`.
- Отказ резерва, несущего трафик (возврат на основной с причиной `RESERVE-FAILED-PRIMARY-VERIFIED`):
  `native_switch.committed_recovery_decision` (`native_switch.py:1385`) / `transaction.lua` (`lua/transaction.lua:822`).
- В `probe_evidence` попытки — `failure_model` (журнал истории его не хранит, поле только в статусе перехода).
- Не изменены (по-прежнему `streak`): ручные переходы (`pair_manual`, `manual.lua`), однопарный старый Auto
  (`auto.lua`, `native_switch` main loop), диагностические поля `decision_explanation`, «здоров» резерва (2 успеха подряд).

## Совмещение с механизмами alpha7

- **Late-switch recheck** — без изменений и после решения модели: перед фиксацией ухода новая здоровая проба монитора
  или одна живая проба с ожиданием 1 с отменяют уход; то же доказательство повторно не решает. На блэкауте 20 с модель
  решает на последней неудачной пробе, recheck находит основной живым — ухода нет.
- **VPN-MTU** — наблюдение H (жёсткий отказ). Как и раньше, живая проба Auto его не проверяет (`PROBE_BLIND_CODES`): уход
  отменяет только новая здоровая проба монитора. При пробах раз в 10 с решение — на третьей (persist 0,956), как у «3 подряд».
- **Flap damping** (`return_hold`) — без изменений; уход с упавшего основного не ограничивается.
- **Плотное подтверждение** (`probe_policy.Booster`, обе среды): монитор передаёт вид модели каналов пары (`models`).
  Новое: «подозрение» модели (`P(bad) ≥ 0,2`, решение ещё не принято) у канала, несущего трафик (основной в `OBSERVING`,
  резерв в `COMMITTED`/`DEGRADED-ON-RESERVE`), запускает эпизод (`reason: model`, та же пауза 30 с с удвоением). В режиме
  модели эпизод заканчивается решением модели (`failure-confirmed`), ложной тревогой только при ≥ 2 хороших пробах **и**
  снятом подозрении, переходом или через 60 с. Без `models` (прежнее правило) — всё как раньше. Следствие: одна
  неудачная обычная проба (P(bad) ≈ 0,56) уже включает плотные проверки; ложная тревога удваивает паузу, как раньше.
- **Возврат (новое, только режимы HMM)**: плановый возврат со здорового резерва дополнительно требует от основного
  **P(здоров) = π_G ≥ 0,90** (до интеграции alpha8 — 0,95) по той же модели **или** 300 с подряд здоровых проб (`stable_success` за 300 с) —
  `channel_model.return_ready`, вызывается в `pair_auto.tick`/`pair.lua` (путь «ядро на резерве») и в
  `committed_recovery_decision` (если резерв не упал). С упавшего резерва возврат — без этого условия (после слияния с
  rescue-tune — общее правило `return_rule`, см. «Интеграция 2.1.0-alpha8»).

в разделе «Интеграция 2.1.0-alpha8».

## Интеграция 2.1.0-alpha8 (03.11.2026, ветка `integ/alpha8-20261103`)

### Порог возврата 0,90 (решение владельца «0,9 сразу»)

`channel_model.HEALTHY` = **0,90** (было 0,95) в Python и Lua. Ограничение 300 с подряд здоровых проб (`CLEAN`) не
менялось. `hmm_detector_cases.json` перегенерирован (`gen_hmm_detector_cases.py --write`): поменялись константа и один
случай `evaluate` (`healthy` false → true). Мутант порога теперь 0,9 → 0,95.

Задержка возврата после конца сбоя, `python3 router/tests/hmm_tick_sim.py --return 100` (стандартный HMM, пульс 2 потери,
резерв здоров; медиана / P95, с; в скобках — прогоны с уходом и возвратом из 100):

| сбой | 120 с (умолчание после слияния), ≥ 0,95 | 120 с, **≥ 0,90** | 30 с (как в разделе выше), ≥ 0,95 | 30 с, **≥ 0,90** |
|---|---|---|---|---|
| блэкаут 40 с | 137,2 / 147,2 (100) | 137,2 / 147,2 (100) | 67,2 / 68,3 (100) | **57,3 / 58,5** (100) |
| потеря 40 %, 150 с | 131,1 / 308,4 (98) | 130,9 / 310,4 (99) | 61,9 / 307,2 (100) | **58,4 / 305,8** (99) |
| потеря 50 %, 150 с | 131,5 / 147,1 (100) | 131,5 / 147,1 (100) | 59,9 / 67,7 (100) | 59,9 / 67,7 (100) |
| постоянная потеря 30 %, сутки: уходов / возвратов | 1 / 0 (весь день на резерве) | 1 / 0 | 1 / 0 | 1 / 0 |

Выводы. С `primary_stable` 30 с порог 0,90 убирает около 10 с задержки после блэкаута 40 с (+16 → +6 с к прежнему
правилу, как предсказывал раздел выше). «Качели» при постоянной потере 30 % не возвращаются: один уход в сутки, возврата
нет. Со значением по умолчанию после слияния (`primary_stable` 120 с, rescue-tune) возврат определяют 120 с стабильности
основного, и порог 0,90 почти ни на что не влияет (разница ≤ 2 с, в пределах шума). Он важен тем, кто ставит
`primary_stable` ниже, и профилю «Быстрое восстановление» (60 с).

### Одно правило возврата с rescue_stable

При отказавшем резерве условие модели не применяется: стабильность берётся `min(primary_stable, rescue_stable)`. Плановый
возврат с неотказавшего резерва требует `max(primary_stable, hold)` и, в режимах HMM, `return_ready`. Подробно — в
[RESCUE-STABLE-2026-11-03.ru.md](RESCUE-STABLE-2026-11-03.ru.md#интеграция-210-alpha8-03112026-ветка-integalpha8-20261103).
Мутанты условия возврата в `mutate_hmm_detector.py` переведены на объединённый код (`model_gate`).

`primary_stable` 30 с, пульс 3 потери, без условия возврата); умолчание после слияния (стандартный HMM, 120 с, пульс
2 потери — `lua/fast_detect.lua` LOSSES из rescue-tune, условие возврата 0,90); быстрый пресет с теми же правилами.

Что изменилось от слияния (по сравнению с одним детектором HMM, таблица выше с 30 с и пульсом 3):
- пульс по 2 потерям ускоряет уход примерно на 0,8 с (24,6 → 23,8–23,9 с на долгом обрыве; быстрый 20,6 → 19,8 с);
- 120 с стабильности гасят флаппинг 60/120: 1 уход вместо 5;
- **цена:** на «шумных» сутках стандартный пресет дал 1 лишний уход с возвратом, быстрый — 2 (раньше 0). На блэкаутах
  15 и 20 с — по 1 % прогонов. Это то же, что исследование rescue-tune предсказало для LOSSES 2 («ненужные
  переключения 0,168 → 0,190 в сутки»): чаще начинается плотное подтверждение, а плотные пробы в модели весят сильнее.
  Выборка «шумных» суток — один прогон (seed 9), это оценка, а не измерение. Проверить на роутере (фаза 2 и сутки
  без сбоев). Если подтвердится — вернуть LOSSES 3 или поднять θ стандартного пресета.

## Стоимость

Операций на пробу: 6 `exp`, ~24 умножения/сложения прогноза, 6 умножений на правдоподобие, 2 × (6 сложений + 6 делений)
нормировки, 6 сравнений с полом, 4 умножения + 3 сложения решения. Lua: шесть локальных переменных, массив состояния
обновляется на месте — в горячем пути ни одной таблицы (тест: 100 000 шагов, рост памяти < 1 КБ).

Замер (контейнер CI, x86-64): Lua 5.1 `step` 3,4–3,5 мкс на пробу; CPython 3.9 ~15–20 мкс. Оценка MT3000 (Cortex-A53
1,3 ГГц, Lua 5.1, ×10 к x86): ~35 мкс на пробу; окно 600 с — 60–150 проб → 2–5 мс на пересчёт, пересчёт — только с новой
пробой (раз в 4–10 с) благодаря памяти окна; плюс просмотр `status.samples` (как у `streak` сейчас). Итого ≤ 0,1 %
одного ядра; ×10 — допущение, на роутере не замерено.

## Не сделано / ограничения

- Отображение P(bad)/остатка на странице не добавлено (бюджет страницы): поле `status.profiles[].failure_model`
  (`model, p_bad, p_healthy, persist, remaining_s, failed, suspect, time, observations`) у каналов пары — единый источник
  для страницы и истории; журнал истории его пока не пишет.
- Тексты встроенной помощи по-прежнему говорят «3 неудачи подряд» (для жёстких отказов раз в 10 с это и сейчас верно:
  решение на третьей пробе).
- Однопарный старый режим Auto (`auto.lua`, основной цикл `native_switch`) и ручные проверки — на прежнем правиле.
- Всё — модель: таблица правдоподобий откалибрована на 6 уровнях потерь (кроме 30 % — по 2 цикла), потеря только исходящая,
  шум «микроблэкаутов» — допущение. Приёмка на MT3000 не выполнялась.

## Проверка на роутере (отдельная приёмка; только при свободном исполнителе и разрешении владельца)

Пакет — после следующего повышения версии (здесь версия не повышалась); установка — обычным набором
`router-test-kit` того же коммита (`01-preflight.sh`, `02-install.sh /tmp/<пакет>.ipk`, `03-verify.sh wait`).

1. Только чтение после установки (режим по умолчанию — `hmm`, настройку можно не задавать):
   ```
   uci -q get homensai_vpn.main.failure_model || echo 'не задано -> hmm'
   ubus call homensai-vpn status | jsonfilter -e '@.profiles[@.role="source"].failure_model' -e '@.profiles[@.role="target"].failure_model'
   ubus call homensai-vpn status | jsonfilter -e '@.samples[-1].dense'
   ```
   Ожидание: у обоих каналов пары `{"model":"hmm","p_bad":~0,"p_healthy":>0.95,"failed":false,...}`; в пробах поле `dense`.
2. Матрица фазы 2 (`private/soak-24h`, ПК): `py -3.14 soak24.py --matrix phase2 --passes 3 --slot 300`.
   Ожидание (исследование, раздел 6.6, и симуляция выше): блэкаут 5/10/15/20 с — 0 переключений (на 20 с допустимы отмены
   `PRIMARY-RECOVERED-BEFORE-SWITCH`); 25/30/40 с — трафик на резерве за 24–27 с; потеря 5/10/20 % — 0; 50/80 % — 3 из 3;
   30 % — «любое», но без качелей; `primary-mtu` — уход (VPN-MTU) без живой пробы; задержка 200/500 мс — без переключений.
3. Порог потерь: `py -3.14 soak24.py --kinds primary-netem-loss-35,primary-netem-loss-40,primary-netem-loss-45 --passes 3 --slot 300`.
   Ожидание: 40/45 % — 3 из 3 за ≤ 60 с (медиана ~35–40 с), 35 % — большинство.
4. Флаппинг, фаза 3: `py -3.14 soak24.py --matrix phase3 --passes 1`. Ожидание: каждый сбой 60 с, пока трафик на основном, —
   уход; возвраты не быстрее `return_hold`; в `probe-history.json` эпизоды `reason: model` заканчиваются
   `failure-confirmed`/`switched`.
5. Сравнение с прежним правилом на тех же блэкаутах (A/B): `uci set homensai_vpn.main.failure_model='consecutive'; uci commit homensai_vpn`,
   `py -3.14 soak24.py --kinds primary-blip-15,primary-blip-20,primary-blip-25,primary-blip-40 --passes 3 --slot 300`, затем
   вернуть `uci set homensai_vpn.main.failure_model='hmm'; uci commit homensai_vpn`.
6. Сутки без сбоев: `py -3.14 soak24.py --hours 24` (матрица по умолчанию) — между циклами ни одного ложного перехода;
   доля проб с `dense: true` в `status.samples` — единицы процентов.
7. LAN-набор (реальный клиент за роутером, `docs/LAN-HELPER.ru.md`): во время цикла `primary-blip-40` и после возврата —
   `pwsh -NoProfile -File .\client-test.ps1 -Router http://192.168.8.1:8080/ -CableInterface <N> -ProbeOnly`
   (DNS и два HTTPS проходят через выбранный канал; переключение он не доказывает).
