# Возврат с отказавшего резерва, настройки по исследованию и туннели после Stop (03.11.2026)

Ветка `feat/rescue-tuning-ux-20261103` от `0c8b6400` (запись 2.1.0-alpha7). Три пункта, одобренные владельцем. Версия не повышалась, на роутере не проверялось.

## 1. `rescue_stable` — возврат, когда отказал сам резерв

Офлайн-исследование (генетический алгоритм и отжиг, `private/math/evolution/REPORT.ru.md`) нашло расхождение: заметки alpha6 обещали «вернётся сразу», а `committed_recovery_decision` при отказавшем резерве ждал полный `primary_stable`. Вдобавок `finish_committed` перед возвратом ещё раз спрашивал `recovery_ready` с полным `primary_stable`: короткое правило без этой правки остановилось бы на `HELD-ON-RESERVE / SOURCE-NOT-VERIFIED`, то есть на отказавшем резерве.

Теперь, если резерв, который везёт трафик, сам отказал (`RESERVE-FAILED-PRIMARY-VERIFIED`), основной возвращается после `min(primary_stable, rescue_stable)` секунд стабильности. Остальные условия прежние: `primary_successes` подряд и живая проверка DNS/HTTPS. Удлинённое удержание от флаппинга и пауза на резерве не применяются, как и раньше.

- Настройка владельца `recovery_rescue_stable`: по умолчанию 10 с, диапазон 0–60, **0 — прежнее правило** (полный `primary_stable`). Поле есть в мастере «Правила переключения Auto»; старая страница, которая его не передаёт, значение не трогает.
- Реализация одинакова в Python и Lua: `recovery_settings.rescue_settings`/`stable_seconds` и `pair.rescue_settings`/`stable_seconds`. Временная метка `rescue_return` — это булево значение в памяти, не опция UCI, и в отпечаток настроек она не входит. Её читают `recovery_ready` (`native_switch.Linux`, `backend.lua`), `committed_recovery_decision` и `source_ready` (обе среды).
- Не изменён возврат из состояния «ядро на резерве» без журнала COMMITTED (`pair_auto.tick` / `pair.lua`, ветка `kernel.role=='target'`): он по-прежнему ждёт `min_dwell` и паузу между попытками.

## 3. Туннели после Stop

На MT3000 сегодня проявилось следующее. После Start подготовка выключает автозапуск GL (`network.<туннель>.auto=0`, `PREP-*-AUTOSTART`), чтобы пару поднимал только Auto. Когда Auto остановлен, переключатель туннеля в VPN Dashboard GL ничего не делал, и владелец думал, что VPN сломан.

- **Возврат флагов после Stop владельца** (`preparation_control.restore_autostart`). Супервизор вызывает его после каждого прохода пары (Python — `native_switch.serve`, Lua — `auto.lua` → `backend.autostart_after_stop` → `python3 preparation_control.py restore-autostart`). Работа идёт только при смене одного из определяющих файлов, поэтому на холостом проходе дочерних процессов нет. Под замком управления возвращается значение из записи «до» (`'1'` или опция снимается), только если выполнены все условия:
  - намерение Auto не `on`; защёлка Stop (`native-stop.json`) цела, поставлена страницей (`request_source` `manual`) и новее начала сессии и маркера возобновления владельца;
  - журнал отсутствует или `ROLLED-BACK`; сессия `STOPPED` (без передачи и удержания клиентов при загрузке), `FAILED` без владения, отсутствует или `HELD` только из-за правки снаружи (путь передачи HELD: К9 держит защиту до Start или Stop, этот Stop её и снимает; остальное в сессии не трогается);
  - флаг всё ещё равен `'0'`, который поставило приложение, у клиента свой протокол и есть проверенная запись подготовки. Флаг, который владелец поменял сам, остаётся как есть. Флаги, которые приложение не меняло, не трогаются.
- Туннели не поднимаются и не останавливаются: нет `ifup`/`ifdown`/reload. Записи возвращённых флагов удаляются, потому что изменение отменено. Следующий Start снова готовит роутер с новой записью «до», и история подготовки не растёт от циклов Start/Stop. В системный журнал пишется строка `PREP-AUTOSTART-RESTORED: network.<туннель>.auto <значение> after the owner Stop`. Записывает один узкий писатель `preparation_write.lua` (действие `restore-autostart`: только `auto` у `wgclientN`/`ovpnclientN` и только поверх `'0'`, с чтением после записи).
- **Подсказка.** Когда Auto выключен, а выбранный туннель не поднят (у привязанного интерфейса `disabled`, или `VPN-001`), лампа Auto показывает «Туннели поднимает Auto — нажмите Start.» / «Auto brings the tunnels up — press Start.» с существующим кодом `TUNNEL-DISCONNECTED`. Новых кодов и строк в таблице ошибок нет. Бюджет страницы (`test_lazy_help_ui.js`, ≤ 941 706 байт): сборка с этими правками даёт 941 658 байт. Для этого профили восстановления встраиваются в страницу компактным JSON (`build_sidebar_ui.py`), а схема в «Помощи» поле `rescue_stable` не показывает.
- Согласование с `fix/formal-k2-k5-20261103` (К9): ветка только прочитана. Охрану HELD, `outside_hold`, `release_session` и `release_for_start` эта правка не трогает. Общие файлы — `native_switch.py` (`source_ready`/`committed_recovery_decision` против `finish_committed(hold=…)` у К2) и `pair.lua`/`transaction.lua`; при слиянии правки лежат в разных функциях. Если К2 принят: возврат по `RESCUE_REASON` в `finish_committed` должен по-прежнему идти через `rescue_settings`, а `hold=` относится только к очистке без Stop владельца.

## Интеграция 2.1.0-alpha8 (03.11.2026, ветка `integ/alpha8-20261103`)

### Одно правило возврата вместе с детектором HMM

Ветки `feat/rescue-tuning-ux-20261103` и `feat/hmm-detector-20261103` меняли одно и то же решение о возврате. При слиянии
оно сведено в одну чистую функцию, одинаковую в обеих средах: `recovery_settings.return_rule` (Python) и
`pair.return_rule` (Lua), общие случаи — `router/tests/rescue_stable_cases.json` (разделы `return_rule` и `combined`).

| Резерв | Стабильность основного (`recovery_ready`) | Условие модели HMM (`channel_model.return_ready`) |
|---|---|---|
| **отказал сам** (`failed`: модель владельца, для `consecutive` — серия) | `min(primary_stable, rescue_stable)` (0 — весь `primary_stable`) | **не применяется** — возврат с мёртвого резерва не задерживается |
| **не отказал**, плановый возврат (`planned`) | `max(primary_stable, hold)` (`hold` — гашение флаппинга) | в режимах `hmm`/`hmm-fast` обязательно; в `consecutive` — нет |
| неизвестно (`unknown`, только ядро на резерве: серия успехов резерва не набрана, отказа нет) | `primary_stable` | нет (как до детектора) |

Где решается:
- `native_switch.committed_recovery_decision` / `lua/transaction.lua` `M.committed_recovery_decision` (журнал COMMITTED):
  `return_rule(settings, failed ? 'failed' : 'planned', hold)`.
- `pair_auto.tick` / `lua/pair.lua` `M.tick` (ядро на резерве без журнала COMMITTED): здоровый резерв → `planned`,
  резерв, отказавший по модели владельца (`channel_failed` резерва) → `failed`, иначе `unknown`. **Новое:** спасение
  действует и здесь. С `primary_stable` 120 с по умолчанию без этого мёртвый резерв держал бы трафик 120 с.
  `min_dwell` и пауза между попытками на этом пути остаются, как и были.

Проверки: `test_rescue_stable.py` и `lua/test_rescue_stable.lua` (15 случаев `return_rule`, 30 решений `combined`:
здоровый или отказавший резерв × `hmm` / `hmm-fast` / по умолчанию / `consecutive`; спрашивалась ли модель и для какого канала).
Мутации на копии дерева (`mutate_return.py`, 18 мутантов, Python и Lua: спасение без секунд rescue, условие модели для
отказавшего резерва, условие без учёта `consecutive`, без гашения, «отказ → плановый», условие снято или навязано) — все
18 убиты. Связь самого `tick` с `return_rule` на уровне тика тестами не закрыта (см. «Не сделано»).

### Стоковый автозапуск vpn-client после Stop владельца (решение владельца 03.11.2026)

При Start подготовка `vpn-boot` (`PREP-STOCK-VPN-BOOT`) удаляет ссылку автозапуска стокового клиента GL
`/etc/rc.d/S??vpn-client`. Запись «до» (`before.links`: имя и цель каждой ссылки сервиса) уже сохранялась, добавлять её
не понадобилось. Теперь `preparation_control.restore_autostart` после Stop владельца возвращает и эту ссылку. Условия те же,
что для `network.<туннель>.auto`: намерение не `on`, ручной Stop новее начала сессии и маркера возобновления, журнал
отсутствует или `ROLLED-BACK`, сессия остановлена, нет незавершённых ручных команд. Сверх этого:

- ссылка возвращается только тогда, когда сейчас у сервиса **нет ни одной** ссылки запуска (`S..vpn-client`). Если владелец
  включил сервис сам, хоть под другим номером, его ссылка остаётся, а запись не трогается;
- остальные ссылки сервиса (`K..`) совпадают с записанными, а `/etc/init.d/vpn-client` — обычный файл. Иначе ничего не
  делается (`boot_kept`);
- создаётся только символическая ссылка с записанными именем и целью. Init-скрипт не запускается, сервис не стартует и не
  останавливается, туннели не трогаются. Ссылку подхватит следующая загрузка;
- ссылка читается обратно, после этого запись подготовки удаляется. В журнал пишется
  `PREP-BOOT-RESTORED: /etc/rc.d start link of vpn-client after the owner Stop`. Следующий Start снова готовит роутер,
  с новой записью «до».

Супервизоры вызывают это после каждого прохода пары. `/etc/rc.d` добавлен к файлам, по которым определяется холостой проход
(`preparation_control.after_stop_key` и `backend.lua` `after_stop_key`). Ответ: `boot_restored` / `boot_kept`.

Проверки (`test_autostart_restore.py`): ссылка возвращается вместе с флагами, записи удаляются, повтор ничего не меняет;
циклы Start/Stop не растят историю; при каждом отказе (Auto включён, сессия не остановлена, Stop не владельца,
незавершённая команда, неподтверждённая запись флагов, повреждённая запись) ссылка не появляется. Ссылку, сделанную
владельцем (в том числе под другим номером), появившуюся `K`-ссылку и пропавший init-скрипт код не трогает. Если осталась
только запись `vpn-boot`, UCI не читается. Запись без ссылки запуска ничего не возвращает. Если ссылка после записи не читается, запись остаётся
(`PREPARATION-WRITE-UNCONFIRMED`). Мутации `restore_autostart` на копии дерева: 9 из 9 убиты. Десятый мутант эквивалентен:
отказ записи флагов всё равно ловит их чтение после записи. Проверка на роутере не выполнялась.

Проверка на роутере (MT3000, с разрешения владельца): Start → `ls /etc/rc.d | grep vpn-client` — ссылки `S..` нет;
Stop на странице → после `STOPPED`: `logread | grep PREP-BOOT-RESTORED`, `ls -l /etc/rc.d/S*vpn-client` (прежнее имя и цель
`../init.d/vpn-client`), сервис при этом не запущен заново (`ps | grep vpn-client` без изменений). Перезагрузка без Auto:
клиент GL стартует, как до установки.
