# Куда уходят ~255 с после отключения питания MT3000 — разбор, 01.11.2026

> Разбор 01.11.2026 по журналам стенда (только чтение, без доступа к роутеру). Изменения ниже сделаны в ветке `lua/agent-boottime-20261101` для Python и Lua. Выигрыш — **оценка**, на роутере ещё не измерен.

Источник: `private/soak-24h/` — `midcut-log.jsonl` (alpha22, питание снято посреди ручного переключения), `soak-log-alpha20-lua3h.jsonl`, `soak-log-alpha21-c3h.jsonl`, текущий `soak-log.jsonl` (alpha24). В каждом цикле `sysrq-*` есть `reboot` (`ssh_back_s`) и `post_boot.boot_timeline`: опрос `status` раз в ~3 с, строка пишется только при смене состояния. Время — `uptime` роутера, секунды.

## Что измерено, а что выведено

- **Измерено:** время каждой смены состояния в `boot_timeline`; момент, когда `requested` стал `on` (Start принят); число попыток `boot_resume` (`attempts`); одна строка `ROLLBACK-BOOT-RETRY` в midcut.
- **Измерено один раз (старые доказательства):** WAN (`wwan`) поднялся на ~64 с (`evidence-alpha13-powercut-held.json`); OpenVPN от `ifup` до `Initialization Sequence Completed` ~4 с (alpha11); WireGuard ~1 с, перезагрузка firewall после ifup/ifdown ~1–2 с (alpha16).
- **Не видно:** что происходит до первого ответа `status` (~47–53 с). Стенд начинает опрос после SSH (~41 с после разреза, это уже ~45 с uptime). Шагов внутри восстановления в журнале не было — `logread` в циклах почти пустой.
- **Выведено из кода:** разбивка внутри интервалов (см. ниже, помечено «вывод»).

## Разбивка ~255 с (midcut, alpha21 #0)

| Отрезок | С | Чьё | Как известно |
|---|---|---|---|
| Разрез → загрузка ядра, procd, наш сервис отвечает | 0 → ~50 | прошивка | измерено (верхняя граница) |
| Восстановление: поднять туннели пары, `vendor_settled`, откат, повтор после `KERNEL-POLICY-UNVERIFIED` с паузой 20 с | ~50 → 138–141 | **наше** (ждём прошивку внутри) | итог измерен; разбивка — вывод; повтор — строка в журнале |
| После отката до конца очистки пары | 135–141 → ~234 | **наше**, причина не доказана | измерено ~95 с; вывод: `ifdown` + `quiet(45)` на каждый туннель, но строк `PAIR-CLEANUP` в опросе нет |
| Ожидание следующей попытки `boot_resume` (шаг 15 с) | ~234 → ~249 | **наше** | измерено 12–15 с во всех трёх циклах |
| Запуск пары: `ifup`, тишина прошивки, проверка | ~249 → ~255 | наше + прошивка | измерено ~6 с |

Итого: прошивка — ~50 с до нашего сервиса. Остальные ~205 с — наши шаги. Часть из них — ожидание прошивки (туннели, firewall, `rtp2.sh`), но решаем, сколько ждать, мы.

`boot_resume` пробовал 14 раз (с ~53 до ~249 с, каждые 15 с). Все попытки до ~249 отказаны — восстановление ещё шло.

## Что сделано (безопасно, Python и Lua одинаково)

| Файл | Изменение |
|---|---|
| `lua/auto.lua`, `native_switch.py` | `BOOT_RETRY_WAIT` 20 → 5 с. Каждый повтор отката и так начинается с `vendor_settled()` (тихие воркеры GL, два одинаковых отпечатка ядра, с пределом). Проверки, коды, окно без счёта (600 с) — те же. |
| `lua/boot_resume.lua`, `boot_resume.py` | Шаг попыток `EVERY` 15 → 5 с. Отказ Start — это чтение под замком, дёшево. После передачи Start в `agent.py` (только Lua) пауза по-прежнему 15 с (`FALLBACK_EVERY`): два Python-процесса сразу не запускаются. |
| `lua/boot_resume.lua`, `boot_resume.py` | Перед **каждой** попыткой снова читается маркер и защёлка Stop. Stop, нажатый в окне загрузки, побеждает сразу (раньше проверялось один раз в начале). |
| `lua/boot_resume.lua`, `boot_resume.py` | Принятый Start наблюдается `START_WATCH`=240 с. Если запрос, который он поставил, упал (`failed_request_id` = этот запрос), Start нажимается снова — не больше `START_RETRIES`=2 раз, в том же окне, со всеми проверками Start. Чужой отказ, Stop, перезапуск супервизора — не повод для повтора. |
| `lua/auto.lua`, `lua/pair.lua`, `lua/durable.lua`, `native_switch.py`, `pair_auto.py` | След загрузки: строка `BOOT-RECOVERY-STEP: <шаг> at <uptime>` на каждом шаге восстановления и очистки пары, только пока uptime < 600 с. Нужен, чтобы измерить отрезок ~95 с. |
| `tests/lua/test_boot_resume.lua`, `tests/lua/test_auto_recovery.lua`, `tests/test_boot_resume.py` | Тесты: шаг 5 с, пауза после `agent.py`, Stop в окне, повтор упавшего запуска с пределом, окно, чужой отказ, след загрузки. |

## Что нужно измерить на роутере

1. Повторить разрез посреди переключения и в покое на этой версии. Снять `logread | grep BOOT-RECOVERY-STEP` — так видно, сколько длится каждый шаг.
2. Отрезок ~95 с после отката: это `ifdown` + `quiet(45)` туннелей или что-то другое. Если это очистка пары — см. предложение 1 ниже.
3. Код, с которым падает ранний запуск пары после разреза в покое (`boot-resume.json` теперь пишет его в `code` при повторе). Стенду стоит сохранять `blockers` в `boot_timeline`.
4. Сработал ли повтор Start и сколько раз.

## Предложения, требующие решения владельца (не сделано)

1. **Не гасить туннели пары при загрузке, если `boot_resume` всё равно нажмёт Start.** Сейчас восстановление поднимает туннели (для guard), откатывает, потом очистка пары их гасит, потом Start поднимает снова. Возможный выигрыш — до ~90–100 с, но это меняет устройство «забора» после разреза. Нужен замер (пункт 2) и решение владельца.
2. **`VENDOR-SETTLING` после запуска пары.** В циклах с kill Auto даже на alpha24 (предел 45 с) блокировка длится ~100–130 с. Похоже, что прошивка меняет поколение туннеля несколько раз и срок начинается заново. Отдельный разбор.
