## Что кэшируется

| Что | Где | Ключ | Когда считается заново |
|---|---|---|---|
| Зоны `/var/run/fw3.state` (чтение, проверка UTF-8, разбор `zones`) | `platform.fw3_zones` (Lua), `native_platform.fw3_zones` (Python) | «отпечаток» файла | см. правила ниже |
| SHA-256 закреплённых скриптов прошивки (`PINS`, список аудита, `rtp_boot`) | `platform.sha_file` (Lua), `native_platform.sha_file` (Python) | «отпечаток» файла + предел размера | см. правила ниже |
| Список закреплённых программ `native-audit-hashes.json` (разбор JSON и порядок имён) | `backend.audit_order` (Lua), `Linux.diagnostic` (Python) | «отпечаток» файла | см. правила ниже |
| Разобранный JSON `ip -4 -j route show table all` и `ip -4 -j rule show` | `backend.route_reads` (только Lua) | **весь текст вывода** `ip` | при любом отличии текста; при каждой своей записи (`B.invalidate`) |

Правила «отпечатка» (`platform.cached_file` = `native_platform.cached_file`, одинаково в Lua, Python и C):

1. Ключ — `тип:inode:размер:mtime:ctime` из `lstat(path)`, взятый **до** чтения файла (секунды, как `sys.key`
   на роутере). Изменение файла после взятия ключа даёт другой ключ при следующем вызове.
2. Нет файла — нет записи в кэше (каждый вызов читает заново и получает ту же ошибку).
3. Ошибка при чтении или разборе — запись удаляется, следующий вызов читает и разбирает заново.
4. «Молодой» файл (новейшее из mtime/ctime моложе 2 с относительно часов в момент чтения) не считается
   надёжным: в следующий раз читается заново. Так перезапись того же размера в ту же секунду (ключ тот же)
   не может спрятаться — тот же приём, что «racy index» в git.
5. Запись живёт не дольше 30 с по монотонным часам; часы назад — пересчёт. Это ограничивает худший случай
   (скачок системных часов назад, после которого старый ключ совпал бы случайно).
6. Кэш привязан к таблице `sys` (на роутере одна; у каждого тестового «роутера» свой).

## Почему это безопасно

- Значение — чистая функция содержимого файла. Пока ключ тот же и запись надёжна (п. 4), содержимое не могло
  измениться без смены inode/размера/mtime/ctime: запись в файл меняет ctime (её нельзя выставить назад),
  а надёжная запись означает, что любая следующая запись получит время ≥ момента чтения > сохранённого.
- JSON маршрутов и правил переиспользуется только при **побайтно том же** тексте: `ip` по-прежнему
  вызывается на каждом проходе, поэтому изменённый маршрут или правило видны сразу (тест).
  Разобранные строки только читаются (`route_binding`), не изменяются.
- Ничего не привязано к ревизии управления: кэши зависят только от файлов и вывода ядра, поэтому
  Stop/новая ревизия не может получить «чужое» решение — значения те же для любой ревизии. Свои записи
  (`run_write`, `forward_dispatch`, аренда, uci) по-прежнему сбрасывают все кэши `backend` (`B.invalidate`).

## 4.2: почему без `ip monitor` и без чтения отдельных таблиц

- **Монитор событий не сделан** — не получается «очевидно безопасно»:
  - событие доходит до нас через процесс `ip`: ядро кладёт его в сокет сразу, но `ip` должен проснуться,
    прочитать и записать в канал. Под нагрузкой (именно тогда, когда чтение `table all` шло 3,4 с) эта
    задержка ничем не ограничена; «пустой канал» не доказывает «нет изменений». Барьера без собственной
    записи в ядро (или своего netlink-сокета, которого в Lua нет) нет;
  - при переполнении буфера сокета `ip monitor` пишет `ENOBUFS` в stderr и **продолжает работу** — события
    потеряны молча;
  - нужен неблокирующий разбор вывода дочернего процесса в цикле Auto и его перезапуск — новая сложность
    в ядре Auto ради экономии одного вызова `ip`.
- **Чтение только нужных таблиц не сделано**: `route_binding` ищет default-маршруты устройства **во всех**
  таблицах, а ответы `ip route get` (3 цели × 2 канала) кэшируются по полному тексту маршрутов и правил —
  `route get` зависит от любой таблицы, куда ведёт правило. С неполным текстом пришлось бы на каждом проходе
  запускать 6 `ip route get` — дороже.
- **Кэш «на проход» не сделан**: внутри одного прохода диагностика вызывается и как проверка перед записью
  (`apply_steps`, `assert_selection` перед каждой записью, ожидание после `rtp2.sh` в `verify-diagnostic`,
  где маршруты меняет фоновая перезагрузка прошивки, а не наша запись). Граница «прохода» там неочевидна,
  ошибка = решение по старым маршрутам.
- Сделано: `table all` читается как раньше, но разбор JSON (основная работа Lua) повторяется только при
  изменении текста. Дочерний процесс монитора не нужен; «монитор умер → полное чтение» выполняется всегда.

## 4.3: обход `/proc` оставлен на каждом проходе — решение прохода от него зависит

`platform.workers` (обход `/proc`: два чтения `stat`, `cmdline`, `wchan` на процесс) вызывается:

- `platform.assess` ← `backend.diagnostic` (каждая диагностика) и `backend.pair_preflight`;
- `platform.wait_quiet` ← `backend.apply` (после `rtp2.sh`), `net.lua` (ожидание тишины), `recovery.lua`
  (после отката: 286, 592).

Почему нельзя убрать из диагностики холостого прохода (`pair.tick`):

1. `reapply_missing_policy`: диагностика с `VENDOR-WORKER-BUSY` → публикуется `BLOCKED` и проход
   заканчивается; без обхода тот же проход дойдёт до `T.attempt` (повторное применение политики) — запись
   начнётся и будет отклонена уже внутри `apply_steps` с записью неудачной попытки в историю и журнал.
2. Основная диагностика прохода: `VENDOR-WORKER-BUSY` → `BLOCKED` (не `ARMED`: код не входит в список
   «подготовки»). Без обхода проход публикует `OBSERVING`, а при решении переключиться повторная полная
   диагностика (`b2`) даст `value_error('PAIR-READINESS-CHANGED')` → публикация отказа вместо `BLOCKED`.
3. То же в Python (`pair_auto.tick`), а условие 3 требует одинаковых решений.

Сами записи защищены и без обхода холостого прохода (`apply_steps`, `assert_selection` перед каждой записью
и `verify-diagnostic` вызывают полную диагностику, `wait_quiet` — после `rtp2.sh`), но **видимые решения**
(состояние, история, попытки) изменились бы. Предложение владельцу (отдельное решение, Lua + Python + C
вместе): «лёгкая» диагностика без обхода только для двух вызовов в `pair.tick`, а перед `T.attempt` (оба места)
и в `b2` — полная, при занятости — та же публикация `BLOCKED`, что сейчас. Цена: во время короткой работы
прошивки страница показывает `OBSERVING` вместо `BLOCKED/VENDOR-WORKER-BUSY`.

   том же тексте; `ip` вызывать на каждом проходе; сбрасывать при своей записи.
4. Обход `/proc` в `assess` не трогать (п. 4.3).
5. Общий тест решений: `file_cache` в `router/tests/test_lua_backend.py` (последовательности `lstat`/часов →
