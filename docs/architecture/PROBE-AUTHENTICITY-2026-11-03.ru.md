# Подлинность проверок канала (03.11.2026)

Пункт №1 криптографии, одобренный владельцем: проверки канала, которые нельзя обмануть. Ветка `feat/crypto-probe-20261103` от записи 2.1.0-alpha7 (`0c8b6400`). Код: `probe_trust.py` и его двойник `lua/probe_trust.lua`, общие случаи `router/tests/probe_trust_cases.json`. Роутер для этой работы не трогали: всё ниже проверено тестами в Docker и рукопожатием с настоящими серверами с ПК сопровождающего; шаги проверки на роутере перечислены в конце.

## 1. Как проверка работала до этого (2.1.0-alpha7)

Одна проверка канала (Python `agent.probe`, Lua-монитор `probe.lua`, Lua Auto `live_probe.lua`) делает одновременно:

| Цель | Адрес | Запрос | Что считалось верным ответом |
|---|---|---|---|
| one.one.one.one | 1.1.1.1:443 | `GET /cdn-cgi/trace` | статус 200, строки `ip=` и `http=` |
| dns.google | 8.8.8.8:443 | `GET /resolve?name=example.com&type=A` (JSON) | статус 200, `Status=0`, непустой `Answer` |
| dns.quad9.net | 9.9.9.9:443 | `GET /dns-query?dns=…` (RFC 8484) | статус 200, наш случайный 16-битный ID, QR, rcode 0, есть ответ |
| DNS по UDP | 9.9.9.9:53 | вопрос A `example.com`, случайный 16-битный ID | ID и вопрос совпадают, rcode 0, есть ответ |

Вердикт: меньше двух верных HTTPS-ответов — `VPN-003`; иначе без DNS — `DNS-001`; иначе здоров. Все сокеты привязаны к устройству туннеля (Python ещё и к fwmark), адреса фиксированы (`--resolve` в curl), DNS для HTTPS не нужен. Маршрут и устройство сверяются до и после измерения (`VENDOR-IDENTITY-CHANGED`).

TLS уже проверялся строго: Python `ssl.create_default_context()` (цепочка + имя), curl без `-k`, `--proto =https`, `--max-redirs 0`. Слабые места:

1. **Доверие всему системному хранилищу** (≈140 корней ca-bundle 20260601). Любой из них, включая случаи ошибочного выпуска (в 2025 году Fina RDC 2020 выпустил несанкционированные сертификаты на 1.1.1.1), делает подмену «настоящей».
2. **Причина не видна**: сертификат портала, редирект на портал и обычный обрыв давали одинаковые `tls-error` / `http-error` — непонятно, туннель мёртв или ответы подменяют.
3. **Нет свежести у trace**: страница /cdn-cgi/trace без привязки к запросу; кэширующий посредник с доверенным сертификатом мог бы вернуть старую страницу.
4. DNS по UDP подделывается любым посредником на пути (криптографии там нет и быть не может).

## 2. Модель угроз

| Угроза | Что делает | Чем закрыто теперь |
|---|---|---|
| Captive portal / платный Wi-Fi на выходе VPN | Перехватывает 443, отдаёт свой сертификат или 302 на страницу входа | Сертификат вне закреплённых корней → `untrusted-certificate`; 3xx → `portal-redirect` |
| DPI, подделывающий ответы | TLS с самоподписанным/чужим сертификатом, сброс | `untrusted-certificate`; сброс — обычный `tls-error`/`transport-error` (без заявления о подделке) |
| Национальный или ошибочно выпустивший УЦ | Сертификат на one.one.one.one от доверенного системой УЦ | Корни закреплены по хосту: чужой УЦ не принимается, даже если он в ca-bundle |
| Кэш / повтор страницы | Старый trace, «мёртвый туннель выглядит живым» | `uag=` должен равняться одноразовому nonce запроса; без `uag` — `ts` в пределах ±60 с |
| Перехват DNS | Подменённый UDP-ответ | Не закрывается криптографически; опция `probe_dns 'doh'` переносит DNS-проверку в HTTPS с закреплёнными корнями |
| «Живой туннель выглядит мёртвым» | Подделка одной цели | Кворум 2 из 3 сохранён; одна подделанная цель видна в деталях, но не валит канал |

## 3. Что проверяется теперь

### 3.1 Закреплённые корни (SPKI pinning на уровне якорей)

Для каждого из трёх фиксированных хостов в пакете лежит свой маленький набор корневых сертификатов: `/usr/lib/homensai-vpn/probe-anchors/<host>.pem`, и манифест `pins.json` (имя, роль `current`/`backup`, SHA-256 от SubjectPublicKeyInfo в base64, срок действия). Проверка TLS идёт **только** против этого набора:

- curl: `--cacert /usr/lib/homensai-vpn/probe-anchors/<host>.pem` (системное хранилище тогда не читается);
- Python: `ssl.create_default_context(cafile=…)` (то же: при `cafile` системные корни не загружаются), имя хоста проверяется как раньше.

Почему корни, а не ключ листового сертификата: curl `--pinnedpubkey` и Python 3.9 видят только лист, а Cloudflare и Google меняют ключи листа каждые 1–3 месяца — пин листа ломался бы на всех роутерах сразу. Ограничение доверия набором корней — та же идея (отказ всем остальным УЦ), без привязки к часто меняющимся ключам.

Все корни взяты из ca-bundle самой прошивки GL 4.11 (ca-certificates 20260601-1): закреплённый набор — строгое подмножество системного доверия, никогда не шире. Если файла нет (повреждённая установка), используется системное хранилище — проверка 2.1.0-alpha7, а не отсутствие проверки.

| Хост | current (цепочка 03.11.2026) | backup |
|---|---|---|
| one.one.one.one | SSL.com Root Certification Authority ECC (лист ← SSL.com SSL Intermediate CA ECC R2) | SSL.com RSA, SSL.com TLS ECC/RSA 2022, DigiCert Global Root G2/G3, DigiCert TLS ECC P384/RSA4096 G5, GTS Root R1/R3/R4, ISRG Root X1/X2 |
| dns.google | GTS Root R4 (лист ← WE2) | GTS Root R1 (цепочка WR2), GTS Root R3, GlobalSign ECC Root CA - R4 |
| dns.quad9.net | DigiCert Global Root G3 (лист ← DigiCert Global G3 TLS ECC SHA384 2020 CA1) | DigiCert Global Root G2, DigiCert TLS ECC P384/RSA4096 G5, ISRG Root X1/X2 |

Проверено 03.11.2026 рукопожатием с настоящими серверами (`openssl s_client -CAfile <host>.pem -verify_hostname`): каждый хост проходит со своим файлом; one.one.one.one не проходит с файлами Google и Quad9, dns.google — с файлом Quad9, dns.quad9.net — с файлом Google (`unable to get local issuer certificate`). SPKI в `pins.json` совпали с `openssl x509 -pubkey | openssl dgst -sha256`.

Набор Cloudflare шире остальных намеренно: 1.1.1.1 за последние годы менял УЦ (DigiCert → SSL.com), а trace-цель нужна не только для здоровья, но и для адреса выхода при переключении (`native_switch.trace`): если её УЦ окажется вне набора, переключение будет отказываться `EXIT-TRACE-FAILED`/`NATIVE-SYSTEM-001` до обновления пакета. Поэтому включены все УЦ, которые Cloudflare использует для своих сертификатов.

### 3.2 Одноразовый nonce и свежесть trace

Каждый HTTPS-запрос отправляет `User-Agent: HomenSAI-probe/<32 hex>` (128 бит из `/dev/urandom` / `os.urandom`, новый на каждый запрос; Lua — `curl -A`). Cloudflare `/cdn-cgi/trace` возвращает его строкой `uag=`. Правило (`probe_trust.fresh`):

1. есть строки `uag=` → все должны точно равняться нашему значению, иначе `nonce-mismatch`;
2. нет `uag=` (Cloudflare может убрать поле) → нужна ровно одна строка `ts=` в виде десятичного числа (до 12 цифр, до 9 знаков дроби), лежащая в окне `[время начала − 60 с; время конца + 60 с]` по часам роутера, иначе `stale-time` / `no-freshness`;
3. допуск на скачок часов: если за время запроса настенные часы сдвинулись больше чем на 2 с относительно монотонных (`|Δwall − Δmono| > 2`), сравнивать `ts` нельзя → `clock-jump` (проверка не засчитывается).

При совпавшем nonce `ts` не мешает: nonce сильнее (страница сделана для этого запроса), а неверные часы роутера (до синхронизации NTP после включения питания) не должны делать живой канал мёртвым. Неподходящий trace даёт `invalid-response` с причиной `stale-response`, адрес выхода из него не берётся. То же правило применено к отдельному запросу trace при переключении (Python `native_switch.trace`, Lua `live_probe.trace`): `EXIT-TRACE-FAILED`.

Для dns.quad9.net nonce уже был: случайный ID DNS-сообщения в URL возвращается в ответе (RFC 8484). Для dns.google JSON API ничего из запроса не возвращает — свежесть там держится только на TLS с закреплёнными корнями (см. «Не покрыто»).

### 3.3 Отдельная причина отказа без нового кода

Вердикт не меняется: меньше двух верных ответов — `VPN-003` (страница ошибок не расширялась). Добавлено:

- у каждой проверки в `probe_checks` поле `trust`: `untrusted-certificate` (Python `ssl.SSLCertVerificationError`; curl 60/51/83/90), `portal-redirect` (HTTP 3xx), `stale-response` (nonce/ts); на прошедшей проверке его нет;
- у результата `probe_trust: "untrusted"`, когда код `VPN-003` и хотя бы одна проверка не прошла по подлинности. Обычный обрыв (тайм-аут, сброс, curl 35/77) так не помечается.

Санитайзеры статуса (`vendor_observation.py`, `vendor.lua`) пропускают оба поля только из закрытого списка значений. Интерфейс по-прежнему показывает `tls-error`/`http-error` с HTTP-статусом; отдельной строки в таблице ошибок нет (бюджет страниц).

### 3.4 DNS: опция DoH (по умолчанию выключена)

`option probe_dns 'doh'` в `config main 'main'` файла `/etc/config/homensai_vpn` (только UCI, без интерфейса) заменяет UDP-вопрос к 9.9.9.9:53 тем же случайным вопросом в виде RFC 8484 GET к `https://dns.google/dns-query` через туннель, с закреплёнными корнями dns.google и проверкой ID/вопроса/rcode. Любое другое значение или отсутствие опции — UDP, как раньше. Файл перечитывается только при смене mtime/размера/inode. Стоимость при включении: один дополнительный HTTPS (в Lua — ещё один процесс curl, по замерам Lua-проекта 10–40 мс CPU на MT3000) вместо одного UDP-пакета; по умолчанию ноль.

Что есть в прошивке GL 4.11 (аудит образа MT6000 `mt6000-4.11.0_release3`, пакеты opkg): curl 7.83.1 + libcurl4 с OpenSSL 1.1.1t (умеет `--doh-url`, `--cacert`, `--pinnedpubkey`), ca-bundle/ca-certificates 20260601-1, uclient-fetch + libustream-openssl, openssl-util 1.1.1t (`s_client`), bind-dig 9.18.7 (собран с libnghttp2: `+https`, `+tls`), busybox nslookup, lua-eco-ssl/lua-eco-dns (только Lua 5.4 GL SDK), dnscrypt-proxy2, dnsproxy. Наш код использует только curl (Lua) и модуль ssl Python — новых зависимостей нет. dig/kdig на MT3000 не проверялись: в коде не используются.

Случайная метка в имени (`<random>.example.com`) не добавлена: такой вопрос даёт NXDOMAIN без ответа, а нынешний критерий требует непустой ответ; ослаблять критерий нельзя. 0x20-регистр в имени не добавлен: сохраняет ли Quad9 регистр, не проверено на роутере, а ошибка дала бы `DNS-001` на всех каналах сразу. Против перехвата DNS правильный инструмент — опция DoH выше.

## 4. Обновление и ротация пинов

- Источник правды — `scripts/build_probe_anchors.py` (таблица `ANCHORS`: хост → имена корней из `/etc/ssl/certs` прошивки, роль). Запуск: `python3 scripts/build_probe_anchors.py <каталог certs прошивки>` пишет PEM и `pins.json`; `--check` сверяет с закоммиченными.
- `test_probe_trust.AnchorFiles` независимо разбирает DER: SPKI и сроки в `pins.json` должны совпадать с PEM, у каждого хоста ровно один `current` и не меньше трёх `backup`.
- `test_rotation_deadline` **падает за год** до момента, когда у какого-либо хоста останется меньше двух действующих корней или истечёт `current`. Сроки сейчас: самый ранний корень — ISRG Root X1 (2035-06-04), `current` — SSL.com ECC до 2041-02-12, GTS Root R4 до 2036-06-22, DigiCert Global Root G3 до 2038-01-15 (`pins.json`); тест начнёт требовать ротацию не раньше лета 2035 года.
- Когда оператор цели меняет УЦ на корень вне набора: проверка этой цели станет `tls-error` + `untrusted-certificate` на всех роутерах; кворум 2 из 3 держит вердикт, но для Cloudflare блокируется адрес выхода при переключении. Порядок: снять цепочку (`openssl s_client -showcerts`), добавить корень в `ANCHORS`, пересобрать файлы, выпустить пакет. Отдельного сетевого механизма обновления пинов нет (его самого пришлось бы защищать подписью) — пины обновляются вместе с пакетом.

## 5. Цена

Замеры CPU в Docker (x86, Python 3.9, OpenSSL 1.1.1n — та же ветка, что 1.1.1t на роутере; ARM роутера медленнее в разы, соотношение то же):

| Что | До (системное хранилище, ca-bundle прошивки 182 КБ) | После (закреплённые корни) |
|---|---|---|
| Python: TLS-контекст на одну HTTPS-проверку | 19,1 мс | 2,9 мс (Cloudflare), 1,0 мс (Google), 1,8 мс (Quad9) |
| Процесс openssl с `-CAfile` (≈ загрузка CA в curl, с запуском процесса) | 39 мс | 14–19 мс |
| `fresh()` на один trace | — | 24 мкс (Python), 25 мкс (Lua) |
| `agent()` на запрос | — | 2,3 мкс (Python), 21 мкс (Lua, чтение `/dev/urandom`) |

Итог: проверка стала **дешевле** на ≈50 мс CPU (x86) за проход Python и на ≈20 мс на каждый процесс curl, потому что разбирается 4–13 корней вместо ≈140. Число процессов curl, ожидания и тайм-ауты не менялись; аргументов curl на 2–4 больше.
- Опция DoH (выключена по умолчанию) — см. 3.4.

## 6. Что не покрыто

- Скомпрометированный или сговорившийся УЦ из закреплённого набора (например, GTS для dns.google) — защиты нет; пин листа был бы хрупким (см. 3.1).
- dns.google JSON не возвращает ничего из запроса: свежесть только за счёт TLS и пинов. Переход этой цели на RFC 8484 (с ID-nonce, как у Quad9) — предложение, не сделано: меняет конечную точку без проверки на роутере.
- DNS по UDP (режим по умолчанию) подделывается посредником на пути; DNS-проверка может показать «есть DNS», когда его подделывают. Здоровье канала при этом всё равно требует двух подлинных HTTPS-ответов.
- Проверки идут с роутера (router-originated); путь LAN-клиента отдельно не доказан, как и раньше.
- Часы роутера до NTP: trace без `uag` и с `ts` вне окна не засчитывается (`stale-time`); с `uag` — засчитывается.
- Скорость (speed test), Telegram, отклик сайтов и прочие HTTPS вне проверки канала не менялись.

## 7. Проверка на роутере (выделенный MT3000, отдельным разрешением)

1. Установить пакет ветки; `ls /usr/lib/homensai-vpn/probe-anchors` — три PEM и `pins.json`.
2. Обычный проход монитора: у обоих каналов `probe_checks` все `ok`, нет `trust`, есть `exit_ip`. В `ps`/`logread` у curl видны `--cacert …/probe-anchors/<host>.pem` и `-A HomenSAI-probe/…`.
3. Ручная проверка пинов: `curl --interface <dev> --resolve one.one.one.one:443:1.1.1.1 --cacert /usr/lib/homensai-vpn/probe-anchors/one.one.one.one.pem -A HomenSAI-probe/test https://one.one.one.one/cdn-cgi/trace` → в ответе `uag=HomenSAI-probe/test`; с `--cacert …/dns.quad9.net.pem` → код 60.
4. Портал/чужой сертификат: на роутере поднять локальный HTTPS с самоподписанным сертификатом (`openssl req -x509 … -subj /CN=one.one.one.one`; `openssl s_server -accept 8443 -cert … -key … -www`) и временно перенаправить на него трафик одного канала (GL 4.11 / OpenWrt 21.02 — fw3/iptables: `iptables -t nat -I OUTPUT -o <dev> -d 1.1.1.1 -p tcp --dport 443 -j DNAT --to-destination <LAN-адрес роутера>:8443`; на fw4 то же правилом `nft … oifname <dev> ip daddr 1.1.1.1 tcp dport 443 dnat to …`). Не проверено, пропустит ли ядро такой DNAT для сокета, привязанного к устройству туннеля (SO_BINDTODEVICE); если нет — поднять `s_server` на машине по ту сторону туннеля или проверить вручную `curl --cacert …/one.one.one.one.pem --resolve one.one.one.one:8443:<адрес> https://one.one.one.one:8443/` → код 60. Ожидание: у one.one.one.one `tls-error` + `trust: untrusted-certificate`, канал остаётся здоровым (2 из 3). Повторить для 8.8.8.8 и 9.9.9.9 вместе — `VPN-003` + `probe_trust: untrusted`, Auto реагирует как на `VPN-003`. Правило удалить сразу.
5. Редирект 3xx возможен только от сервера с доверенным сертификатом (иначе раньше срабатывает `untrusted-certificate`), поэтому на роутере его не воспроизвести без настоящего портала; проверен тестами `test_probe_trust.RealTls` (настоящий TLS с тестовым УЦ) и общими сценариями обоих рантаймов.
6. DoH: `uci set homensai_vpn.main.probe_dns=doh; uci commit homensai_vpn` → следующий проход без UDP к 9.9.9.9:53 (`tcpdump -ni <dev> udp port 53` пуст), `dns_ok: true`; вернуть `uci delete homensai_vpn.main.probe_dns`.
7. Часы: `date -s` на 10 минут назад при работающем мониторе — проверки остаются `ok` (nonce), вернуть время.
