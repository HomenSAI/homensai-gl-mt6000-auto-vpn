## Пункт 1: быстрое обнаружение (`option lua_fast_detect '1'`, включено на MT3000)

Подозрение появляется через 2,6–3,1 с после начала сбоя (`lost 3 beats (send-refused); dense confirmation started`). Решение Auto приходит через 26–28 с, а раньше «с нуля» было 58–88 с. Остальные ~23 с — три неудачные полные проверки подряд (`failures`: по умолчанию 3, меньше 3 нельзя по проекту). Каждая проверка отрезанного канала ждёт истечения времени DNS и HTTPS.

## Пункт 2: автоматическое переключение по быстрому пути

Замер показал, что моя оценка в разговоре с владельцем (около 4 с) была завышена:
- от решения до ухода трафика — 1,3–1,6 с: проверка и подтверждение ядра ~0,5 с, UCI ~0,5 с, iptables ~0,5 с;
- остальные 3–5 с до COMMITTED идут уже после ухода трафика: это проверка резерва через новый путь, и пользователь её не ждёт.

Быстрый путь ручной кнопки занимает ~0,5 с, то есть выигрыш около 1 с. При этом пришлось бы менять защищённую автоматическую процедуру с откатом. Предложение владельцу: не делать сейчас, а заняться оставшимися ~23 с подтверждения сбоя.

## Что сокращает оставшееся время дальше (предложения)

1. **Короче ожидание в проверке канала, который уже под подозрением.** При плотном подтверждении — время ожидания DNS/HTTPS, например, 2 с вместо полного. Это даст примерно 23 → 10–12 с.
2. **Сделать быстрое обнаружение включённым по умолчанию** после 3-часового теста с ним.
3. **Вариант Б** для ожиданий прошивки (см. `VENDOR-SETTLING-2026-11-01.ru.md`).
