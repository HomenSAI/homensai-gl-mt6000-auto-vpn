Изменения одинаковы в обеих средах (Lua и Python); у каждого контрпримера есть тест, который падает на исходной ветке и проходит после исправления (`router/tests/lua/test_formal_fixes.lua`, `router/tests/test_formal_fixes.py`, хвост К1 — `router/tests/test_held_start_handover.py`). Новых кодов состояния нет; в системный журнал добавлены строки `PAIR-OUTSIDE-CHANGE-GUARD: …` и `GUARD-DEVICE-UNAVAILABLE: HELD-ON-RESERVE …`.

## Что изменилось в поведении

- **К3 — защита после отключения питания на резерве.** Если журнал в состоянии HELD-ON-RESERVE и маршрут по-прежнему его (резерв первым), восстановление после перезагрузки сразу ставит VPN-only на поднятые туннели — как для COMMITTED. Сессия, переданная на резерв (STOPPED с передачей), тоже поднимает свои клиенты для этой защиты. Раньше защиты не было до отпуска передачи (до 600 с). Если ни один туннель не поднялся — строка `GUARD-DEVICE-UNAVAILABLE` и решение за обычным проходом, как для COMMITTED.
- **К4 — запуск пары с медленными клиентами.** Полная блокировка LAN сама снимается через 90 с, а подъём двух клиентов может идти до ~170 с. Теперь защита ставится заново перед каждым ограниченным шагом (ожидание 20 с, `ifup -w`, ожидание 45 с) — LAN не остаётся без защиты, а при гибели процесса блокировка по-прежнему снимается ядром через 90 с. Уже стоящая VPN-only не понижается до самоснимающейся блокировки: Start после передачи резерва (резерв проверен) и Start, который завершает удержание внешней правкой (К9), держат VPN-only на поднятых туннелях — пока поднимаются клиенты, LAN работает через туннель.
- **К2 — удержание возврата после перезапуска.** Очистка, которую не просил Stop владельца (восстановление после сбоя/питания, отпущенная передача), возвращается на основной только после удержания по журналу переключений (`ledger_hold`), как обычный проход. Проверка передачи («основной уже доказан») тоже считает с этим удержанием. Stop владельца и отказавший резерв возвращают без удержания, как раньше.
- **К5 — запись COMMITTED.** Проверка ревизии и запись COMMITTED идут под одним замком управления (также в завершении после перезапуска `forward_resume`): Stop либо раньше (откат), либо позже записи, но не между ними. Ранняя проверка ревизии перед проверкой порядка осталась (как в `attempt`): Stop, пришедший раньше, по-прежнему даёт CLIENT-STOP до замка.
- **Хвост К1 — возобновление после питания.** Ранняя передача сессии, удержанной правкой в GL (58921e2f), выполняется и для программного Start возобновления, если есть маркер владельца (`auto-resume.json`) и нет более нового Stop. Проверки условий (terms, ревизия, ledger, журнал, подготовка) те же.
- **К9 — решение владельца: защиту держим.** Сессия, удержанная внешней правкой в GL (коды PAIR-EXTERNAL-NETWORK-CHANGE / CONFIG-CHANGE / POLICY-CHANGE / SOURCE-ORDER-MISMATCH), при спокойном журнале (нет или ROLLED-BACK) держит LAN за VPN-only до Start или Stop — и после отключения питания. Если ни один туннель не работает, интернета нет: ставится полная блокировка, она обновляется каждые 45 с (и снимается ядром через 90 с, если процесс погиб). Stop снимает защиту, как обычно. «Stop новее» считается по защёлке Stop (`native-stop.json`) против более позднего из маркера владельца (`auto-resume.json`) и начала самой сессии (`started`): программный Start маркера не оставляет, и старая защёлка не снимает защиту более поздней сессии; повреждённая защёлка — не Stop. То же правило решает в К2, нужно ли удержание. Start идёт через передачу 58921e2f.

## Проверки на роутере (MT3000, по разрешению владельца)

1. **Питание в окне передачи (К3).** Auto включён, переключение на резерв, основной остаётся мёртвым; отключить питание → после загрузки идёт передача (`BOOT-RECOVERY-STEP: pair cleanup handover on the reserve`). До нажатия Start снова отключить питание. Ожидается: после второй загрузки `nft list table inet homensai_vpn_guard` показывает правило `oifname != { … }` (VPN-only) сразу после восстановления, клиенты пары подняты (`PAIR-RECOVERY-REVIVE: ifup …`), журнал HELD-ON-RESERVE, LAN-клиент ходит только через туннель резерва; Start затем принимает передачу (COMMITTED BOOT-RESERVE-ADOPTED).
2. **Медленный старт (К4).** Оба клиента выключены, Start; во время подъёма раз в 5 с читать `nft list table inet homensai_vpn_guard`. Ожидается: таблица есть всё время (имя набора `blocked_lan_<generation>` меняется при каждом шаге), без окна без защиты; в конце правило VPN-only. Start после передачи резерва: только VPN-only, без полной блокировки, LAN работает через резерв. Start после удержания внешней правкой (п. 3): тоже только VPN-only на поднятых туннелях.
3. **Правка в GL, затем питание (К9).** Auto работает, в GL изменить VPN-клиентов → HELD с кодом внешней правки; отключить питание. Ожидается: после загрузки таблица защиты есть (VPN-only, либо полная блокировка, обновляемая каждые 45 с, если туннели не поднялись), строка `PAIR-OUTSIDE-CHANGE-GUARD`; Stop снимает таблицу (`released by the owner Stop`); Start (или возобновление с маркером владельца) — передача, подготовка и новый старт.

## К11 — исправлено в этой же ветке

Модель с включёнными шестью исправлениями (К1-хвост, К2, К3, К4, К5, К9) показала новое нарушение «k11-start-hand-over». Это настоящая ошибка продукта, не артефакт модели: передача 58921e2f (`release_for_start` / `request` → `release_session`, под замком управления) архивирует сессию и пишет запись STOPPED, а проход очистки супервизора, который прочитал запись HELD раньше (не под замком), затем писал поверх свою STOPPING. Дальше та же очистка снова падала на внешней правке и возвращала HELD; Start владельца уже был принят, но следующий проход видел чужую незавершённую сессию — PAIR-RECOVERY-REQUIRED, сессия HELD с этим кодом (уже не код внешней правки, так что ранняя передача не срабатывала) до Stop и нового Start. Окно — от чтения записи в начале прохода до первой записи очистки (миллисекунды–секунды).

Исправление (обе среды, `pair.cleanup` / `pair_auto.cleanup`): запись STOPPING делается под тем же замком управления, запись перечитывается; если на диске уже другая сессия или завершённая (STOPPED/FAILED) при незавершённой у прохода — проход заканчивается без записи (`cleanup` возвращает false, в журнале загрузки `pair cleanup superseded by a hand-over`). Пустая запись (тесты, вызывающие `cleanup` без сохранённой сессии) ведёт себя как раньше. Новых кодов нет.

Тот же класс гонки есть и на пути ошибки (найдено при проверке 04.11.2026, в модели не представлено — там `publish_failure` атомарен): если очистка падает до записи STOPPING (например, PAIR-EXTERNAL-POLICY-CHANGE при проверке контекста журнала), `publish_failure` читал запись HELD и писал её же HELD с кодом без замка — передача Start между чтением и записью так же перезаписывалась. Теперь чтение и запись HELD в `publish_failure` (обе среды) идут под замком управления; после передачи запись STOPPED не трогается. Все вызовы `publish_failure` — вне замка (проверено по коду: `recover`, `tick`, `serve`/`auto.iteration`), повторного входа нет.

Тесты: `K11` в `test_formal_fixes.py` и `test_formal_fixes.lua` — (1) передача вставлена в первый шаг `cleanup`; (2) `publish_failure` пишет HELD только внутри замка, после передачи запись остаётся STOPPED. Сам замок в `cleanup` (а не только перечитывание) модульным тестом гонки не воспроизводится — по построению (Start пишет запись только под этим замком); для `publish_failure` тест проверяет, что запись идёт внутри замка.

3. **Удержание внешней правкой писало запись каждые ~2 с (среднее).** Сессия HELD с кодом внешней правки (К9) без Auto: каждый проход писал STOPPING (`cleanup`), затем HELD (`publish_failure`) — запись на флеш каждые ~2 с на всё время удержания, а в Lua-среде ключ «после Stop» (в нём inode/mtime файла сессии) каждый раз запускал python3. Теперь `held_unchanged` без записи находит отказ, который очистка дала бы до первого действия (порядок правил, сеть, конфигурация), и тогда ничего не пишется; `publish_failure` не переписывает неизменную запись HELD. Изменение правки (другой код) пишется один раз; отменённая правка — очистка как раньше. Ключ «после Stop» (обе среды) теперь берёт из записи сессии только то, от чего зависит решение (`SESSION_FIELDS`: id, phase, recovery_error, started, owned, kept, handover), а не inode/mtime: сессия HELD с удержанным журналом или ждущая демпфированного возврата по-прежнему пишет STOPPING + HELD на своих проходах (там очистка действует на самом деле), но python3 из-за этого больше не запускается.
4. **Осиротевшая VPN-only после передачи и отказа Start (среднее/низкое).** `release_for_start` передаёт сессию (STOPPED, owned=[]); если Start затем отказал до `request` (подготовка, SPEED-BUSY, CONTROL-REVISION-STALE) или оборвался, защита К9 оставалась без сессии — LAN без интернета при маршруте через WAN, а Stop её не снимал (путь журнала требует восстановленного порядка). Теперь отказавший после передачи Start снимает её сам (`auto_control.start`), а супервизор снимает после Stop владельца (`release_orphan_guard`, один раз на запись): только у записи STOPPED с передачей (`AUTOMATIC-EXTERNAL-CHANGE-READOPT`), без своих интерфейсов, kept/handover, при намерении не 'on' и журнале нет/ROLLED-BACK. До Stop супервизор читает на холостом проходе защёлку и маркер (два маленьких файла, без дочерних процессов), после Stop запись больше не смотрится.
5. **К9 при owned=[] (низкое).** Сессия без своих интерфейсов (клиенты были подняты до неё) при NETWORK-/CONFIG-CHANGE не проверяла сеть в очистке и сразу становилась STOPPED без защиты. По решению владельца К9 («защиту держим до Start или Stop») изменение теперь проверяется снова и для неё (`outside_recheck`), пока нет Stop владельца; Stop завершает удержание как раньше (своих интерфейсов нет — останавливать нечего). POLICY-CHANGE и SOURCE-ORDER-MISMATCH не меняются (порядок правил очистка проверяет всегда; повторной проверки SOURCE-ORDER-MISMATCH в очистке нет).
6. **Возврат заряда после настоящего переключения (низкое).** Коды VENDOR-* бывают и после самого переключения (ожидание проверки после rtp2, wait_quiet после отправки) — тогда откат шёл после двух настоящих переключений ядра, а `refund_abort` возвращал заряд. Теперь заряд возвращается только если журнал доказывает, что ничего не записано: `rtp_dispatched` и `forward_policy_touched` оба ровно false. Случай цикла 28 (отказ на первой диагностике шага применения) не меняется.
7. **Пересборка резерва вендором (высокое, инцидент MT3000 04.11 14:06–15:33).** Вендор пересобрал резерв OpenVPN под трафиком, изменился только `vendor_generation`; каждый проход давал HOLD RESERVE-IDENTITY-UNKNOWN, Auto больше часа стоял в DEGRADED-ON-RESERVE при двух здоровых туннелях, помог только Stop + Start. Правило (обе среды, `committed_recovery_decision`): вендор спокоен (READY), те же id, протокол, интерфейс и туннель и успешная серия замеров **нового** поколения — это тот же резерв, решение идёт дальше, а проход пары переписывает доказательство в журнале (`reserve_rebound`: обе роли, свежая диагностика без блокеров, под замком управления, Stop важнее). Всё остальное остаётся неизвестным, но со стабильно здорового основного Auto возвращается обычным плановым правилом (min_dwell, max(primary_stable, hold), шлюз модели, защищённый `finish_committed`). `hold_reserve` владельца соблюдается для работающего или неизвестного резерва; при занятом вендоре (не READY) — по-прежнему HOLD. **Уточнение 07.11.2026 (решение владельца, F-80):** `hold_reserve` теперь означает «не возвращаться с РАБОТАЮЩЕГО резерва». Резерв, который детектор сбоя назвал отказавшим и свежая проверка роутера подтвердила отказ (`health == False`), спасается на проверенный основной по существующему правилу спасения (`rescue_stable`, без шлюза модели, через `finish_committed` и его защиту) при любой политике возврата; неизвестная или устаревшая проверка (RESERVE-HEALTH-UNKNOWN) остаётся удержанием, неизвестная идентичность резерва — тоже. Спасение не учитывает удержание `return_hold`, поэтому «пинг-понг» ограничен только бюджетом попыток (3 за 15 мин, пауза 60 с). Общие случаи — `rescue_stable_cases.json`, разделы `decisions` и `combined`. Новых кодов и состояний нет, новая строка журнала `PAIR-RESERVE-REBOUND`. Формальную модель менять не потребовалось: идентичности резерва в ней нет, новые ветви ведут в уже описанные переходы. То же правило в ручном удержании (`pair_manual.held_reserve`, `manual.held_reserve`: `hold_verified`, `hold_released`): пересобранный канал с успешной серией нового поколения — доказательство переписывается (у удержания основного журнал может быть ROLLED-BACK, `settled`), удержание продолжается; серия отказов нового поколения снимает удержание, как раньше; неизвестный резерв держится, пока автоматическое правило не вернёт трафик на основной, тогда удержание заканчивается и тот же проход делает защищённый возврат (`hold_reserve` соблюдается). Удержанному основному возвращаться некуда: BLOCKED, пока серия не решит в ту или другую сторону; другой туннель — не пересборка, BLOCKED остаётся. Тесты: `reserve_rebuild_cases.json` (17 решений автомата, 15 решений удержания и воспроизведение инцидента), `test_reserve_rebuild.py`, `lua/test_reserve_rebuild.lua`.

1. **T1. Auto возвращался после питания вопреки последнему Stop (высокое, обе среды).** Правило владельца: Stop отменяет возврат. `auto_control.stop` и `control_request.stop` сравнивали защёлку с `auto-control.json`, который парный режим не пишет (время 0), поэтому второй Stop после Start, Stop, Start отвечал `already_requested`: защёлка оставалась старше маркера Start, и после питания монитор запускал Auto.
