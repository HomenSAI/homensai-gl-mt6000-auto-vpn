# Поздняя перепроверка перед уходом с основного / Late-switch recheck

Дата: 03.11.2026. Ветка `feat/late-switch-recheck-20261103` от `83e4f7cb` (2.1.0-alpha6). Обе среды (Lua и Python) решают одинаково; общие случаи — `router/tests/late_switch_cases.json`.

## Что было (MT3000, 02.11.2026, 2.1.0-alpha5, фаза 2, один проход)

`private/soak-24h/report-phase2-alpha5-pass1.md`, `soak-log-phase2-alpha5-pass1.jsonl`. Отключение основного (nft drop) на 5 и 10 с — переключения нет (правильно); на 20–40 с — APPLYING в 19,7–21,0 с, трафик на резерве в 20–22 с (правильно). На **15 с** — APPLYING в 18,7 с, трафик на резерве в 20,0 с, т. е. **после** того, как основной уже восстановился (15 с): лишнее переключение и возврат через ~96 с.

Почему (времена от начала сбоя, цикл 2 и сравнение с циклами 1, 3, 6):

1. Быстрое обнаружение (`lua/fast_detect.lua:31`, `LOSSES=3`, такт 1 с) через ~3 с запускает плотное подтверждение (`lua/probe_policy.lua:24`, `DENSE_INTERVAL=4`): полные проходы монитора (DNS + 3 HTTPS) каждые 4 с. Время пробы — её **начало** (`lua/probe.lua:248`), опубликована она после конца прохода (`lua/monitor.lua:703–709`, ≈2,5 с). Первая ошибка видна в 6,6 с во всех циклах.
2. Уход решает `pair.streak` (`lua/pair.lua:111–138`; Python `failover_plan.py:12–36`): три **подряд** неудачи (`recovery_failures=3`), самая свежая не старше `valid_for` = 3 × интервал = 30 с (`lua/pair.lua:74–79`). Три неудачи — пробы, начатые в ≈3,5 / 7,5 / 11,5 с, все внутри 15-секундного отключения; третья опубликована ≈14 с.
3. Auto перечитывает `status.json` раз в ~2 с (`lua/pair.lua`, `M.tick`: чтение статуса, затем `reapply_missing_policy` → диагностика + `attest_policy`, ещё диагностика, `configure_lease`, ещё диагностика, затем `T.attempt` → `assert_selection` ×2, `attest_policy`, `rtp_boot.prepare`, ARMED → APPLYING; `lua/transaction.lua:456–584`). На MT3000 от прочтения до APPLYING проходит ≈3–5 с (в цикле 3: ARMED 18,35 с → APPLYING 19,73 с).
4. Первая здоровая проба (начата 15,5 с) опубликована ≈18 с — в тот момент, когда переход уже шёл (в журнале цикла код основного сменился на «нет ошибки» в том же опросе 18,7 с, что и APPLYING). Решение опиралось на доказательство, которое к моменту применения устарело на 7 с (возраст пробы) + время конвейера, а свежей проверки перед применением не было.

## Что стало

Прямо перед тем, как уход с основного фиксируется (`pair.lua M.tick` / `pair_auto.tick`, ветка `failed and healthy and dwell and not suppress_switch`, после последней диагностики и перед `T.attempt`), источник проверяется ещё раз (`M.late_recheck` / `pair_auto.late_recheck`):

1. Перечитывается `status.json`: если монитор уже опубликовал **здоровую** пробу основного (код нет, DNS ок, ≥2 из 3 HTTPS, в пределах поколения профиля) новее самой свежей пробы, на которой основано решение, — уход отменяется без пробы.
2. Иначе одна живая проба основного с коротким ожиданием `RECHECK_SECONDS = 1` с на каждый HTTPS и на DNS (`live_probe.lua` `L.probe(profile, keep, seconds)`, `backend.lua` `B.recheck`; Python `agent.probe(profile, seconds)`, `native_switch.Linux.recheck`). Только нативная Lua-проба: мост `lua_bridge.py` (~2 с на запуск Python) не используется.
3. Отменяет уход **только положительный ответ** (основной прошёл DNS + 2 из 3 HTTPS). Таймаут, ошибка, недоступная проба, нечитаемый статус — уход идёт как раньше. Мёртвый основной этой проверкой не удерживается никогда.
4. Отмена публикуется как `OBSERVING / PRIMARY-RECOVERED-BEFORE-SWITCH` (поле `late_recheck`: `monitor`, `probe` или `same-evidence`). Время пробы, которую перепроверка опровергла, запоминается (в памяти процесса); то же доказательство повторно не решает и не пробуется — следующую попытку запускает только новая проба монитора. Если основной снова упал, новые три неудачи приводят к уходу обычным путём.
5. Нестабильный источник (`source_unstable`, постоянные перестройки поставщиком) уходит по своей нестабильности, без перепроверки (как раньше).

Цена для настоящего ухода: одна проба мёртвого основного — не больше ~1 с ожидания (+ два чтения маршрута); при отказе отправки (EPERM, как при nft drop) — сразу. Настройки владельца и пороги не изменены.

## Потери (netem loss): почему результаты непоследовательны

Наблюдение (фаза 2, по одному циклу на точку, сбой 150 с): loss 10 % → уход в 37 с; 20 % и 30 % → нет; 50 % → 51 с; 80 % → 21 с.

- netem стоит только на исходящем трафике туннеля. HTTPS идёт по TCP с повторами (ожидание 6 с, в плотном режиме 3 с) и при ≤ 30 % почти не падает; DNS-проба — **одна UDP-датаграмма без повтора** (`lua/probe.lua:88–96`, `agent.py:438–444`), поэтому при потерях вероятность `DNS-001` в пробе ≈ p. При 50–80 % падает и HTTPS (`VPN-003`).
- Правило «3 неудачи подряд» превращает это в случайную величину. Для независимых потерь и ~15–25 проб за 150 с вероятность хотя бы одной серии из трёх: 10 % → 1–2 %; 20 % → 8–14 %; 30 % → 24–38 %; 50 % → 68–86 %; 80 % → ≈ 99–100 %. Один проход на точку поэтому даёт «монетку» в диапазоне 20–50 %: отсутствие ухода при 20/30 % и уход при 50/80 % — ожидаемые исходы.
- Уход при 10 % маловероятен для независимых потерь (≈ 1 %): в журнале цикла 8 код `DNS-001` держится непрерывно с 12,9 до 78 с (≥ 6 проб подряд, без единой успешной), а плотного эпизода не было (нет строки «fast detect»): решали обычные пробы раз в 10 с (≈13/23/33 с → уход 37 с). Это указывает на коррелированный отказ DNS-пути при netem, а не на 10 % случайных потерь; данных для вывода не хватает (в журнале нет вида отказа DNS). Отдельно: контрольный ping из 5 пакетов (0 % при «10 %», 20 % при «5 %») слишком мал, чтобы проверить заданный процент.

Рекомендация (не реализовано: меняет правила проверки во всех трёх местах — монитор, живая проба Lua и Python — и требует новой приёмки):

1. Повтор DNS-вопроса один раз внутри того же ожидания (как делает обычный резолвер): вероятность `DNS-001` ≈ p², при 10–20 % уход практически исключён (≤ 0,1 %), при 50 % ≈ 15 %, при 80 % ≈ 90 %.
2. Для устойчивого решения при частичных потерях — правило «k из m» по более частым данным (как SLA-мониторинг): например доля потерь ICMP-пульса (1/с) за 30 с ≥ 50 % вместе с подтверждающей неудачной полной пробой; биномиальный разброс при 30 сэмплах ≈ ±8 п. п. вместо «монетки». «k из m» по самим полным пробам (например 4 из 6) без увеличения их частоты лишь сдвигает порог и замедляет обнаружение.
3. Записывать в пробу вид отказа DNS (`timeout`/`transport`) и повторить loss-10 несколько раз, чтобы объяснить корреляцию.

## Проверки

- `router/tests/test_late_switch.py`, `router/tests/lua/test_late_switch.lua`: общие случаи `monitor_recovered`/`same_evidence`; `late_recheck` (проба монитора без живой пробы, только `true` отменяет, ошибки/таймауты/нет пробы — уход); короткое ожидание доходит до всех трёх HTTPS и DNS; симуляция `tick` по измеренным временам MT3000: 15 с — без фикса уход (воспроизведение), с фиксом нет ухода и `OBSERVING / PRIMARY-RECOVERED-BEFORE-SWITCH`, затем `PAIR-WATCHING`; 20/25/30/40 с — уход в том же такте, позже ровно на ожидание пробы (1 с); основной, «оживший» на 2 с и снова упавший, — уход по новым трём неудачам; всё время мёртвый основной — уход без отмен.
- Совместно с проверкой больших пакетов (VPN-MTU, ветка mss-sqm, интеграция alpha7): короткая живая проба шлёт только маленькие пакеты и не видит «чёрной дыры» MTU, а живые пробы Auto проверку больших пакетов не запускают. Поэтому если самая новая неудачная проба основного имеет код `VPN-MTU` (`PROBE_BLIND_CODES`), живая проба не спрашивается; отменить уход может только более новая здоровая проба монитора (он повторяет проверку больших пакетов на каждой пробе после «чёрной дыры»). Без этого каждая новая проба `VPN-MTU` отменялась бы живой пробой, и уход откладывался бы до признания основного нестабильным (окно 120–900 с). Тесты: `late_recheck` с `VPN-MTU` и симуляция «чёрной дыры» в обоих файлах выше.
- Приёмка на MT3000 — отдельно (повтор циклов фазы 2).
