# MSS, проверка больших пакетов (VPN-MTU) и SQM на выходе туннеля / MSS, large-packet check and tunnel SQM

Дата: 03.11.2026. Ветка `feat/mss-sqm-20261103` от `83e4f7cb` (запись 2.1.0-alpha6). Без работы с роутером. Обе среды (Lua и Python) решают одинаково; общие случаи — `router/tests/mtu_check_cases.json`, `router/tests/sqm_cases.json`.

## Находка на роутере

Матрица фаза 2 (MT3000, 02.11.2026), вид `primary-mtu`: nft `oifname @devs meta length > 1300 drop` на основном туннеле (WireGuard, MTU 1350) — «чёрная дыра» MTU. Проверки здоровья Auto (3 HTTPS + DNS) шлют только малые запросы, поэтому основной считался здоровым, переключения не было, а большие передачи пользователей зависали.

## A1. TCP MSS: прошивка GL уже ограничивает — своё правило не добавлено

- Прошивка GL 4.11 (`/usr/bin/rtp2.sh`, аудит `private/workspace-transfer-2026-10-16/router-firmware-audit-2026-10-12`): для каждого включённого `wgclient`/`ovpnclient` `load_vpn_instance_rule` → `instance_set_firewall_main_rule` создаёт зону брандмауэра с именем интерфейса и `option mtu_fix '1'`; плюс `rtp2.sh` ставит `-A POSTROUTING -p tcp -m mark ! --mark 0x0/0xf000 --tcp-flags SYN,RST SYN -j TCPMSS --clamp-mss-to-pmtu` (в ветке fw4 — `tcp option maxseg size set rt mtu`, но эти роутеры работают на fw3 + iptables).
- Живой снимок MT3000 (`private/revive-alpha37-20261027/live-incident-mangle.txt`, 29.10.2026, `iptables-save -t mangle`):
  ```
  -A FORWARD -o wgclient1 -p tcp -m tcp --tcp-flags SYN,RST SYN -m comment --comment "!fw3: Zone wgclient1 MTU fixing" -j TCPMSS --clamp-mss-to-pmtu
  -A FORWARD -i wgclient1 -p tcp -m tcp --tcp-flags SYN,RST SYN -m comment --comment "!fw3: Zone wgclient1 MTU fixing" -j TCPMSS --clamp-mss-to-pmtu
  -A FORWARD -o ovpnclient2 ... "!fw3: Zone ovpnclient2 MTU fixing" -j TCPMSS --clamp-mss-to-pmtu
  -A FORWARD -i ovpnclient2 ... "!fw3: Zone ovpnclient2 MTU fixing" -j TCPMSS --clamp-mss-to-pmtu
  -A POSTROUTING -p tcp -m mark ! --mark 0x0/0xf000 -m tcp --tcp-flags SYN,RST SYN -j TCPMSS --clamp-mss-to-pmtu
  ```
  WAN-зона (`eth0`, `apcli0`) тоже с `mtu_fix`. Ограничение в обе стороны по MTU маршрута туннеля уже есть, поэтому второе правило приложения было бы дублем; оно не добавлено (таблица `inet homensai_vpn_guard` — временная защита на время переключения и по-прежнему должна отсутствовать в покое).
- Ограничение MSS не лечит «дыру» ниже MTU туннеля (как в тесте: 1300 < 1350) и не помогает UDP/QUIC — для этого нужна проверка ниже.
- Проверка на роутере (только чтение): `uci show firewall | grep -E "mtu_fix|=zone"`; `iptables-save -t mangle | grep TCPMSS`; `nft list ruleset | grep -i maxseg` (ожидается пусто на fw3).

## A2. Проверка больших пакетов (код VPN-MTU)

`mtu_check.py` / `lua/mtu_check.lua`, вызывается только монитором (единый источник показаний; живые проверки Auto — `native_switch`, `lua_bridge`, `live_probe.lua` — её не запускают).

- Одна проверка: через устройство туннеля (Python: `SO_BINDTODEVICE` + fwmark туннеля, как `icmp_ping.py`; Lua: raw-сокет nixio, привязанный к устройству) к `1.1.1.1` и `9.9.9.9` по одному малому эхо (64 байта IP) и по два больших длиной MTU устройства туннеля (`/sys/class/net/<dev>/mtu`, не больше 1500, меньше 576 — не проверяется), параллельно с HTTPS/DNS, ожидание 1,5 с.
- Вердикт: `ok` — вернулся хотя бы один большой эхо-ответ (усечённый ответ, как у 8.8.8.8, тоже считается) или пришло «fragmentation needed» на наш запрос (PMTUD работает — не дыра); `black-hole` — ни одного большого ответа, но малый ответ пришёл; `inconclusive` — не пришло ничего (ICMP фильтруется или туннель лежит — решают HTTPS/DNS); `unavailable` — ошибка сокета.
- Только `black-hole` меняет здоровье: иначе здоровая проба получает код `VPN-MTU` (диагноз `LARGE-PACKETS-FAILED`, `suppress_switch=false`). Код HTTPS/DNS-сбоя, если он есть, остаётся. Поле строки `mtu_check = {state, size}`.
- Темп: первая проба канала, затем раз в 300 с; после `black-hole` — на каждой пробе, пока проверка не пройдёт (`inconclusive`/`unavailable` подозрение не снимают). Каждый образец с `VPN-MTU` — собственное свежее измерение, без кэша кода. Нагрузка: 6 ICMP-пакетов на канал раз в 5 минут.
- Auto: `VPN-MTU` добавлен в коды сбоя серий (`failover_plan.FAILURES`, `pair.lua FAILURES`), `PROBE_FAILURES`/`UNSTABLE_CODES` диагностики, `reliability BAD`, учёт простоя, отмену теста скорости и списки страницы. Основной с дырой уходит на резерв после обычной серии сбоев (`recovery_failures`), если у резерва нет дыры (резерв с `VPN-MTU` не «готов»: серия успехов требует `code=null`). Если дыра на обоих туннелях, переключения нет. Возврат — по обычной стабильности основного (с гашением флаппинга).
- Защита от ложных переключений: нужны малый ответ при потере всех четырёх больших к двум адресам, повтор на каждой пробе и обычная серия из `recovery_failures` таких проб подряд; фильтрация ICMP даёт `inconclusive` и ничего не меняет; ответы «fragmentation needed» и усечённые ответы считаются успехом.
- Не обнаруживается: дыра только во входящем направлении при ответах меньшего размера от адресов проверки; провайдер, полностью фильтрующий ICMP.

## B. SQM (cake) на выходе туннеля — механизм за настройкой, по умолчанию выключен

`sqm.py` / `lua/sqm.lua`, проход монитора в обеих средах.

- Настройка владельца (UCI, читается `inventory.lua`): `sqm_enabled='1'` **и** `sqm_upload_kbit` 1000..1000000. Иначе ничего не делается и не запускается ни одного процесса (`SQM-OFF`, `SQM-BANDWIDTH-UNSET`). Кнопки на странице пока нет.
  ```
  uci set homensai_vpn.main.sqm_enabled='1'
  uci set homensai_vpn.main.sqm_upload_kbit='18000'
  uci commit homensai_vpn
  ```
- Команда на каждом проверяемом туннеле (устройство и ifindex из привязки маршрута пробы): `tc qdisc replace dev <tunnel> root cake bandwidth <kbit>kbit besteffort triple-isolate nat`. `nat` — cake берёт адреса LAN до маскарада из conntrack, поэтому изоляция по хостам работает и после SNAT зоны туннеля.
- Заменяется только корень по умолчанию ядра (handle `0:`: noqueue/fq_codel) или cake, записанный приложением (`/var/run/homensai-vpn/sqm-state.json`, с ifindex). Любая другая корневая дисциплина (владельца или прошивки) не трогается: `SQM-ROOT-QDISC-BUSY`. WAN, LAN и другие устройства не затрагиваются. Применённое перепроверяется раз в 300 с.
- Возврат к умолчанию ядра (`tc qdisc del dev <tunnel> root`, только если корень всё ещё cake): выключение/смена скорости — следующий проход; остановка службы — `sqm_release` в `/etc/init.d/homensai-vpn` (по файлу состояния, после хука монитора), Python-монитор при выходе, Lua-монитор в `shutdown` и больше не применяет до SIGTERM; удаление/обновление пакета — через `prerm` → `stop`; перезапуск туннеля — новое устройство уже с умолчанием ядра, запись сбрасывается по новому ifindex, cake ставится снова только при включённой настройке. Остановка Auto (кнопка Stop) SQM не трогает: это настройка трафика, а не переключения.
- Статус: `status.sqm = {enabled, kbit, code, devices: {dev: applied|busy|failed|restore-failed}}` (только когда SQM включён или есть что вернуть). Коды: `SQM-APPLY-FAILED` (нет `tc`/`kmod-sched-cake` или отказ), `SQM-RESTORE-FAILED`.
- Почему по умолчанию выключено и без авто-скорости:
  - cake помогает только если туннель — узкое место: скорость ниже реальной отдачи переносит очередь на роутер (меньше задержка под нагрузкой — bufferbloat), но ограничивает пропускную способность; скорость выше реальной ничего не даёт (очередь остаётся в модеме/у провайдера). Реальная отдача через VPN зависит от WAN и сервера и меняется при переключении канала; надёжного источника для «авто» нет (тест скорости — выборка, по требованию).
  - CPU MT3000 (MT7981, 2×A53 1,3 ГГц): шейпинг cake — программный, на каждом пакете, обходит аппаратное ускорение (`mtkhnat`) для трафика туннеля (который и так идёт через ядро из-за шифрования); на сотнях Мбит/с это заметная доля ядра CPU вдобавок к WireGuard/OpenVPN. Для типичной отдачи 10–50 Мбит/с — приемлемо; измерений на роутере ещё нет.
  - Наш netem-тест (задержка при очереди) показал рост задержки под нагрузкой, но не доказал, что cake на туннеле его снимает при реальном WAN — нужен отдельный замер.
  - При двух одновременно используемых туннелях каждый получает `kbit` (сумма может превысить отдачу) — Auto обычно ведёт трафик через один.
- Рекомендация: включать только при реальном bufferbloat на отдаче, задав 85–90 % измеренной отдачи через VPN; проверить `tc -s qdisc show dev <tunnel>` и задержку под загрузкой.

## Проверка на роутере (отдельная приёмка, не выполнялась)

1. MSS (чтение): команды из A1.
2. VPN-MTU: набор `private/soak-24h`: `py -3.14 soak24.py --kinds primary-mtu,primary-netem-delay-500 --passes 3 --slot 300`. Ожидание для `primary-mtu`: в `status.json` у основного `mtu_check.state=black-hole`, код `VPN-MTU` на каждой пробе после первой проверки (≤ 300 с + серия), переход на резерв (`switch`), после снятия — `mtu_check.state=ok` и обычный возврат. Для `primary-netem-delay-500`: `mtu_check` остаётся `ok`/`inconclusive`, ложного `VPN-MTU` нет. Также фон без сбоев: ни одного `VPN-MTU` на здоровых туннелях.
3. SQM (только с разрешения владельца, на MT3000 есть `tc-tiny` и `kmod-sched-cake`): включить настройкой выше; `tc qdisc show dev wgclient1 root` → `qdisc cake ... bandwidth 18Mbit`; `ubus call homensai-vpn-lua status`/`status.json` → `sqm.devices.wgclient1=applied`; выключить (`sqm_enabled='0'`) → через проход `qdisc noqueue 0: root`; включить и `/etc/init.d/homensai-vpn stop` → корень снова по умолчанию, файла `/var/run/homensai-vpn/sqm-state.json` нет; `ifdown wgclient1; ifup wgclient1` → после прохода cake на новом устройстве. Нагрузка CPU: `top` при загрузке отдачи с cake и без.
