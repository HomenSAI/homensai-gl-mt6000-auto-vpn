# Сброс старых соединений LAN после переключения (03.11.2026)

Ветка `feat/conntrack-reset-20261103` (от 2.1.0-alpha6, `83e4f7cb`). Версия не поднималась; на роутере не проверено.

## Что наблюдали (MT3000, 03.11.2026, внешний LAN-клиент, 3 прогона, `private/lan-client-kit/phase5-run*.out`)

- Отказ основного, Auto переводит трафик на резерв: старое TCP-соединение ошибки не получает, висит ещё ~20 с после переноса и умирает только по тайм-ауту приложения (новое соединение через ~40 с после переключения).
- Возврат на основной: старое соединение получает RST сразу (новое через 1–2 с).
- UDP продолжает идти по новому туннелю. Пакетов старых потоков в WAN: 0.

## Причина (по снимкам conntrack из `lan-log.jsonl`)

| поток | ctmark | NAT-адрес (reply dst) |
|---|---|---|
| TCP 41001 → 1.1.1.1:443 | `0x0` | `10.5.0.2` (wgclient1) |
| UDP 53530 → 1.1.1.1:53 | `0x1000` | `10.5.0.2` (wgclient1) |

GL route_policy ставит метку каждому пакету (`MARK --set-xmark`), а в conntrack метку сохраняют только DNS-правила. Поэтому уже существующее `conntrack -D -m <старая метка>/0xf000` удаляет UDP-поток (DNS), но не TCP. После переноса пакеты старого TCP уходят в новый туннель с исходным адресом СТАРОГО туннеля (NAT уже записан в conntrack), новый сервер молча их отбрасывает — соединение висит до тайм-аута приложения.

## Решение

После подтверждённого переноса трафика с канала A на канал B:

    conntrack -D -f ipv4 --reply-dst <IPv4-адрес туннеля A> --src-nat

- Где вызывается: `COMMITTED` в `transaction.attempt` / `native_switch.attempt` (отказ основного и любой подтверждённый перенос) и конечный `ROLLED-BACK` в `rollback.rollback` / `native_switch.rollback` (плановый возврат, откат неудачного переключения, Stop), а также `COMMITTED` переключения, которое `forward_resume.lua` / `forward_resume.py` довёл до резерва после перезапуска супервизора. Оба раза — после установки VPN-only guard. Общий помощник `reset_old_flows` (Lua `transaction.lua`, Python `native_switch.py`), модуль `flow_reset.lua` / `flow_reset.py`, общие случаи `router/tests/flow_reset_cases.json`.
- Адреса A и B читаются из `network.interface.<интерфейс> status` (netifd) в момент сброса.
- Что удаляется: только потоки с source-NAT, у которых адрес NAT = адрес A. Это ровно LAN-потоки, вышедшие через A.
- Что не трогается по построению: управление роутером (SSH/LuCI из LAN — без NAT), собственные потоки роутера, привязанные к туннелю (без NAT), входящие соединения, потоки нового туннеля (другой адрес; если адреса A и B совпадают — ничего не делается, код `SAME-ADDRESS`).
- После удаления следующий пакет потока создаёт новую запись по ТЕКУЩЕЙ политике (туннель B, адрес B); сервер не знает этого адреса/порта и отвечает RST — приложение узнаёт об обрыве сразу. Маршрутизация, правила и guard не меняются; путь в WAN не открывается.
- Ограничение времени: `timeout 1`. Ошибка никогда не проваливает и не откатывает переключение — только строка в системном журнале: `FLOW-RESET-<DONE|NONE|NO-TOOL|NO-ADDRESS|SAME-ADDRESS|TIMEOUT|FAILED>: address <A> deleted <n>`.
- Проверено по исходникам conntrack-tools 1.4.6 (версия пакета `conntrack 1.4.6-3` в прошивке GL 4.11): `-D` допускает `-f`, `--reply-dst`, `--src-nat`; фильтр NAT применяется при удалении; при 0 удалённых код выхода 1; каждая удалённая запись — строка в stdout.
- Нет утилиты conntrack — ничего не делается (`NO-TOOL`). Вариант через nft (reject с tcp-reset на окно) не делали: утилита есть в прошивке и уже используется, а правило-окно при сбое процесса могло бы остаться и рвать новые потоки после возврата.

## Настройка

Включено по умолчанию; `option flow_reset '0'` в `/etc/config/homensai_vpn` выключает. Без файла конфигурации (ПК, тесты) ничего не запускается. Коды пишутся в системный журнал (`logread -e FLOW-RESET`); все коды (`FLOW-RESET-DONE`, `-NONE`, `-NO-TOOL`, `-NO-ADDRESS`, `-SAME-ADDRESS`, `-TIMEOUT`, `-FAILED`, `-OFF`) объяснены одной строкой семейства `FLOW-RESET-` в таблице ошибок страницы (`router/error_rows_extra.inc.js`, `ERROR_FAMILIES`; отдельные строки не помещаются в предел размера главного модуля страницы); в исходниках коды записаны целиком.

## Не покрыто

- Ручное мгновенное переключение (`instant_switch.lua`) и восстановление после смерти процесса внутри перестройки GL (`rollback_recovery.rebuild`) сброс не вызывают.
- Если правила политики направляют часть клиентов через второй канал постоянно, их потоки один раз сбросятся при переключении (в стандартной паре «все клиенты» таких нет).
- Приложение, которое ничего не отправляет и ждёт данных, узнает об обрыве при первой своей отправке (keepalive).
- На роутере не проверено. Проверка: `py -3.14 lan_pc.py --mode command --command "sh /tmp/devdrop.sh wgclient1 150" --streams --full-window --window 300 --ip 192.168.12.<свободный>`; ожидание: в `jump_away` `tcp_old` = `broke` c `error` = `reset` и `new_s` ≈ 1–5 с вместо `timeout`/40 с; в `logread` строки `FLOW-RESET-DONE` на COMMITTED и на ROLLED-BACK; утечка в WAN 0.
