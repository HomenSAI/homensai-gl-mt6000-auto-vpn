# Пункт 5 плана Lua: быстрое обнаружение сбоя (пульс раз в 1 с на uloop)

Дата: 31.10.2026 · Ветка: `lua/agent-fastdet-20261031` (поверх `feat/lua-core-20261030`, 2.0.0-alpha11) · План: `LUA-PLAN-2026-10-30.ru.md`, строка 5. Источник логики: `fast_detect.py` из ветки `feat/fast-detection-20261030` (`FAST-DETECTION-2026-10-30.ru.md`).

Пометки: **[Ф]** — факт (код, тест/замер на ПК), **[О]** — оценка, **[П]** — проверить на MT3000.

Статус: код и тесты готовы на ПК; **на роутере не запускался**. По умолчанию выключено: без `option lua_fast_detect '1'` монитор не открывает ни одного сокета и не меняет `status.json` [Ф].

## 1. Что сделано

| Файл | Изменение |
|---|---|
| `lua/fast_detect.lua` (новый) | пульс `Pulse`: каналы пары, удары, счёт потерь, «вооружение», доказательства, `status.fast_detect`; разбор флага владельца |
| `lua/monitor_io.lua` | `beat_socket(dev)` — постоянный неблокирующий raw ICMP сокет с `bindtodevice` (без uloop-объекта); в белый список sysfs добавлены `statistics/rx_packets`, `tx_packets` |
| `lua/monitor.lua` | `fast_option()` (флаг, перечитывается только при смене ключа файла конфигурации), `fast_tick()`; настройка пульса после каждого прохода; удар в существующем таймере 1 с; немедленный проход при начале эпизода; закрытие сокетов при `shutdown` |
| `lua/probe_policy.lua` | причина подозрения `heartbeat-lost` и поля доказательства `losses`, `cause` в `Booster:suspect` |
| `tests/lua/test_fast_detect.lua` | 15 тестов, в т.ч. симуляция приёмки на виртуальных часах |
| `tests/lua/bench_fast_detect.lua` | замер стоимости удара (ПК и роутер) |

Кто решает: **монитор** обнаруживает и даёт полные проверки, **Auto** (Lua или Python) решает по своим неизменным правилам. Пульс сам ничего не переключает и не пишет маршруты/межсетевой экран/VPN.

## 2. Сигналы

Раз в секунду (таймер наблюдения монитора, который уже был; новых объектов uloop нет), для каждого канала пары (источник/резерв последнего прохода с полной привязкой ядра device/ifindex/mark/table):

| Сигнал | Как читается | Итог удара |
|---|---|---|
| `ifindex` | sysfs, каждый удар | нет устройства → потеря `link-missing`; другой ifindex (устройство пересоздано) → не считается (`link-changed`), новый проход перепривяжет |
| ответ на эхо предыдущего удара | неблокирующее чтение постоянного сокета (до 32 датаграмм), `probe.valid_reply` | нет ответа за ~1 с → потеря `timeout`; ответ → `ok` (счёт сброшен, канал «вооружён») |
| отправка нового эхо | `connect`+`send` на raw-сокете, адреса чередуются 1.1.1.1 / 8.8.8.8 | ядро отказало (EPERM от nft drop, ENETUNREACH, ENETDOWN, EHOSTUNREACH, ENOBUFS, EACCES) → потеря `send-refused` сразу; ENODEV/ENXIO → `link-missing`; прочее → не считается |
| `operstate`, `rx_packets`, `tx_packets` | sysfs, **только пока канал не отвечает** | `down` → потеря `link-down`; счётчики — доказательство (`stalled_s`: сколько секунд туннель ничего не принял с первой потери) |

Один удар — один итог. Текущий отказ (нет устройства, отказ отправки) важнее ответа на предыдущее эхо. Первый удар только отправляет.

Почему не только счётчики/рукопожатие: тестовый сбой (`fault_control`, правило nft `oifname @fault_devs drop`) отбрасывает пакеты до устройства — `tx_packets` не растёт, а рукопожатия и keepalive WireGuard идут через WAN и продолжаются (keepalive увеличивает `rx_packets`). Счётчики такой сбой не видят (разбор в `FAST-DETECTION-2026-10-30.ru.md` §1). Эхо через raw-сокет — те же несколько системных вызовов, без процессов. Рукопожатие WireGuard в Lua читается только через `wg show` (процесс) — в пульс не включено.

## 3. Пороги и подавление дребезга

| Параметр | Значение | Смысл |
|---|---|---|
| `LOSSES` | 3 | столько потерь подряд у «вооружённого» канала делают его подозреваемым (≈3 с при чёрной дыре, ≈2–3 с при отказе отправки) |
| подтверждение | `Booster:suspect` → плотный эпизод `probe_policy` (уже перенесён в alpha4, до сих пор не вызывался) | полные проходы монитора (DNS + 3×HTTPS через канал, идентичность маршрута до/после, эпохи производителя) раз в `DENSE_INTERVAL`=4 с, до 60 с; публикуются как обычные образцы |
| решение | Auto: `pair.streak` — 3 неудачи источника (`recovery_failures`), 2 успеха резерва, `diagnose`, бюджет попыток, `min_dwell/cooldown` | правила не менялись; Lua Auto перечитывает `status.json` каждый такт (~2 с), отдельный файл пробуждения не нужен |
| после начала эпизода | канал «разоружён» до первого ответа на эхо | один эпизод на сбой; провайдер, режущий ICMP, даёт не больше одной ложной тревоги |
| ложная тревога | пауза `Booster` 30 с, удваивается до 10 мин | как в Python |
| отказ `Booster` (идёт эпизод, пауза, Auto не наблюдает) | повтор не раньше чем через `RETRY`=5 с | `native-status.json` читается только когда есть подозреваемый |
| тест скорости (`speed-pause.json`) | ударов нет, счёт сброшен | насыщенный туннель не даёт ложных потерь |

Работает только когда флаг включён и Auto наблюдает (`OBSERVING`, `COMMITTED`, `DEGRADED-ON-RESERVE`); иначе ни одного пакета.

Отличие от Python-проекта: раунды подтверждения не перекрываются (проход монитора один за раз), и это полные проходы, а не урезанные. Поэтому подтверждение ≈26 с вместо расчётных ≈17 с, зато нового планировщика и второго пути записи статуса нет.

## 4. Приёмка в симуляции [Ф]

`test_fast_detect.lua`: настоящий `monitor.lua` + `probe_policy` + `pair.streak` на виртуальных часах; уровень 1 (проход раз в 60 с, ускорение 10 с); проход через отказавший канал 7 с (curl `-m 6`), исправный 2 с; Auto видит образцы после публикации прохода и проверяет правило раз в 2 с. Режимы сбоя: `refused` (как nft drop) и `blackhole` (ответов нет).

| Сценарий | С пульсом | Без пульса (как сейчас) |
|---|---|---|
| 4 сбоя по 150 с, отказ отправки: правило переключения выполнено через | 26 / 26 / 26 / 26 с | 48 / 28 / 148 / 68 с |
| 4 сбоя по 150 с, чёрная дыра | 28 / 22 / 26 / 28 с | 48 / 28 / 148 / 68 с |
| короткие сбои 4, 8, 12 с и два по 4 с с перерывом 1 с | правило не выполнено ни разу (пульс заметил, эпизод закрылся ложной тревогой) | — |
| самый короткий сбой, который приводит к переключению (фазы 0–9 с) | 20 с (отказ) / 22 с (чёрная дыра) | — |

Без пульса третий сбой ждёт 148 с из-за паузы ускорения 10 мин после предыдущего эпизода — это поведение существующего кода, пульс его обходит. Время самого перехода (≈3–5 с на MT3000) в таблицу не входит.

## 5. Стоимость удара [Ф ПК, О роутер]

`bench_fast_detect.lua`, 50 000 ударов, 2 канала, настоящее чтение sysfs (`lo`, `eth0` в docker), поддельный сокет, который отвечает на каждое эхо (ответ строится и проверяется в Lua), плюс `config_mtime` и проверка `speed-pause.json` — всё, что выполняет таймер 1 с, пока подозреваемых нет:

| Вариант | ЦП на удар (i5-1135G7) | Доля ядра при 1 ударе/с |
|---|---|---|
| первая версия: 4 чтения sysfs на канал каждый удар | 127–135 мкс | 0,013 % |
| итог: 1 чтение sysfs на канал, пока канал отвечает | 75–105 мкс (из них ~15 мкс — построение ответа в подделке) | 0,008–0,010 % |

Чтение одного файла sysfs стоит ~16 мкс — основная часть удара; поэтому `operstate` и счётчики читаются только у неотвечающего канала. Оценка для Cortex-A53 MT3000 (Lua в 5–10 раз медленнее, плюс 4 системных вызова сокета на канал): 0,5–1,5 мс на удар → **0,05–0,15 % ядра** [О]. Память: две таблицы состояния и два сокета; рост кучи за 50 000 ударов — десятки–сотни КБ до сборки мусора [Ф]. Трафик: эхо 52 байта + ответ через каждый туннель раз в секунду, ≈0,25 КБ/с на канал в WireGuard [О по Python-проекту].

На роутере тот же замер с настоящими сокетами (только чтение, два эхо на удар):
```sh
cd /usr/lib/homensai-vpn/lua && lua /tmp/bench_fast_detect.lua 2000 wgclient1 ovpnclient2
```
(файл `router/tests/lua/bench_fast_detect.lua` скопировать в `/tmp`; он ищет модули в `/usr/lib/homensai-vpn/lua`).

## 6. A/B на роутере (MT3000, по указанию владельца и при свободном `ACTIVE-EXECUTOR`)

Требуется Lua-монитор (`lua_monitor='1'`); Auto может быть Lua или Python.

1. Включить:
   ```sh
   uci set homensai_vpn.main.lua_fast_detect='1'; uci commit homensai_vpn
   ```
   Перезапуск не нужен: монитор перечитывает флаг по ключу файла конфигурации на следующем ударе и настраивает пульс после ближайшего прохода (до 60 с на уровне 1).
2. Проверить: `ubus call homensai-vpn status | jsonfilter -e '@.fast_detect'` — `enabled=true`, `active=true`, два канала `state=ok`, `replies` растут; `tcpdump -ni wgclient1 icmp` — 1 запрос/с, адреса чередуются.
3. ЦП в покое 10 мин с флагом и без (по `/proc/<pid>/stat` процесса `monitor.lua daemon`, как в LUA-MONITOR-ITEM2 §11); ожидание — разница в пределах шума (<0,2 %).
4. 4 контролируемых сбоя основного по 150 с (тест сбоя со страницы), пауза ≥ 2 мин; для каждого: время начала сбоя (`fault-history.json`), строка `suspicion-start` с `reason=heartbeat-lost` в `probe-history.json`, `suspicion-end`, начало перехода и COMMITTED в истории Auto. Ожидание: подозрение ≤ 4 с, начало перехода ≤ 30–35 с.
5. Короткие сбои 4–10 с (если тест сбоя позволяет такую длительность): `suspicion-end` с `false-alarm`, переключения нет.
6. Те же сбои с `lua_fast_detect='0'` для сравнения.
7. Выключить: `uci set homensai_vpn.main.lua_fast_detect='0'; uci commit homensai_vpn` (или `uci delete`) — сокеты закрываются на следующем ударе, поле `fast_detect` исчезает из статуса после следующего прохода.

## 7. Риски

| Риск | Что делаем |
|---|---|
| raw-сокет nixio: `connect`/`send` на роутере возвращают коды ошибок, как ожидается (EPERM при nft drop) | [П] шаг 4; при другом коде отказ считается «не измерено», пульс просто молчит, обычная частота проверок остаётся |
| провайдер режет ICMP через туннель | одна ложная тревога, дальше канал разоружён до ответа; видно в `status.fast_detect.channels[].state=lost` при живом канале |
| сбой только TCP/HTTPS при живом ICMP | пульс не видит, работает обычная частота и ускорение |
| сокет получает все ICMP своего устройства | `connect` на адрес цели фильтрует по источнику; чтение ограничено 32 датаграммами за удар |
| удар задерживается, пока проход выполняет синхронные команды (`inventory.lua`, `ip`) | окно ответа становится длиннее (меньше ложных потерь), не короче |
| плотные проходы чаще пишут `status.json` (141 КБ) и чаще будят разбор у Auto | только во время эпизода (≤ 60 с), частота эпизодов ограничена паузами |
| страница показывает причину `heartbeat-lost` без перевода | текст в `probe_panel.inc.js` не добавлен (требует пересборки страницы) |

## 8. Тесты на ПК [Ф]

`lua5.1 router/tests/lua/test_fast_detect.lua` — 15 тестов: флаг (по умолчанию выкл., только `'1'`, только секция `main`, последнее значение); каналы пары; исправные каналы (постоянные сокеты, чередование адресов); чёрная дыра и отказ отправки (3 потери, короткий дребезг не считается, разоружение, удержание); сигналы устройства; настройка (выключено/не наблюдает/нет пары — ни одного пакета; новая привязка — новый счёт); пауза теста скорости; `monitor_io.beat_socket` на поддельном nixio (привязка, неблокирующий режим, коды ошибок, отказ небезопасных имён); монитор с выключенным флагом (ни сокета, ни поля в статусе); монитор с включённым флагом (эпизод `heartbeat-lost` один раз, плотный интервал, запись `suspicion-start`, выключение закрывает сокеты); отказ при неподходящем состоянии Auto и повтор; приёмка из §4.
