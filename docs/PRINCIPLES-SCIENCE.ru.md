### 1.3 Правила честной статистики

Эти правила применяются ко всем числам ниже (подробно — раздел 2.3).

- **Правило 59.** Максимум из n независимых замеров является верхней 95 %-й границей P95 только при n ≥ 59. Ниже этого «P95» — оценка, а при n ≤ 19 он просто равен максимуму. При любом n сам эмпирический P95 — только оценка: он накрывает настоящий P95 лишь примерно в 57 % случаев при n = 59, 35 % при n = 60, 38 % при n = 100 и 43 % при n = 300. Верхняя 95 %-я граница — другая, отдельно считаемая порядковая статистика X_(s), наименьший ранг с P(Binomial(n; 0,95) ≤ s−1) ≥ 0,95: максимум при 59 ≤ n ≤ 92, X_(n−1) при 93 ≤ n ≤ 123, X_(99) при n = 100, X_(292) при n = 300. 95 % верно только для независимых замеров; подряд идущие циклы одного стенда автокоррелированы, это уменьшает эффективное n и реальное покрытие. `[расчёт]`
- **Логарифмическая формула правила.** Нужно n ≥ ln(1−C)/ln(q). Для P95 при уверенности 95 %: ln 0,05 / ln 0,95 = 58,4, значит 59; для P99 это 298,1, значит 299. `[расчёт]`
- **Интервал Уилсона** для долей вида «k из n» (95 %). «3 из 3» доказывает только нижнюю границу 43,8 %.
- Метка «n=… <59» ставится у каждого числа с выборкой меньше 59.
- Разные версии программы в одну выборку не сливаются: смесь дала P95 88 с вместо 38,5 с у текущих сборок. `[расчёт]`

## 2. Математика

### 2.1 Скрытая марковская модель (HMM) вместо «3 неудачи подряд»

**Проблема (почему взяли).** Правило «3 неудачные проверки подряд» уходит с канала при блэкауте 12–20 с, хотя к моменту переключения (≈20 с «цены») канал уже жив. На постоянной потере 10 % оно переключается ≈10 раз в сутки, на 20 % — ≈59 раз (флаппинг). `[симулятор]`

**Цель.** Уходить на резерв только тогда, когда сбой, скорее всего, продлится дольше цены переключения C = 20 с. На коротком сбое и на небольшой потере — оставаться.

**Простыми словами.** Программа держит шесть «версий» о состоянии канала: здоров, лёгкая потеря, тяжёлая потеря, короткий блэкаут, долгий обрыв, мёртвый DNS. У каждой версии есть вероятность. Каждая проверка пересчитывает вероятности (как врач, который после каждого анализа уточняет диагноз). Уход происходит, если вероятность «сбой продлится ещё минимум 20 секунд» выросла до 0,8. Короткий блэкаут (около 4 с) почти не набирает эту вероятность, долгий — набирает. Модель сама выясняет, что сбой долгий, по тому, сколько он уже длится.

**Формулы и детали.**

- Шесть состояний {G, L, M, B, X, N}. Прогноз за Δt: `g = e^(−ΛΔt)`, `π'_G = π_G·g + Σ_s π_s(1−e^(−Δt/dur_s))`, `π'_s = π_s·e^(−Δt/dur_s) + π_G·(λ_s/Λ)(1−g)`.
- Обновление по наблюдению (O — здоров, D — DNS-001, H — HTTPS-сбой): `π'_s ← π'_s · P(obs | s, ритм)`, нормировка, пол вероятности 1e-9.
- Решение: `persist = Σ_{s∈{M,B,X,N}} π_s · e^(−C/dur_s) ≥ θ`, где θ = 0,8, C = 20 с, dur_B = 4 с. Короткий блэкаут вносит лишь e^(−5) = 0,7 % своей массы, долгий обрыв — 97,8 %.
- Плотная проба (ожидание 3 с) в 2–4 раза чувствительнее к потере, чем обычная; ритм проб входит в модель.
- Условие возврата в той же модели: P(здоров) = π_G ≥ 0,90 (решение владельца 03.11.2026; было 0,95).

**Где в программе.** `channel_model.py` / `lua/channel_model.lua`; настройка `failure_model = hmm` (по умолчанию) | `hmm-fast` | `consecutive`. Статус: **реализовано** (интеграция alpha8); в пакете alpha7, проверенном на роутере, этой модели нет. Файлы: [channel_model.py](../router/files/usr/lib/homensai-vpn/channel_model.py), [channel_model.lua](../router/files/usr/lib/homensai-vpn/lua/channel_model.lua), описание: [HMM-DETECTOR](architecture/HMM-DETECTOR-2026-11-03.ru.md).

**Эксперименты.**

- Детекторное исследование: пакетная модель канала, откалиброванная по MT3000 (лучшие k=6, rto=0,6 с), n = 300 прогонов на точку, 295 пригодных циклов логов. Реконструированное правило совпало с решением роутера в 38 из 38 циклов phase-2/3. `[симулятор]`

### 2.2 Биномиальные гарантии и кворум k из n

**Проблема.** Правило «N потерь подряд» выбирали «на глаз». Неясно, сколько ложных тревог оно даёт в неделю, и что даст несколько независимых датчиков.

**Цель.** Выбирать N и правило «k из n» по заданному бюджету ложных тревог, а не на глаз.

**Простыми словами.** Если проверка теряется случайно и независимо, то подряд N потерь — редкое событие, и его частоту можно посчитать формулой. Если ответ даёт не один датчик, а три, и тревога объявляется, когда молчат хотя бы два, ложных тревог от **одиночного шума пробы** становится в сотни раз меньше. Это гарантия только против шума одной пробы: против настоящих коротких обрывов канала она ничего не обещает (см. «Две цифры гарантии» ниже).

**Формулы и детали.**

- Независимая потеря p. «N подряд»: тревог на пробу `(1−p)·p^N`. Вероятность хотя бы одной за T проб ≈ `1 − exp(−T·(1−p)·p^N)`.
- Кворум m датчиков: «плохой момент» при потере ≥k из m: `q = Σ_{j≥k} C(m,j)·p^j·(1−p)^(m−j)`; затем N плохих моментов подряд: `(1−q)·q^N`.
- Скользящее «k потерь в окне n» считается точной цепью Маркова по 2^n состояниям окна; всплески Гилберта–Эллиотта — стационарным распределением.

**Две цифры гарантии, а не одна.** Формула `p^k` (для окна — `(1−p)·p^N`) описывает **только одиночный шум одной пробы**. Второе число — настоящие короткие естественные обрывы канала; оно на 5–6 порядков больше первого и считается отдельно:

- Первое число, `p^k`: частота отказной пробы p = 0,060 % (95 % ДИ 0,019…0,140 %; 8 361 проба, 23,2 канало-часа, 5 отказных проб), три подряд дают 2,1·10⁻¹⁰ на окно, 1,9·10⁻⁶ в сутки на канал. `[роутер, n малое]`
- Второе число: отказные пробы идут сериями, а не независимо. За те же 23,2 канало-часа — 1 серия из ≥3 отказных проб подряд, то есть **≈0,04 в час на канал (95 % ДИ 0,001…0,24)**; по формуле `p³` в 6 601 окне ожидалось 1,4·10⁻⁶ окна, наблюдено 2. Порядок величины меняется на 5–6 порядков, потому что это не шум датчика, а короткие (10–40 с) обрывы самого канала. `[роутер, n малое]`
- Третье: **эффективное число независимых датчиков в кворуме ≈1,2–1,9** для сбоев пути. Все три HTTPS-цели (1.1.1.1, 8.8.8.8, 9.9.9.9) идут через один туннель и один WAN, при сбое пути они падают вместе. Поправка Киша `n_eff = n/(1+(n−1)ρ)` для трёх целей даёт 1,88 при ρ = 0,3, 1,50 при ρ = 0,5 и 1,15 при ρ = 0,8 (при ρ → 1 — один датчик). Поэтому кворум «2 из 3» защищает в основном от сбоя одной цели или одного сервера, а не от сбоя пути. `[расчёт]` Диапазон ρ — сценарий, а не измерение (прежняя метка `[роутер, n малое]` к нему не относилась): в журналах soak по целям ничего не записывалось, попарную корреляцию целей измерить было нельзя. Для прямого измерения добавлен журнал по целям (`probe_target_log`, [PER-TARGET-PROBE-LOG](architecture/PER-TARGET-PROBE-LOG-2026-11-04.ru.md)).

**Где в программе.** Подсчёт N и кворума как формула в продукте не стоит: для решения о переключении используется HMM (2.1). ### 2.3 Честная статистика: Уилсон, эмпирический P95 и его верхняя граница, правило 59, логарифмическая формула

**Проблема.** Из 509 опубликованных в истории тестов P95 ни один не опирался на n ≥ 59, 507 были просто максимумом выборки, самая большая выборка — 21. `[расчёт]`

**Цель.** Никогда не называть оценку границей. Показывать, сколько замеров стоит за числом и что по ним можно утверждать.

**Простыми словами.** Если вы измерили 4 раза и самый плохой результат был 47 секунд, нельзя сказать «в 95 % случаев быстрее 47 с». Можно лишь сказать «с 95 % уверенностью не менее 47 % случаев не медленнее этого максимума». Чтобы можно было назвать границу настоящего P95, нужно 59 замеров, а показанный по ним P95 остаётся оценкой.

**Формулы и детали.**

- Шанс, что все n замеров ниже истинного P95: `0,95^n`. При n=59 это 0,0485 < 0,05, при n=58 — 0,0510. Отсюда `n ≥ ln(1−C)/ln(q)`: P95 — 59, P99 — 299. `[расчёт]`
- Максимум из n замеров покрывает не менее `100·0,05^(1/n)` % случаев с уверенностью 95 %: n=4 — 47,3 %; n=14 — 80,7 %; n=20 — 86,1 %; n=59 — 95,0 %; n=93 — 96,8 %. `[расчёт]`
- Минимальные n: максимум ≥ P95 — 59; двусторонний интервал P95 с хвостами по 2,5 % — 72; второй по величине ≥ P95 — 93; максимум ≥ P99 — 299; «отказов < 5 %» при 0 отказов — 59. `[расчёт]`
- Интервал Уилсона: `p = k/n, d = 1+z²/n, c = (p+z²/2n)/d, h = z·√(p(1−p)/n + z²/4n²)/d`, интервал `c ± h`, z = 1,96. «3 из 3» → 43,8…100 %; «59 из 59» → 93,8…100 % (печатается осторожно: нижняя граница округляется вниз, верхняя вверх до одного знака, поэтому 43,85 % показано как 43,8 %); «0 из 10» → 0…27,8 % (точная верхняя ≈ 3/n = 25,9 %). Чтобы «n из n» гарантировал успех ≥ 80/90/95/99 %, нужно подряд n = 16/35/73/381. `[расчёт]`

**Где в программе.** Стенд на ПК: `soak-24h/honest_stats.py` и `soak_report.py` (печатают «P95≈X (n=…, мало данных: нужно ≥ 59)»). В продукте и CI — ветка `feat/honest-p95-formal-ci-20261103`, **не влита** в alpha8. Статус: **в ветке** (стенд — применяется).

**Что означают два числа.** Печатаемый P95 — 95-й процентиль самой выборки, оценка при любом n. Для n = 60, 100 и 300 он накрывает настоящий P95 лишь примерно в 35 %, 38 % и 43 % случаев (57 % при n = 59). На всём диапазоне 59 ≤ n ≤ 300 это покрытие остаётся между 35 % и 57 %, поэтому эмпирический P95 никогда не является верхней 95 %-й границей. Верхняя 95 %-я граница — отдельно считаемая порядковая статистика (максимум при n = 59…92, 99-я из 100 при n = 100, 292-я из 300 при n = 300), верная для независимых замеров; повторные циклы одного стенда автокоррелированы, поэтому эффективное n меньше, а реальное покрытие ниже 95 % (грубая эвристика n_eff = n(1−ρ)/(1+ρ): при n = 59–61 максимум покрывает около 80 % при ρ = 0,3 и 64 % при ρ = 0,5). `[расчёт]`

**Эксперименты и результаты.** Пример из отчёта доступности (`primary-drop`, трафик перешёл): n=20, медиана 35,9 с, P95 38,5 с, нижняя 95 %-граница 37,2 с; верхнюю дать нельзя (максимум покрывает только P86). `[роутер]`, n=20 <59. Смесь версий: P95 88 с против 38,5 с. `[расчёт]` Старая печать «P95 = 39,3 (n=15)» теперь «P95≈39,3 (n=15, мало данных: нужно ≥ 59), с 95 % уверенностью ≥ 81 % случаев не медленнее max». `[роутер]` Первый P95 из n ≥ 59 на роутере (с отдельно посчитанной верхней границей) — раздел 7.

**Сравнение.** Новое честнее, цифры те же; проигрыш — время стенда: ≈3,5–5,6 ч на 59–93 цикла на каждый вид сбоя и версию.

**Источники:** `private/math/availability/p95_honesty.json`, `private/soak-24h/honest_stats.py`, [MEASUREMENTS](MEASUREMENTS.ru.md).

### 2.4 Байесовский выбор сервера и бандит UCB

> **Статус проверки (2026-11-07).** Пока не проверено: числа получены в старой симуляции (n = 40), зарегистрированная перепроверка не завершена. Байесовский выбор выключен; по умолчанию — простое правило с гистерезисом 20 %.

**Проблема.** Внутри канала (например, пул NordVPN) надо выбирать сервер по замерам задержки с шумом. Простое правило «сменить, если лучше на 20 %» при шуме замеров σ≈0,39 даёт ≈42 бесполезные смены простаивающего канала в сутки на двух равных серверах и лишние перезаписи настроек во flash. `[симулятор]`

**Цель.** Менять сервер только при уверенности, что кандидат быстрее; мерить меньше; не изнашивать flash.

**Простыми словами.** Для каждого сервера хранится не одна цифра, а «облако возможных значений»: насколько он быстр и насколько надёжен, с поправкой на то, сколько замеров есть. Старые замеры постепенно «забываются» (период полураспада 1 час). Сменить сервер можно, только если вероятность «кандидат быстрее» не ниже 0,95. Чтобы не застрять на среднем, программа иногда проверяет серверы, о которых мало данных: это идея «многорукого бандита».

**Формулы и детали.**

- Задержка: апостериорное нормально-обратногамма распределение логарифма RTT. Доступность: `Beta(ответил+1, не ответил+1)`.
- Забывание: все данные затухают с полупериодом `HALF_LIFE` = 1 ч (вес замера `2^(−Δt/3600)`).
- Смена: `P(кандидат быстрее) ≥ 0,95` (z ≥ 1,645), кандидат ответил в этом раунде и имеет доступность ≥ 80 %. Если текущий не ответил, берётся лучший живой.
- Бандит UCB: каждый раунд мерятся текущий сервер, серверы без данных, не измерявшиеся час, и те, что ещё могут оказаться лучшими. Замеров не больше, чем в простой модели.

**Где в программе.** `server_pick.py` / `lua/server_pick.lua`, функция `bayes_round`; настройка `server_pick_model = simple` (по умолчанию) | `bayes`. Статус: **реализовано, но выключено по умолчанию**, потому что не строго лучше по всем метрикам. Файлы: [server_pick.py](../router/files/usr/lib/homensai-vpn/server_pick.py), [server_pick.lua](../router/files/usr/lib/homensai-vpn/lua/server_pick.lua), [SERVER-PICK-DESIGN](architecture/SERVER-PICK-DESIGN-2026-11-02.ru.md).

**Эксперименты.** Реальный код `server_pick.py`, 40 прогонов на точку, σ шума 0,2–0,6, сценарии: два и четыре равных сервера, лучше на 10 % и на 30 %, медленная деградация, мёртвый, шесть разных. `[симулятор]` Тесты Lua = Python на общих случаях. `[тесты]`

**Результаты (σ=0,39, n=40 <59, `[симулятор]`).**

### 2.6 Марковская модель доступности

> **Статус проверки (2026-11-07).** Пока не проверено: только симулятор (зарегистрированная проверка не завершена); цифра 287 → 29 мин/мес — модель, а не измерение.

**Проблема.** Сколько минут простоя в месяц даёт каждая версия и что вообще можно улучшить: секунды переключения или независимость резерва?

**Цель.** Перевести секунды переключения в минуты простоя в месяц и показать, где выигрыш кончается.

**Простыми словами.** Система — несколько состояний (оба канала живы, идёт переключение, работаем на резерве, оба лежат). Переходы между ними идут со своими скоростями. По ним считается доля времени без связи.

### 2.7 Фронт Парето, «главный ползунок» и ночной советник (поиск золотым сечением)

**Проблема.** Настроек детектора много (порог θ, «пережидание» dur_B, число потерь пульса, условие возврата, `primary_stable`, `rescue_stable`), а пользователю нужна одна понятная ручка «быстрая реакция ↔ без лишних переключений».

**Цель.** Найти набор лучших компромиссов, свести их в одну кривую и дать совет по ней на основе истории сети самого пользователя.

**Простыми словами.** Любая настройка что-то улучшает и что-то портит. Мы перебрали все сочетания, оставили только те, которые нельзя улучшить сразу по двум показателям (это и есть «фронт Парето»), и растянули их на один ползунок от 0 до 1. Ночью советник «переигрывает» прошедшие дни при разных положениях ползунка и рекомендует тот, у которого суммарная цена меньше. Лучшее положение он ищет методом золотого сечения: интервал сужается в 1/φ ≈ 0,618 раза за шаг, поэтому нужно всего около 9 вычислений.

**Формулы и детали.**

- Цена = простой пользователя + 20 с за каждое лишнее переключение (+ 1 % от секунд на резерве в симуляции ползунка).
- Золотое сечение на [0, 1] до точности 0,02: пробные точки `b − (b−a)/φ` и `a + (b−a)/φ`, φ = (1+√5)/2 ≈ 1,618. Если цена в 11 опорных точках не «одногорбая», берётся лучшая опорная.
- Сдвиг рекомендуется, только если экономия ≥ 5 % и событий ≥ 5; режим «Авто» двигает не больше одного шага (0,1) в сутки и не во время сбоя.

**Где в программе.** Кривая и фронт: `private/math/master-slider` (симуляция). Советник (журнал сети + `advisor.py`, `lua/advisor.lua`, ночной запуск в 03:30 с nice 19) и главный ползунок (`router/ui/advisor.js`) **есть в продукте с alpha9**. ### 2.10 Диагноз «WAN или туннель» по Байесу, события WireGuard и пассивный датчик «тихого» туннеля

**Проблема.** При падении интернета у роутера оба канала «плохие»: Auto может переключаться впустую. После возврата WAN резерв поднимается на секунды раньше основного и перехватывает трафик (лишнее переключение туда и обратно). Пинги через туннель не отличают «молчит сервер фильтруемой цели» от «мёртв туннель».

**Цель.** Не переключаться, пока интернет у самого роутера доказанно лежит; быстрее проверять основной, когда WAN жив, а туннель упал; не считать тревогой отсутствие эха, если по туннелю идут данные.

**Простыми словами.** Несколько независимых «свидетелей» (эхо через порт WAN в обход VPN, вердикт прошивки GL, состояние линка, проверки обоих каналов, события WireGuard) голосуют, но не поровну: у каждого своя надёжность. Результат — вероятности шести версий («всё хорошо», «упал туннель», «сервер молчит», «оба VPN», «нет интернета у роутера», «DNS»). Пассивный датчик смотрит на счётчики сетевой карты: если исходящих байтов растёт, а входящих нет ≥ 3 с — подозрение; если входящий поток течёт ≥ 10 кбит/с, пропажа эха пульса тревогой не считается.

**Формулы и детали.** Наивный Байес: апостериорное `∝ prior · Π_i P(свидетельство_i | гипотеза)`, нормировка после каждого множителя (одинаково в Lua и Python). Априори 0,968 / 0,012 / 0,004 / 0,004 / 0,010 / 0,002. Правила безопасности поверх вероятности: удержание (WAN-DOWN) только при P(WAN) ≥ 0,95, **и** жёстком доказательстве, **и** основном `bad`, **и** резерве не `ok`; ускорение проверок основного — при WAN `ok`, основной `bad`, резерв `ok`, P(WAN) ≤ 0,01. Датчик: stall — rx не менялся ≥ 3 с, tx вырос ≥ 300 байт; вето — rx вырос ≥ 3750 байт за 3 с (10 кбит/с).

**Где в программе.** Ветка `feat/gl-sensors-20261104` (`fc395675`): `wan_diag.py`, `lua/wan_diag.lua`, `stall.py`, `lua/stall.lua`; настройки `wan_sensor`, `wg_events`, `stall_sensor`, `stall_veto` включены, `heartbeat_quorum` выключена. Статус: **в ветке**, в alpha8 не влито.

**Эксперименты.** Общие случаи Lua = Python (`gl_sensors_cases.json`), проверка Lua и Python тестами; симулятор кворума (раздел 2.2). `[тесты]` `[симулятор]` Цена CPU: пульс как раньше 0,027 % ядра на ПК, со stall и вето +0,02 %; оценка MT3000 ×5–10 (≈0,14–0,27 % и +0,1–0,2 %), на роутере не замерено. `[симулятор]`

## 3. Физика

### 3.1 Гашение дребезга: полупериод RFC 2439, удвоение паузы и Фибоначчи

**Проблема.** Нестабильный основной канал (дребезг: падает, поднимается, снова падает) заставляет Auto качаться туда-сюда, и каждое переключение стоит секунд простоя.

**Цель.** Удерживать трафик на резерве тем дольше, чем чаще основной подводил недавно, не лишая возможности вернуться.

**Простыми словами.** Каждый сбой добавляет «штраф», и штраф сам тает со временем, как радиоактивное вещество с периодом полураспада (физика распада). Пока штраф выше порога, возвращаться на основной нельзя. Так делают в интернет-маршрутизации с 1998 года (RFC 2439). В нашем продукте пауза не тает по закону, а удваивается с каждым лишним уходом.

**Формулы и детали.**

- Продукт сегодня: пауза возврата `s · 2^min(excess, 6)`, excess = (число уходов за окно) − лимит + 1, потолок 600 с; по умолчанию лимит 2 за окно 60 мин (опции конфигурации `recovery_flap_limit`, `recovery_flap_window`; политика читает их как свои внутренние поля `flap_limit`, `flap_window`), ниже лимита пауза равна просто `s`.
- Фибоначчи: `s · F_excess`, F = 1, 1, 2, 3, 5, 8, 13, 21.
- Полупериодный штраф: +1000 за каждый уход, затухание `P(t) = P₀ · 2^(−t/H)`; при штрафе выше suppress пауза `s + H·log₂(P/reuse)`, пока штраф не упадёт ниже reuse; потолок 600 с.
- Цена = простой + 20·ненужные уходы + 15·возвраты на мёртвый основной + w·секунды на резерве.

**Где в программе.** `pair_auto.return_hold` / `pair.lua M.return_hold`, опции конфигурации `recovery_flap_model`, `recovery_flap_limit`, `recovery_flap_window` (а для полупериодного штрафа `recovery_flap_halflife`, `recovery_flap_suppress`, `recovery_flap_reuse`); внутри политики это поля `flap_model`, `flap_limit`, … без приставки. Отдельные опции `recovery_attempt_limit` и `recovery_attempt_window` — это бюджет переключений, а не пауза возврата. ### 3.2 Закон квадратного корня для бюджета проб

> **Статус проверки (2026-11-07).** Пока не проверено: только симулятор; закон не включён (`reserve_probe_interval` = 0).

**Проблема.** Каждая проба стоит процессора, трафика и износа; резерв и основной проверяются одинаково часто (по 10 с), хотя отказ резерва «стоит» пользователю меньше.

**Цель.** Распределить фиксированное число проб между объектами так, чтобы суммарные потери от необнаруженных отказов были минимальны.

**Простыми словами.** Чем чаще объект ломается и чем дороже секунда его простоя, тем чаще его надо проверять, но не пропорционально, а по корню. Резерву хватит проверок реже.

**Где.** Рекомендация для `probe_policy.lua` и монитора, не внедрено. Статус: **только исследование**.

**Эксперименты.** Монте-Карло 18 000 ч, пуассоновские отказы: равные интервалы 5,19 против формулы 5,12 с/ч; закон √ 3,08 против 3,03. `[симулятор]`

### 3.3 Сброс «памяти» соединений (conntrack) после переключения

> **Статус проверки (2026-11-07).** Пока не проверено: цифра 54,8 → 23,6 с — оценка (задержка на стороне роутера A ≈ 3 с не измерена), а не замер на роутере.

**Проблема.** На роутере после переноса трафика старое TCP-соединение LAN-клиента висит ≈20 с и умирает только по тайм-ауту приложения (новое соединение — через ≈40 с после переключения). Причина: в таблице соединений осталась запись NAT со старым адресом туннеля, новый сервер молча отбрасывает такие пакеты. `[роутер]`, 3 прогона LAN-клиента.

**Цель.** Чтобы приложения узнавали об обрыве сразу и переподключались.

**Простыми словами.** У соединения есть «память» о пути, и она устарела. Мы стираем только записи, прошедшие через старый туннель; следующий пакет создаёт запись по новой дороге, сервер отвечает RST, приложение переподключается за секунды.

**Формулы и детали.** После подтверждённого переноса A → B: `conntrack -D -f ipv4 --reply-dst <адрес туннеля A> --src-nat` (таймаут 1 с). Не трогаются управление роутером, собственные потоки, входящие соединения и потоки нового туннеля. Ошибка не откатывает переключение.

**Где.** `transaction.attempt` / `native_switch.attempt`, помощник `reset_old_flows`; `option flow_reset '0'` выключает. Статус: **реализовано** (влито в alpha8). Описание: [FLOW-RESET](architecture/FLOW-RESET-2026-11-03.ru.md).

**Эксперименты и результаты.** Модель доступности: при обрыве 15 с простой приложений на событие 54,8 → 23,6 с (оценка, диапазон 15–25 с); допущение «A≈3 с после сброса» на роутере не измерено. `[симулятор]` Роутер: `[нет данных]` по результату сброса. Сравнение: без сброса приложение ждёт тайм-аута (≈20 с); со сбросом — оценка 3 с. Тесты общих случаев Lua = Python. `[тесты]`

### 3.4 Чёрная дыра MTU

**Проблема.** Обычные проверки здоровья шлют только маленькие запросы, а большие пакеты теряются на узком месте. Основной канал считался здоровым, переключения не было, большие передачи зависали. Найдено на роутере (nft `meta length > 1300 drop` на туннеле с MTU 1350). `[роутер]`

**Цель.** Обнаруживать такую «дыру» и считать канал нездоровым.

**Простыми словами.** Как груз, который не проходит в узкую дверь: маленькие письма проходят, посылки нет. Мы раз в 5 минут посылаем через туннель «посылку» размером с его MTU и смотрим, вернулась ли она.

**Формулы и детали.** Эхо 64 байта и два больших эхо длиной MTU туннеля (не больше 1500, меньше 576 не проверяется), ожидание 1,5 с. Вердикт `black-hole`, если ни одного большого ответа при живом малом; пришедшее «fragmentation needed» (PMTUD работает) дырой не считается. Нагрузка: 6 ICMP-пакетов на канал раз в 5 минут. Ограничение MSS не лечит дыру ниже MTU туннеля, а прошивка GL уже ставит `TCPMSS --clamp-mss-to-pmtu`.

**Где.** `mtu_check.py` / `lua/mtu_check.lua`, код VPN-MTU, диагноз LARGE-PACKETS-FAILED. Статус: **реализовано** (alpha8, исправление `fix/mtu-check-runtime`). Файлы: [mtu_check.py](../router/files/usr/lib/homensai-vpn/mtu_check.py), [mtu_check.lua](../router/files/usr/lib/homensai-vpn/lua/mtu_check.lua), [MTU-SQM](architecture/MTU-SQM-2026-11-03.ru.md).

**Результаты.** **Провал, сохранённый как доказательство:** в alpha7 проверка на роутере не сработала — 0 переключений из 5 циклов (3 + 2 длинных по 450 с; Уилсон 0…43,5 %), код VPN-MTU в журналах отсутствует. Причина — ошибка рантайма (отказ отправки EPERM считался не потерей); исправление влито в alpha8, повторная проверка на роутере впереди. `[роутер]`, n=5 <59. Тесты общих случаев `mtu_check_cases.json` проходят. `[тесты]`

**Сравнение.** Старое (только малые запросы) не видит дыру; новое должно видеть, но на роутере пока доказано обратное. Победителя нет, пока нет успешного прогона.

### 3.5 SQM и закон Литтла

**Проблема.** При насыщении канала растут очереди в буферах («раздувание буфера»), задержка растёт и все проверки начинают падать.

**Цель.** Держать задержку низкой шейпером (SQM, алгоритм cake) на выходе туннеля; в перспективе подбирать скорость автоматически.

**Простыми словами.** Закон Литтла: среднее число ожидающих = скорость прихода × среднее время ожидания (L = λW). Если скорость постоянна, а очередь растёт, растёт и время ожидания. Шейпер намеренно ограничивает скорость чуть ниже пропускной способности, чтобы очередь не копилась в большом буфере провайдера.

**Где.** `sqm.py` / `lua/sqm.lua`, `sqm_enabled` и `sqm_upload_kbit` — **выключено по умолчанию**, кнопки на странице нет. Статус: SQM — **реализовано** (alpha8), авто-скорость по закону Литтла — **не реализовано**; скорость задаёт владелец вручную. Файлы: [sqm.py](../router/files/usr/lib/homensai-vpn/sqm.py), [sqm.lua](../router/files/usr/lib/homensai-vpn/lua/sqm.lua).

**Эксперименты и результаты.** Тесты на подставном `tc` (`sqm_cases.json`). `[тесты]` Замеров cake на роутере нет, влияние на задержку и CPU `[нет данных]`. Оговорка: cake — программный шейпер, на сотнях Мбит/с заметная доля ядра.

### 4.1 Генетический алгоритм против имитации отжига для настроек

> **Статус проверки (2026-11-07).** Подобранные значения `primary_stable` = 120 с и `rescue_stable` = 10 с пока не проверены: проверочные задания не завершены, а совпадение с роутером «22 из 23» посчитано на данных, по которым модель подгонялась. Это значения по умолчанию (длинное окно консервативно); они помечены экспериментальными: выбраны в симуляции, на железе не проверены.

**Проблема.** Настроек Auto много, взаимодействие неочевидно (например, длинный `primary_stable` помогает при дребезге, но ухудшает худший случай при падении резерва).

**Цель.** Найти значения по умолчанию, которые уменьшают суммарную цену суток, и сравнить два способа поиска.

**Простыми словами.** Генетический алгоритм копирует естественный отбор: «популяция» наборов настроек, лучшие скрещиваются и мутируют, худшие вымирают. Имитация отжига взята из металлургии: сначала допускаются и плохие шаги («горячий» металл), потом всё строже («остывание»). Оба прогоняют настройки через модель суток роутера и ищут минимальную «цену».

**Формулы и детали.** Fitness `F = простой (с/сутки) + 60·ложные + 20·ненужные + 30·(проверок в час/720) + 0,01·(с на резерве) + 100·(с блокировки ухода)` по смеси сценариев суток (обрывы 5–120 с, потери 5–80 %, всплески Гилберта–Эллиотта, дребезг, блок DNS, отказ резерва под нагрузкой, здоровые сутки). Интервал проверки закреплён на 10 с (решение владельца по CPU).

**Где.** Код оптимизаторов и модели — `private/math/evolution`; найденные настройки внесены в продукт: `recovery_rescue_stable` = 10 с (0 — прежнее), `primary_stable` 30 → 120 с, `fast_detect.LOSSES` 3 → 2. **Эксперименты.** Модель проверена против роутера: **22 из 23 пунктов совпали** (обрывы 5…150 с, потери 5…80 %, блок DNS/HTTPS, дребезг 60/120 × 10 — alpha5: 6 уходов и 4 непокрытых; alpha6: 8 и 0 — ровно как на роутере; простой LAN при уходе 23,0 против 22,3 с; возврат при упавшем резерве 194,8 против 191,5 с). ## 5. Фибоначчи и золотое сечение

Числа Фибоначчи 1, 1, 2, 3, 5, 8, 13… растут примерно в φ = (1+√5)/2 ≈ 1,618 раза за шаг («золотое сечение»). Это самая «равномерная» иррациональная пропорция: точки `i·φ mod 1` как можно реже накладываются друг на друга. Из четырёх применений в проекте одно явный победитель, одно в ветке, одно эквивалентно простой схеме и одно проиграло.

### 5.1 Паузы повторов по Фибоначчи с потолком и джиттером (выбор симуляции, не доказано)

**Проблема.** При повторных попытках (подъём туннеля, выбор сервера) фиксированная пауза 5 с без разброса приводит к тому, что 30 клиентов после рестарта сервера ломятся одновременно («стадо»), а слишком длинная лесенка паузы без потолка тратится впустую.

**Цель.** Дешевле по сумме «время + число попыток».

**Простыми словами.** После каждой неудачи ждём всё дольше (2, 2, 4, 6, 10, 15 с и дальше 15), но каждый раз случайное время от 0 до этого предела, чтобы клиенты не совпадали.

**Формулы и детали.** Пауза после n-й неудачи `b_n = min(15, 2·F_n)` = 2, 2, 4, 6, 10, 15, 15…; сама пауза = `U(0, b_n)` («полный джиттер»). Цена `J = время + w·число попыток` (w = 0,5/2/5 с на попытку).

**Где.** Рекомендация: функция `retry_pause(n)` в `native_switch.py` / `server_pick.py`; лимиты попыток и cooldown не трогать. Статус: **реализовано, по умолчанию, не доказано** (`retry_policy.py`, Фибоначчи 2, 2, 4, 6, 10, 15 с с полным разбросом; параметр `retry_backoff` = `fixed` оставляет прежние 5 с). Экспериментально: выбрано в симуляции, на железе не проверено; проверяющий анализ заблокирован (corrected) или не завершён (original).

**Эксперименты.** 30 000 прогонов на ячейку, общие случайные числа; модели отказа: независимый успех q = 0,2/0,5/0,8, «сервер недоступен Y с» (экспонента 20 и 120 с, логнормаль, фиксированные 45 с), «стадо» из 30 клиентов. `[симулятор]` Предположение «сейчас — фиксированные 5 с без джиттера» взято из чтения кода, какие циклы именно повторы, не проверено.

**Результаты (`[симулятор]`).** Стадо 30 клиентов: 68 с (сейчас) → 37 с (Фибоначчи 2→15 + джиттер); фиксированные 5 с + джиттер дают 36 с, это в пределах шума от 37 с: не доказано, что умолчание лучше фиксированных 5 с + джиттер. Средняя цена относительно лучшей политики: Фибоначчи 2→15 + джиттер ×1,060 (максимум ×1,16 при w=2); дешевле фиксированных 5 с (без джиттера) на 17/13/9 % (w = 0,5/2/5); в 2,3/2,0/1,6 раза дешевле удвоения 2→60 с. Три эффекта по убыванию: джиттер, потолок, форма (Фибоначчи ≥ удвоение при одинаковом потолке — разница несколько процентов).

**Сравнение.** Фибоначчи 2→15 + полный джиттер был выбором симуляции, но статистически неотличим от удвоения с тем же потолком и от фиксированных 5 с с джиттером; выгода идёт от джиттера и потолка, а не от формы Фибоначчи. Для одного роутера эффект «стада» мал, он важен при массовом рестарте сервера. Роутер: `[нет данных]`.

### 5.2 Разнесение фаз проб (золотое сечение и равномерное i·T/K)

**Проблема.** Если проходы проверок основного и резерва стартуют одновременно, процессов `curl` одновременно до 11, процессор «подпрыгивает» и проверки мешают друг другу.

**Цель.** Размазать старты проб по периоду.

**Простыми словами.** Как расставить точки на окружности, чтобы они мешали друг другу как можно меньше. Для известного числа задач K лучше всего поровну (`i·T/K`, для двух проходов — сдвиг на полпериода). Если задачи добавляются без перенастройки старых, лучше золотой угол: каждая новая точка попадает в самый большой просвет.

**Формулы и детали.** Фаза i-й задачи: `φ_i = (i·φ⁻¹ mod 1)·T`, φ⁻¹ = 0,618…; равномерная — `i·T/K`. Доля стартов, когда уже идёт другая проба (меньше — лучше); число Фано = дисперсия/среднее числа стартов за 1 с.

**Где.** Рекомендация: сдвиг начала прохода резерва на `interval/2` в `probe_policy.lua`/мониторе и расписание по абсолютному времени (старт + n·T). Статус: **реализовано, по умолчанию, не доказано** (`probe_plan.py`, параметр `probe_spread`, абсолютная сетка с фазами; работает равномерное разнесение `i·T/K` с шагом не больше 3 с, а не золотое сечение). Независимая проверка (зарегистрированный анализ фаз, original): CRITERIA_FAIL; золотое сечение хуже равномерного разнесения в части ячеек (K = 2, без дрейфа, длительность 3: 1,44 против 1,00, то есть примерно на 44 % хуже). Экспериментально: на железе не проверено; пик процессов на MT3000 не измерен.

**Эксперименты.** Модель «процессы в окне»: проходы primary и reserve (10 с, 0,6 с, 4 процесса curl), два пульса 1 с, такт Auto 2 с; K = 2, 4, 8 задач, дрейф таймера 0 и 50 мс. `[симулятор]`

**Результаты (`[симулятор]`).**

| Раскладка фаз | Перекрытие двух проходов | Пик процессов | p99 процессов |
|---|---|---|---|
| всё вместе | 0,50 | 11,0 | 9,0 |
| случайные фазы (среднее 30 розыгрышей) | 0,07 | 5,7 | 5,1 |
| только reserve сдвинут на T/2 | 0,00 | 7,0 | 5,0 |
| золотое сечение | 0,00 | 5,0 | 4,0 |

**Сравнение.** Победитель — равномерное `i·T/K` для известного K (K=2: сдвиг 5 с); золотое сечение — когда число задач растёт; взаимно простые периоды не лучше случайных (0,07–0,34) и меняют частоту проб, отброшены. При дрейфе таймера 50 мс/цикл выигрыш фаз за десятки минут размывается (K=8: 0,2 против 0), поэтому планировать надо по абсолютной сетке. Роутер: `[нет данных]`.

## 6. Криптография

### 6.1 Подлинность проверок канала: закреплённые корни TLS и одноразовый nonce

**Проблема.** Проверка канала доверяла всему системному хранилищу сертификатов (≈140 корней). Любой ошибочно выпустивший УЦ (в 2025 году такой выпустил сертификаты на 1.1.1.1) делал подмену «настоящей». Страница `/cdn-cgi/trace` не привязана к запросу, кэширующий посредник мог отдать старую. Сертификат портала, редирект на портал и обычный обрыв выглядели одинаково.

**Цель.** Чтобы живой или мёртвый вид туннеля нельзя было подделать на пути.

**Простыми словами.** Для каждого из трёх проверяемых сайтов мы доверяем не «любому УЦ мира», а только 4–13 корневым сертификатам, которые этот сайт действительно использует. В каждый запрос кладём одноразовый случайный номер (128 бит); настоящий ответ обязан его вернуть, иначе это старая страница.

**Формулы и детали.** Закрепление на уровне якорей: SHA-256 от SubjectPublicKeyInfo корней в `pins.json`, проверка TLS только против `probe-anchors/<host>.pem`. Свежесть: `User-Agent: HomenSAI-probe/<32 hex>` должен вернуться как `uag=`; без него `ts` в пределах ±60 с; скачок часов > 2 с — проверка не засчитывается. Если файла якорей нет, используется системное хранилище (проверка alpha7, а не отсутствие проверки). Причины недоверия: `untrusted-certificate`, `portal-redirect`, `nonce-mismatch`, `stale-response`, `clock-jump`. Кворум 2 из 3 сохранён.

**Где.** `probe_trust.py` / `lua/probe_trust.lua`; опция `probe_dns = doh` (выкл. по умолчанию). Статус: **реализовано** (alpha8). Файлы: [probe_trust.py](../router/files/usr/lib/homensai-vpn/probe_trust.py), [probe_trust.lua](../router/files/usr/lib/homensai-vpn/lua/probe_trust.lua), [PROBE-AUTHENTICITY](architecture/PROBE-AUTHENTICITY-2026-11-03.ru.md).

**Эксперименты.** Рукопожатие с настоящими серверами с ПК (`openssl s_client -CAfile`): каждый хост проходит со своим файлом корней; one.one.one.one не проходит с файлами Google и Quad9, dns.google и dns.quad9.net — с чужими (`unable to get local issuer certificate`); SPKI в `pins.json` совпали с `openssl x509 -pubkey | openssl dgst -sha256`. Общие случаи `probe_trust_cases.json`, тесты с настоящим TLS, тест срока ротации. `[тесты]`

**Результаты.** Доверенных корней 4–13 на хост вместо ≈140 `[расчёт]`; набор Cloudflare шире остальных намеренно (1.1.1.1 сменил УЦ с DigiCert на SSL.com). Реальная проверка на роутере: `[нет данных]`.

**Сравнение.** Новое строго ограничивает доверие и добавляет свежесть; цена — обновление пакета при смене УЦ сайта. Не закрыто криптографией: DNS по UDP (опция DoH переносит проверку в HTTPS); у dns.google JSON API свежесть держится только на закреплённых корнях. Известная идея из стандартов активных измерений (RFC 4656 OWAMP, RFC 5357 TWAMP: режимы authenticated/encrypted), для домашних failover-скриптов не найдена.

### 6.2 Подпись релизов usign, цепочка хешей и OpenTimestamps

**Проблема.** Подменённый или повреждённый пакет `.ipk` на GitHub, Gitea или флешке; «тихий откат» на старый пакет; нужно доказать, что релиз существовал на дату.

**Цель.** Роутер устанавливает только пакеты, подписанные ключом владельца, и только продолжающие проверенную историю.

**Простыми словами.** Каждый релиз подписывается секретным ключом (Ed25519, формат usign из OpenWrt). Каждая запись истории включает хеш предыдущей, поэтому переписать историю нельзя незаметно. Хеш записи «приколачивается» к блокчейну Bitcoin сервисом OpenTimestamps, это доказывает дату. Подписать можно только с кодом из телефона.

**Формулы и детали.** Подпись Ed25519 (векторы RFC 8032); `CHAIN.jsonl`: запись `hash_i = H(запись_i, hash_{i−1})`; два ключа (основной и резервный), отзыв `<ключ>:<номер записи>`; TOTP ±1 шаг (30 с), повтор кода отклоняется, 5 неверных подряд — блокировка на 10 минут. Ключи лежат в `/etc/homensai-vpn/keys`, не в `/etc/opkg/keys` (чтобы не получить права подписывать чужие ленты). Реализация Ed25519 на чистом Python не постоянная по времени, работает только на ПК владельца.

**Где.** Ветка `feat/usign-signing-20261103` (`339e17c1`): `scripts/signing/`, `releases/CHAIN.jsonl`, `homensai-vpn-trust-key`. Статус: **в ветке**, в alpha8 не влита.

**Эксперименты.** Совместимость с настоящим usign из OpenWrt 21.02.7 SDK в обе стороны: подписи побайтно совпадают, все 153 записи настоящей цепочки проверены; все 26 тестов пути установки прошли с настоящим usign, с Python-двойником и под BusyBox ash/sed (alpine 3.20); мутации: 18 из 18 убиты. `[тесты]` OpenTimestamps: отметка головы цепочки отправлена, все 4 календаря ответили, статус «ожидает подтверждения». `[тесты]`

**Результаты.** Роутер: путь установки не проверялся `[нет данных]`; первая проверка — при установке первого подписанного релиза с участием владельца. Не закрыто: первая установка (ключи комплекта могут быть чужими, нужно сверить отпечатки), TOTP — процедурная защита (семя под тем же DPAPI Windows), без внешнего журнала прозрачности с независимыми наблюдателями защита от «разной выдачи разным людям» слабее.

**Сравнение.** Было: SHA-256 рядом с файлом, который подменяется вместе с пакетом. Стало: подпись, которую без секретного ключа не сделать. Все элементы известны (TUF, Sigstore, Go checksum database, OpenTimestamps); редкое — всё вместе в небольшом домашнем проекте.

### 6.3 Шифрованные резервные копии age и закрепление ключей серверов (TOFU)

**Проблема.** Секреты проекта на ПК защищены только Windows DPAPI: сгорел ПК — потеряны ключи доступа к роутеру и все зашифрованные экспорты. Отдельная угроза: роутер доверяет тому, что лежит в конфиге GL; подменённый сервер VPN выглядит здоровым.

**Цель.** (1) Секреты переживают потерю ПК; (2) подмена сервера VPN с тем же именем видна.

**Простыми словами.** age — простой формат шифрования файлов: архив секретов шифруется на публичный ключ владельца и безопасно лежит на флешке; расшифровать можно любым ПК с личным ключом из менеджера паролей. TOFU («доверие при первом использовании», как в SSH): при первой удачной проверке сервера запоминаем его ключ; если тот же сервер (по имени) вдруг показывает другой ключ — тревога.

**Формулы и детали.** age v1: X25519, ChaCha20-Poly1305 блоками по 64 КиБ, заголовок защищён HMAC. TOFU: идентичность = профиль + имя хоста (не IP); WireGuard — публичный ключ пира из `wg show endpoints`; OpenVPN — SHA-256 DER сертификатов CA; состояния `pinned → changed → accepted/forgotten`; «changed» липкое. Режим `server_key_pin`: `warn` (по умолчанию) | `enforce` | `off`; при `enforce` Auto не использует канал со сменившимся ключом. Пул NordVPN не ломается: другое имя хоста — просто новое первое использование.

**Где.** Ветка `feat/age-tofu-20261104` (`724d9fb0`): `scripts/backupcrypt/`, `server_pin.py`, `lua/server_pin.lua`. Статус: **в ветке** (в работе), в alpha8 не влита.

**Эксперименты.** Официальные тестовые векторы C2SP/CCTV: 147, из них 129 проверены (все совпали), 18 — постквантовая личность вне объёма; настоящая утилита `age` 1.1.1: 32 из 32 взаимных проверок; 18 тестов инструмента; мутационная проверка 76 мутантов, 76 убиты (первый прогон 65 из 74 нашёл 9 дыр в тестах — закрыты). Архив 21 МБ (811 файлов, 208 ключей DPAPI) шифруется за ≈6–8 с на чистом Python. `[тесты]`

**Результаты.** Роутер не проверялся `[нет данных]` (нужно: `wg show endpoints` у NordVPN-профиля, реальный путь `--config`/`--cd` у OpenVPN GL 4.11). Не защищает от компрометации самого ПК и от кейлоггера.

**Сравнение.** Было: потеря ПК = потеря всех секретов; подмена сервера не видна. Стало: восстановление на любом ПК и предупреждение (по умолчанию не блокирует). Слабое место: owner-шаги (создание личности, TOTP) ещё не выполнены.

## 7. Первый P95 из n ≥ 59 на роутере (alpha7, n = 61) и найденная им ошибка 84 с

Причина: отправленное переключение (APPLYING, бюджет списан) было прервано прошивкой (`VENDOR-WORKER-QUIET-UNVERIFIED`), транзакция откатилась до какого-либо переключения, но списанный бюджет остался, и следующая попытка ждала `max(cooldown, min_dwell)` = 60 с (`PAIR-RATE-LIMIT`, основной всё ещё упавший). Один выброс из 61 растянул максимум почти втрое выше P95. Исправление `a3591140`: переключение, отказанное временным состоянием прошивки и подтверждённо откатанное, не считается переключением, бюджет возвращается, повтор ждёт 5, 10, 20, 40 с, затем `max(cooldown, min_dwell)` после каждого очередного отказа (не «горячий» повтор); завершённое переключение обрывает серию; все шлюзы прошивки не изменены. Исправление проверено близнецами Python/Lua на общих случаях (в том числе симуляция цикла 28) `[тесты]`, на роутере повторного прогона ещё нет `[нет данных]`.

**Сравнение с прежним.** Прежняя публикация: 2.0.0-beta4, n = 15, медиана 36,1 с, «P95 = 39,3» (на самом деле максимум из 15 замеров: не было ни P95 из n ≥ 59, ни какой-либо верхней границы). Сейчас n=61: P95 = 29,8 с. Версии разные (beta4 и alpha7), поэтому в одну выборку не сливаются и «улучшение» из этих двух чисел делать нельзя.

## 10. Что ещё не проверено и как углубить

Источники: поиск прежних работ `private/research/PRIOR-ART-2026-11-04.ru.html`, отчёты исследований, итоговый отчёт.

1. **Один стенд.** Всё откалибровано на одном MT3000, одной домашней сети, одной паре провайдеров. Прогнать стенд минимум в 3 независимых сетях (проводной и мобильный), опубликовать трассы потерь как набор данных. MT6000, IPv6 у провайдера, внешний LAN-клиент, 24-часовой soak и отключение питания на alpha8 — отдельные пункты.
2. **Мало данных на роутере.** Для каждого вида сбоя и версии нужно 59–93 цикла (≈3,5–5,6 ч); для порогов — доля переключений с интервалом Уилсона на 20–59 циклах. Прогон alpha8 (HMM, условие возврата 0,90, `rescue_stable`, сброс потоков) на роутере ещё не получен.
3. **Калибровка и проверка на одних журналах.** «22 из 23» получено на тех же данных, по которым подгонялась модель. Разделить данные: подгонка на одних сессиях, проверка на других и на другом железе. Пункт «потери 10 %» не совпал и оставлен.
4. **Базовые линии из литературы.** Детектор сравнён только с «3 подряд» и поздней перепроверкой (и SPRT, CUSUM). Добавить φ-accrual (Hayashibara и др., 2004), адаптивный детектор Chen–Toueg–Aguilera, оценку RTO по Якобсону; отчитывать метрики Chen (время обнаружения, интервал между ложными, длительность ошибки) с доверительными интервалами.
5. **Самодельный проверяльщик состояний.** Перенести малый профиль в TLA+/TLC или Promela/SPIN и сверить число состояний и контрпримеры; мутационная проверка самого проверяльщика; валидация трасс реального кода по журналам роутера. Модель не содержит исправления К11, её нужно дополнить; К3, К4, К9 проверить на роутере.
6. **Независимость датчиков в кворуме.** Измерить корреляцию датчиков на своих трассах и дать границу ложной тревоги с поправкой на корреляцию (эффективное n). Журнал по целям `probe_target_log` (результат и задержка каждой цели в каждой пробе, промахи эхо-пульса по целям) добавлен ровно для этого; данные с роутера ещё не собраны, ρ остаётся сценарием.
7. **Длительности сбоев.** Естественных сбоев всего 11; нужно ≥ 100, с учётом цензурирования; проверить форму хвоста на открытых данных (FCC Measuring Broadband America).
8. **Допущения без измерения.** Цена секунды на резерве (c ≈ 0,01), стоимость переключения C = 20 с, A≈3 с после сброса потоков, оценка CPU HMM ×5–10, частоты отказов серверов, распределение длин блэкаутов, cR резерва для закона √.
9. **Фронт Парето: разрыв «симулятор → реальность».** Проверить на стенде несколько точек фронта (t = 0, 0,5, 1) по 59+ повторов и убедиться, что порядок точек сохраняется; семь дней проверки советника на роутере до режима «Авто».
10. **MTU-проверка и SQM.** Повторить проверку чёрной дыры после исправления EPERM (alpha8); измерить cake на роутере (задержка, CPU); авто-скорость по закону Литтла.
11. **Криптография на роутере.** Первая настоящая проверка подписи при установке первого подписанного релиза; TOFU — `wg show endpoints`, путь `--config`/`--cd` у OpenVPN; сопоставление модели угроз проб с OWAMP/TWAMP; внешний журнал прозрачности с независимыми наблюдателями; owner-шаги age (создание личности, TOTP).
12. **Не реализовано из плана:** MDP для решения о возврате, Калман/PID для частоты проб (фильтр Калмана есть только как мягкий сигнал RTT `rtt_watch`, выкл.; CUSUM только как запуск плотной проверки `cusum_trigger`, выкл., решений он не принимает), покрывающие массивы для матрицы испытаний, иммунная память по времени суток, энтропийные пробы и гомеостаз, SQM по закону Литтла, оценка сервера по Махаланобису, дрейф по дивергенции Кульбака–Лейблера, периодичность по FFT, формула износа flash, подписанные отчёты испытаний.
13. **Рецензирование и репликация.** Внешних рецензентов нет; лицензия исходников не open source. Подготовить артефакт для воспроизведения (скрипты, зёрна, данные), препринт (arXiv cs.NI). Идея «подбор порога по истории» пересекается с патентами Cisco (US 11 574 241, US 11 032 181): перед публикацией описать отличия (на устройстве, другая модель).
14. **Оговорка поиска прежних работ.** Поиск шёл по открытым аннотациям (≈45 запросов), «не найдено» означает «не появилось в выдаче». Новизну отдельных методов не заявляем: ни один метод не новый, редким является их сочетание в одном небольшом продукте с проверкой на реальном железе.
