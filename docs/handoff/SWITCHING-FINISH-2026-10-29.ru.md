**Итог: исходник исправлен и прошёл утверждённый CI, но не установлен и не выпущен.** Физический MT3000 остаётся в состоянии инцидента alpha57; для установки нужен один отдельный шаг с разрешения владельца (раздел 4).

## 1. Первопричина (доказана на роутере, только чтение)

- По истории переключений на MT3000 успешный переход проводит в APPLYING 46–52 с, из них около 35 с до запуска штатного `rtp2` (повторные диагностики по ~5 с перед каждой записью). Родитель ждал работника не дольше 50 с.
- Попытки 1516, 1521 и 1558 (инцидент) прерваны по `TimeoutExpired`. В инциденте `rtp2` убит через ~21,8 с после запуска: журнал APPLYING, работник мёртв, файл блокировки `rtp2.lock` остался от мёртвого процесса, цепочки TUNNEL в mangle сброшены, отпечаток ядра отличается от исходного.
- Отличие `firewall` — **не изменение владельца**: отсутствует только штатная секция `forwarding guest2ovpnclient2` с `gl_vpn_rules '1'`. `rtp2` сначала удаляет все такие секции, затем пересоздаёт их по одной; он был убит между `lan2ovpnclient2` и `guest2ovpnclient2`.
- Поэтому alpha57 оставалась в HELD / `PAIR-RECOVERY-REQUIRED`, а ручной запрос получал `KERNEL-POLICY-UNVERIFIED`. Кандидат alpha59 тоже не восстановил бы это состояние (отказ по изменению firewall и отпечатку ядра).

## 2. Что исправлено

| Область | Изменение |
|---|---|
| Бюджет времени | транзакция 120 с; `rtp2` запускается только при запасе ≥75 с, иначе чистый откат UCI без изменения ядра; родитель ждёт срок +5 с; `rtp2` останавливается сначала SIGTERM (его ловушка удаляет блокировку), затем SIGKILL; убрана одна лишняя диагностика |
| Восстановление | узкий путь `vendor-rebuild` для прерванной штатной перестройки: мёртвый работник, блокировка мёртвого процесса, граф без маршрутизации, отличия только в штатных секциях; проверки перед каждой записью; успех только при исходном порядке, подтверждении ядром исходного канала и совпадении всех защищённых конфигураций; Auto остаётся OFF |
| Обновление | lifecycle guard разрешает обновление поверх прерванного журнала только без живого apply-процесса, при Auto OFF и native STOPPED/BLOCKED; журнал, guard и состояние пары не трогаются; удаление пакета по-прежнему запрещено; prerm передаёт `upgrade` только при обновлении |
| Интерфейс | одна модель операции/восстановления и один таймер для всех зон; «Нужно восстановление» вместо «настройки изменены вне приложения»; «Auto: нет связи» только при потере RPC; основной всегда выше резерва; текст «Живой, можно переключиться на него вручную»; таблица Design C: Канал, затем Статус; предел 2 минуты |

## 4. Блокер установки — нужно решение владельца

opkg на роутере (`1bf042dd`, 2021-06-13) при обновлении запускает `prerm upgrade` **установленного** пакета. Установленный prerm alpha57 вызывает проверку `check` и отказывает при журнале APPLYING. Поэтому alpha61 нельзя установить штатно, а alpha57 сама не восстановится.

Варианты:
- **A (рекомендуется):** сохранить копию `/usr/lib/opkg/info/homensai-auto-vpn.prerm` (SHA256 `c2fe1d54…`), заменить только этот файл prerm из пакета alpha61 со сверкой хеша, затем штатный `opkg install` alpha61. Журнал, guard, состояние пары и настройки не трогаются; восстановление выполнит сама новая служба.
- **B:** оставить роутер в текущем безопасном удержании (только VPN, guard) до другого решения.

Ручной перезапуск `rtp2` вне приложения не предлагается как основной путь: он обходит проверки продукта.
