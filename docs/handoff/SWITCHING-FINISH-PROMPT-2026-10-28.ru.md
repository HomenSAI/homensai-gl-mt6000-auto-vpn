# Промпт для другого ИИ: независимо проверить и завершить исправление Auto VPN

Ты принимаешь работу у другого ИИ и независимо проверяешь исправление `HomenSAI/homensai-gl-mt6000-auto-vpn`. Ветка `fix/switching-recovery-20261028`, [draft PR #2](https://github.com/HomenSAI/homensai-gl-mt6000-auto-vpn/pull/2), содержит кандидат alpha59, начатый от GitHub `2b10976cb5686cab149f66c237b1b51c32775cc0` (alpha57). Кандидат не установлен и не выпущен. Пользователь жалуется на невозможность ручного переключения и нестабильную работу Auto. Результат работы — подтверждённая сквозная работоспособность на разрешённом стенде с понятной одинаковой индикацией. Считай прежние выводы проверяемыми утверждениями: сопоставляй код, отрицательные воспроизведения, точный проверенный исходник и конечные результаты. Зелёный unit-тест или вид страницы сам по себе не доказывает маршрут.

## 1. Установи точную исходную точку

Прочитай `CLAUDE.md`, `docs/CURRENT-STATUS.md`, `docs/handoff/CURRENT.md`, `docs/handoff/SWITCHING-REPAIR-2026-10-28.ru.md`, `docs/handoff/SWITCHING-FOLLOWUP-2026-10-28.ru.md`, текущий ROADMAP и release procedure. Получи и прочитай **`docs/handoff/TODO-CLAUDE-SWITCHING-2026-10-28.ru.md` как основное задание владельца**. При предыдущей проверке этого файла не было ни в одной полученной ветке/истории GitHub. Если он всё ещё отсутствует, запроси файл или точный ref; не создавай под его именем выдуманную копию и не объявляй его требования выполненными. Анализ и безопасные локальные исправления продолжай; выпуск/установка остаются заблокированы.

Зафиксируй отдельно commit исходника, ветку, VERSION.json, имя/hash собранного пакета, реально установленный пакет и отданные браузеру assets. Не приравнивай эти сущности. Проверь текущий head PR до начала и перед загрузкой своих изменений; используй fast-forward с проверкой ожидаемого head, без force-push. Коммиты локального проверенного архива и GitHub snapshot могут иметь разные SHA: равенство Git tree и machine records объясняет связь, но не заменяет требуемый exact-SHA release CI. Финальный коммит с evidence также не считается автоматически разрешённым release-record коммитом. Прежние PASS alpha57 относятся к своему исходнику и времени. В частности, её read-only браузерная проверка и отдельные API-переключения не доказывают одну сквозную цепочку «клик → переключение ядра».

Используй ровно три субагента: (1) backend, транзакции и recovery; (2) UI, таймеры и согласованность состояния; (3) независимые fault injection, ядро и настоящий браузер. Основной исполнитель объединяет изменения и проверяет пересечения. Субагенты не управляют физическим роутером параллельно.

## 2. Проверь и заверши уже подготовленные исправления

Сначала воспроизведи новые regression scenarios на исходной alpha57, затем на кандидате. Сохрани отрицательные результаты. Проверь как минимум:

- Stop непосредственно после durable ARMED, до Popen; исключение при создании worker; смерть worker до и после фактического изменения правил.
- Возврат из pair tick с ARMED/APPLYING/WAIT-CLIENT/RESTORING/RELEASE-PENDING: supervisor передаёт управление recovery, отзывается ON, повторное исполнение старого ручного запроса невозможно.
- Stop при QUEUED и CLAIMED; orphan CLAIMED; повторный Stop; рестарт службы; terminal result остаётся доступен UI и не переписывается поздним завершением.
- Отказ RTP после UCI reorder; повторное восстановление только своего подтверждённого промежуточного состояния. Успех RTP с кодом 0 без ожидаемого ядра обязан оставаться отказом.
- Отказ forward RTP до изменения ядра при UCI=after и полном сохранённом kernel_before_fingerprint. Проверь promotion только после OFF с явным restore_proof_source=forward: UCI origin и подтверждённый kernel order разделены, все прежние проверки обязательны. Неверный original proof, confirmed flags, другой граф/профиль/ревизия запрещают этот путь. При неизменившемся реальном канале event.route_changed должен остаться false.
- Обрыв после первого из нескольких UCI moves и после последнего move до commit. Проверь durable checkpoint, записанный до конкретного следующего шага: его before/after должны принадлежать каноническому минимальному плану. Повторный commit требует собственного подтверждённого шага; простое совпадение target order не разрешает сохранять чужие pending changes. Подменённый шаг, non-order изменение UCI, другой hash, guard или revision должны отказать до записи.
- Успешный автоматический failback завершает текущий tick. Контроллер не использует прежний `kernel.role=target`, не отправляет второй return и не переходит в ложный HELD после уже восстановленного основного канала. Следующий tick заново подтверждает ядро и продолжает OBSERVING. Отказ свежей проверки основного при возврате также не разрешает вторую попытку в том же цикле.
- Подмена tx, revision, пары, vendor generation, process bindings, UCI order/hash, routing tables, rule masks/order или owned guard; отсутствующий/повреждённый fingerprint; старый журнал без нового доказательства. Во всех случаях доказать отсутствие запрещённых writes.
- Падение посреди многопозиционного UCI reorder. Если текущий узкий recovery этого не покрывает, либо реализуй отдельное durable доказательство каждого шага и независимо проверь его, либо оставь явно незакрытым обязательным пунктом. Не разрешай произвольные перестановки и не удаляй журнал ради разблокировки кнопки.
- Интервалы проверки 10, 30, 90, 300 секунд; пределы freshness, отрицательные/повреждённые timestamps и обратный ход часов. Health observation, heartbeat, kernel proof и отклик сайтов имеют разные сроки годности.
- Известное невалидное, неразрешённое к восстановлению ядро должно объяснять недоступность ручных routing choices уже в status. Поздняя строгая проверка consume обязательна независимо от этой индикации. Отдельно проверь разрешённое repairable-missing состояние и Resume, который сам не меняет сеть.

Прочитай `observation_freshness.py`, `rollback_recovery.py`, `website_publication.py` и новые tests, не доверяй только описанию. Сохрани общие Stop/CAS/ownership/vendor/kernel проверки, quota/cooldown и отказ от самопроизвольного Start после recovery. Не ослабляй тесты, проверки ядра или version/hash gates ради зелёного результата.

## 3. Выполни одну сквозную проверку в настоящем браузере

Открой реально установленную LuCI-страницу и запиши цепочку одного физического браузерного клика: элемент → RPC и request_id → очередь → claim → worker → исходные/конечные правила → terminal result → все индикаторы. Скриншот, вызов функции в консоли, curl или отдельный API-запрос не заменяют клик. Fixture браузера и отдельное тестовое ядро полезны, но должны оставаться явно отдельным уровнем доказательств.

Проверь основной → резервный и резервный → основной, повторный выбор уже действующего канала без изменения правил/расхода бюджета, видимую кнопку «Возобновить Auto» и автоматический возврат согласно настройке владельца. Resume обязан пройти настоящим браузерным кликом через существующий `pair_manual('resume')`, снять hold и сам по себе не менять правила, не запускать новую сессию и не расходовать бюджет. Ручное удержание здорового канала не отменяет существующую защитную реакцию при его отказе; сообщение не должно обещать полностью выключенную автоматику. Уточни контракт ручного режима по основному handoff: ручной выбор, manual hold и состояние Auto должны согласовываться, не меняй этот контракт догадкой. Проверь двойной клик, потерянный ACK, задержанный старый status, reload/новую вкладку в середине операции, скрытую вкладку, offline/online и пропавший RPC.

Пока запрос QUEUED/CLAIMED/APPLYING/WAIT-CLIENT, UI не показывает успех и не разрешает дубликат. Терминал относится к тому же request_id/revision. Таймер работает независимо от успешного RPC; по исчерпании времени сообщает неопределённость, а не завершение. Stop остаётся доступным в неопределённом состоянии. Поздний ответ не возвращает старую лампу или старый выбранный канал. Смена часов роутера не блокирует все будущие ответы.

Отдельно задержи готовый status на 24 секунды — меньше 30-секундного RPC deadline. Длительность запроса должна войти в возраст всех доказательств: получение старого frame не обновляет kernel TTL 15 секунд, heartbeat 30 секунд и website TTL 45 секунд. Проверь настоящий Chromium до и после доставки, включая «Минимум», боковую панель и оба отклика; фиксируй, где использован синтетический RPC overlay. Новая вкладка после Stop и обратного хода часов должна показать корректную причину CANCELLED/REFUSED, не предоставляя старому сообщению неограниченный срок годности и не используя его как разрешение маршрутизации. Проверь также другую вкладку: её новая команда с другим корректным request ID и меньшим wall-clock timestamp должна заменить старый сохранённый отказ; старый RPC и локальный отказ без request ID по-прежнему имеют свои fences.

Сверь «Минимум», Auto, левую панель, карточки каналов, таблицу проверок, live chart, события и сообщения. Зелёный выбранный канал требует действующего подтверждения ядра и актуального здоровья. Жёлтый здоровый резерв не обещает доступность ручного клика при cooldown; запрет объяснён рядом с действием. Неизвестные данные показаны как неизвестные, реальные ошибки — с причиной. DEGRADED/HELD и только что восстановившийся VPN не должны порождать взаимоисключающие утверждения.

## 4. Проверь отклик обоих каналов

Показатель остаётся средним полного замера Google, Cloudflare и Wikipedia через конкретный VPN: DNS+TCP+TLS+HTTP headers, только 3/3 даёт число. Не заменяй его ICMP или оценкой «канал здоров».

При интервале health scan 300 секунд дай обоим асинхронным измерениям завершиться и проверь, что они появляются в status/UI/истории до следующего health scan. Первый завершённый канал не ждёт второго. Исходные health timestamps не обновляются из-за фонового результата. После 45 секунд показывается просрочка; неполный ответ показывает покрытие, а не придуманный средний. Перевод wall clock назад не оживляет истёкший sample; монотонный возраст также ограничивает его срок. Повторная публикация и повтор после ошибки записи не удваивают статистику; временная ошибка истории допускает retry без нового измерения и не теряет уже завершённое измерение. Старое поколение/другой профиль не получает чужой результат.

## 5. Реальные правила и физическая приёмка

Сначала используй изолированный стенд. Для каждого перехода сохрани UCI order/hash, journal phase/request_id/tx/revision, `iptables-save -t mangle`, `ip -4 -j rule show`, необходимые routing tables и owned guard до/после. Проверь, что выбранная роль выводится из фактических правил; одних успешных проб туннелей недостаточно. Controlled failures: основной недоступен, резерв недоступен, оба недоступны, восстановление основного, ошибка применения и остановка во время применения. Каждая injected неисправность должна иметь доказанное снятие.

Перед выделенным MT3000 прочитай приватный runbook, проверь его аппаратную/прошивочную идентичность и займи `private/ACTIVE-EXECUTOR.local.json`. Primary MT6000 и Windows networking исключены. Не возобновляй исторические fault rules или observers. Не принимай условия за владельца. Используй уже данное разрешение владельца в его реальном объёме; routine проверки не требуют повторного согласования.

Локальные reproduction scripts должны иметь read-only host `/etc` и `/run`, отдельный writable fixture и снятые capabilities. Перенаправляй все производные пути, включая CERT, а не только базовую PERSIST. Ранний QA оставил синтетические служебные файлы на executor; это описано в evidence и не является состоянием физического роутера. Не удаляй неизвестные host-файлы для получения зелёного теста. Отличай model filesystem crash harness от реального выполнения production native child, libuci и ядра; называй каждую такую границу в отчёте.

## 6. Выпуск разрешён только после всех gates

Соблюди основной handoff и текущую release procedure полностью: code/tests → rebuild generated UI → согласованные версии/docs → immutable exact-SHA CI на двух утверждённых средах, включая настоящий Lua → отдельная сборка с тем же SHA256 → допустимый record-коммит → проверенная зашифрованная копия до → штатный Stop/установка/проверка/разрешённый Start → сквозные реальные проверки → проверенная зашифрованная копия после → разрешённая публикация GitHub/Gitea → независимое скачивание и сверка assets. Не заменяй отсутствующий pinned Docker CI локальным похожим Python и не подменяй физический MT3000 виртуальной машиной.

Не force-push, не двигай старые теги/пакеты, не теряй чужие изменения, private и секреты не публикуй. Если gate недоступен или падает, сохрани код и доказательства в отдельной ветке/draft PR, укажи конкретный блокер и продолжай остальные разрешённые проверки. Не выпускай и не устанавливай непроверенную сборку.

Финальный отчёт владельцу — по-русски: первопричины; что исправлено; таблица сценариев до/после с типом стенда; точный commit/пакет/hash и фактическое состояние роутера; ссылки на доказательства; оставшиеся FAIL/BLOCKED. Утверждение «ручное и автоматическое переключение работает» допустимо только после соответствующих сквозных проверок. Большое число тестов, зелёные лампы и код возврата скрипта сами по себе этого не доказывают.
