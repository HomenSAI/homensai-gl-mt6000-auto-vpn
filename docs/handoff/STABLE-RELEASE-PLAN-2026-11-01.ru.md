## 1. Что значит «стабильный» здесь

Сборку можно назвать стабильной, если одновременно:

1. один неизменяемый тег, пакет и контрольная сумма прошли точную сборку в двух средах CI и независимую проверку скачанных файлов (как 0.9.0);
2. на выделенном MT3000 (GL.iNet 4.11.0) пройдены ворота G1–G9 ниже на **этих же байтах кода** (допустима разница только в версии и идентичности ресурсов, как между alpha45 и 0.9.0 — это надо записать);
3. владелец прошёл [живой тест на своём роутере](../OWNER-LIVE-TEST.ru.md) (G10);
4. всё, что не проверено, названо в примечаниях к выпуску как ограничение, а не умалчивается (G11, G12).

Что **не** входит в слово «стабильный»: все провайдеры и прошивки, MT6000, IPv6. Они остаются отдельными приёмками, пока не появится явное свидетельство.

### Предлагаемые критерии прохождения G2 и G4 (черновик для утверждения)

Взяты из того, что уже измеряли в прогонах; пороги владелец может поменять.

- Каждый цикл заканчивается в `OBSERVING` на основном канале, кроме циклов внутри задокументированного окна внешней аварии сервера (как в прогоне C 01.11, 04:00–04:55). Таких циклов не больше 5 %.
- Ни одной блокировки, которая не снимается сама за 10 минут; ни одного `ROLLBACK-GIVEN-UP`, `HISTORY-CORRUPT`, неожиданного `LUA-AUTO-FALLBACK` / `HV-CORE-FALLBACK`.
- Каждый обрыв питания: Auto возвращается без Start, LAN с интернетом, нет остаточного собственного стража `homensai_vpn_guard`.
- История: число событий в журнале и состоянии согласовано (как в прогоне C: 332 события, без пропусков, `archive_gap` = 0).
- Память служб (RSS) и процессор по `report/rss.svg`, `cpu.svg` не растут от начала к концу сутками.
- Переключение при сбое: время от APPLYING до COMMITTED в пределах прошлых прогонов (4,4–8,0 с); решение Auto через 26–28 с после начала сбоя на уровне опроса 1.

## 3. Схема версий (предложение)

| Версия | Когда | Что это |
|---|---|---|
| 2.0.0-alpha26 (если нужны правки) | пока ворота G0–G3 находят дефекты | рабочие тестовые сборки, как сейчас; исправления не откладывать до беты |
| **2.0.0-beta1** | G0–G5 и G9 пройдены на MT3000 на одной сборке; G7 пройден или явно записан как ограничение | кандидат на стабильный; **именно его владелец ставит на свой роутер** (G10). Заготовка примечаний: `releases/v2.0.0-beta1.md.draft` |
| 2.0.0-beta2, … | если владелец или поздние ворота нашли дефект | как beta1, с исправлением; пройденные ворота, затронутые правкой, повторяются |
| **2.0.0** | G10 пройден (и G6, если владелец включил его в условия) на последней бете | те же функциональные байты, что у последней беты; меняются только версия и идентичность ресурсов. В отчёте записывается, что код не менялся и что именно сравнивалось (как в [RELEASE-0.9.0](../RELEASE-0.9.0.md)). Отдельная установка на MT3000 для 2.0.0 нужна не больше, чем для 0.9.0 (проверка отданных байтов), если разница только в версии |
| 2.0.x | после | исправления; 2.1.0 — C читает/пишет журнал, кэш диагностики и т. п. |

Почему так: имена `alpha|beta|rc` уже разрешены `scripts/publish-reviewed.py` (регулярное выражение `v[0-9]+\.[0-9]+\.[0-9]+-(?:alpha|beta|rc)[0-9]+`). Обычный тег `v2.0.0` скрипт **отвергает** (`RELEASE-SCOPE`, комментарий в коде: «a plain version tag (final release) stays a separate owner decision»), а `create_release` всегда ставит `--prerelease`, и `publication_resume.finish` требует `prerelease is True`. Поэтому публикация beta1 идёт существующим скриптом, а 2.0.0 требует отдельного проверенного шага (раздел 5, вариант публикации стабильного). Номер 1.0.0 уже занят линией Python (`v1.0.0-beta15` — `main` на GitHub); 2.0.0 для Lua продолжает существующую нумерацию alpha без пересечений.

## 4. Как линия Lua становится основной на GitHub (варианты, решает владелец)

Факты, проверенные `gh` только на чтение (01.11.2026):

- GitHub `main` = `930bc43c` («Reviewed local snapshot d69586e5…»), `VERSION.json` 1.0.0-beta15, тег `v1.0.0-beta15`.
- Помеченный **Latest** релиз — `v1.0.0-beta13` (линия Python); `v1.0.0-beta14/15` и все Lua-альфы помечены Pre-release.
- Теги Lua (`v2.0.0-alpha22`, `alpha23`) указывают на цепочку снимков в ветке GitHub `feat/lua-core-20261030` (`f78660bd`, родитель `8db86e6f`). Относительно `main` эта ветка **разошлась**: 5 коммитов впереди, 3 позади. Простое быстрое перемотывание `main` на неё невозможно.
- Локальная история (Gitea) и история GitHub различаются; деревья проверенных снимков совпадают (политика `PUBLICATION.md`). Gitea `main` (`0fc0df3e`) устарел (эпоха 0.9.0), Lua-линия живёт в `feat/lua-core-20261030`.
- Скрипт `scripts/publish-reviewed.py` строит снимок так: `git commit-tree <дерево кандидата> -p <текущий GitHub main>`, сохраняет в Gitea и пушит в `main` как **быстрое перемотывание без force**. Теги и релизы создаются только если их нет (`RELEASE-TAG-EXISTS`, `RELEASE-ASSET-COLLISION`).

Обязательные шаги страховки при А (все — только новые ссылки, никаких перезаписей):

1. Перед публикацией создать новую ветку `python-line/1.0.0-beta15` на `930bc43c` (создание новой ссылки, не изменение старой) и записать SHA в документ публикации.
2. Теги `v1.0.0-beta*`, `v2.0.0-alpha*` и их файлы не трогать. Флаг Latest сдвинется на `v2.0.0` только в момент публикации его как обычного релиза (не Draft, не Pre-release), как это было с 0.9.0.
3. Описания репозитория и README обновить в том же снимке; в старые релизы линии Python добавить заметку «текущая линия — 2.x» только по отдельному разрешению (при 0.9.0 это делалось для 40 релизов).
4. Gitea: `feat/lua-core-20261030` слить в `main` Gitea обычным слиянием (история Gitea каноническая и сохраняется); SHA GitHub и Gitea различаются, деревья совпадают, это записывается в `qa/RELEASE-2.0.0-PUBLICATION.json` (по образцу `qa/RELEASE-0.9.0-PUBLICATION.json`).

Публикация стабильного (`v2.0.0`) требует решения владельца о правке скрипта: разрешить тег без суффикса и `--latest`/не-prerelease (или выполнить эти два действия вручную `gh release create … --latest` после проверки скачанных файлов). До этого `publish-reviewed.py` для 2.0.0 использовать нельзя.

## 5. Порядок работ до выпуска (кто что делает)

1. К: собрать alpha26 (или сразу кандидат beta1) с фиксом пинов набора; CI на точном SHA; запись пакета. Проверить, что в пакете `02-install.sh` и `03-verify.sh` согласованы (G0).
2. К: дождаться итога прогона alpha24 (G2), разобрать (G3); при дефектах — исправления и новый 3-часовой прогон.
3. К: G1, G5, G9 на кандидате; G4 суточный прогон (запуск лучше на ночь, роутер занят целиком; в это время никакой другой исполнитель на MT3000 — `CLAUDE.md`, `ACTIVE-EXECUTOR`).
4. К + В: G7 по набору `private/lan-client-kit/` (когда готов), решение по G8.
5. В: G6 физический обрыв питания на MT3000 (пока он в стенде) или на своём роутере.
6. Публикация beta1 как Pre-release существующим скриптом, только после явного разрешения владельца.
7. В: G10 живой тест на beta1; замечания — в beta2 или в 2.0.0.
8. После G10 (и по желанию G6) — 2.0.0 по варианту А, с проверкой скачивания с обоих хостов и SHA256, как в 0.9.0.
