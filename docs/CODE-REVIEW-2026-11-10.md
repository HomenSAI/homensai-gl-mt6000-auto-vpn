# Независимое ревью кода HomenS.AI Auto VPN — 10.11.2026

Ветка `optimize-prompt`, версия приложения `2.1.0-alpha10` (`VERSION.json`, страница `dashboard211`). Ревьюер только
искал и описывал ошибки; код проекта не менялся. Команды на роутеры и в сеть не отправлялись.

Статус документа: итоговый отчёт ревью.

## Итог

- Находок: **критично — 0, важно — 2, мелочь — 11** (из них «подтверждено» — 9, «вероятно» — 3, «проверить на устройстве» — 1).
- Самое опасное (важно, №1): Lua-монитор — а именно он по умолчанию работает на роутере (`lua_monitor` = 1) — не видит,

  тайм-аута и т. п.
- Целенаправленный поиск XSS в интерфейсе (все строки статуса и инвентаря подменены на HTML-нагрузку, отрисованы все

## Подробности: «важно»

### №1. Lua-монитор не видит выключенный WAN

**Что происходит на практике.** Когда у роутера пропадает линк к провайдеру (выдернут кабель, отключился модем),
программа должна понять «интернета нет у самого роутера — перебирать VPN бесполезно» и ждать. В Lua-ветке (она
включена по умолчанию) признак «WAN выключен» никогда не появляется: в статусе всегда `UNKNOWN`. Модули
`diagnosis.lua` (код `UPLINK-LINK-DOWN`, «не перебирать резервы») и `wan_diag.lua` (поле `link='down'`) этот признак
не получают. Последствия: Auto может тратить попытки и бюджет переключений на бесполезный перебор VPN, а в журнале и
на странице не будет понятной причины «нет WAN». Часть случаев, возможно, ловят другие датчики `wan_diag`
(underlay/kmwan), но признак линка — самый прямой — потерян. Python-монитор (`agent.py:695`) делает правильно.

**Где.** `router/files/usr/lib/homensai-vpn/lua/monitor.lua`, `Monitor:sample_wan`, строки 542 и 560–561:

```lua
links[#links+1]=type(interface.up)=='boolean' and interface.up or 'unknown'
...
for _,v in ipairs(links) do if v==true then any_up=true end;if v~=false then all_down=false end end
```

Классическая ловушка Lua: `условие and false or X` всегда даёт `X`. Значение `false` (линк выключен) превращается в
`'unknown'`, и `all_down` не может стать `true`.

**Как воспроизвести.** Загрузить настоящий `monitor.lua` в Lua 5.1, подставить runner, у которого
`ubus call network.interface.<wan> status` отвечает `{"up": false, ...}` для обоих WAN, вызвать `sample_wan`:
результат `uplink_observation.state == 'UNKNOWN'` (ожидалось `DOWN`). Сценарий ревьюера
хранился во временном каталоге (библиотека lupa, Lua 5.1), в репозиторий не добавлен. Существующие тесты проверяют только Python-версию.

**Как исправить.**
```lua
local up=interface.up
if type(up)=='boolean' then links[#links+1]=up else links[#links+1]='unknown' end
```
Добавить общий кейс (Lua и Python) «оба WAN `up=false` → `DOWN`» в тесты двойников.

**Исполнитель:** Opus medium (логика датчиков, нужен тест-двойник).

### №2. Тесты пишут в настоящий каталог роутера и зависят от прав

**Что происходит на практике.** Модули `rpc_throttle.py` (`RUNTIME = Path('/var/run/homensai-vpn')`), а также
модули, создающие `integrity.json`, `pair-budget-clock.json`, `speed-traffic.json`, во время тестов пишут в настоящий
`/var/run/homensai-vpn`. Под обычным пользователем каталог создать нельзя, ошибка глотается (`allow()` → True) и тесты
проходят. Под root (контейнер CI, песочница ревьюера, или запуск тестов на самом роутере) каталог создаётся, ограничение
«не чаще раза в 2 с» начинает действовать между соседними тестами, и они получают `RPC-RATE-LIMIT` вместо ожидаемого
кода. На роутере такой запуск ещё и испортил бы живые файлы состояния (ограничитель частоты, часы бюджета переключений).

**Где.** `router/files/usr/lib/homensai-vpn/rpc_throttle.py:12-19`; тест `qa/test_mt3000_monitor_preflight.py:58`
(скрипт `router-test-kit/00-mt3000-monitor-preflight.sh:44` проверяет настоящие `/etc/homensai-vpn` и
`/var/run/homensai-vpn` машины, на которой идёт тест, и после других тестов видит «чужое» состояние); падают
`test_failure_matrix.Settings.*` (2), `test_setup_config.*` (1–3), `test_priority_recovery.*` (1–2): набор меняется
от порядка запуска.

**Как воспроизвести.** Под root: `rm -rf /var/run/homensai-vpn; cd router/tests; python3 -m unittest
test_failure_matrix.Settings test_setup_config test_priority_recovery` → 4 падения при первом запуске, 7 при повторном
(`AssertionError: 'RPC-RATE-LIMIT' != 'SETUP-PENDING-DELTA'`). После прогона в `/var/run/homensai-vpn` остаются
`rpc-throttle.json`, `pair-budget-clock.json`, `integrity.json`, `speed-traffic.json`.

**Как исправить.** Читать каталог из переменной окружения (например `HOMENSAI_RUNTIME`, по умолчанию
`/var/run/homensai-vpn`) во всех таких модулях; в `router/tests/__init__.py` или общем setUp направлять её во временный
каталог и подменять `rpc_throttle.allow` на «всегда да», где тест проверяет не ограничитель. Добавить в CI прогон под root.

**Исполнитель:** Sonnet medium (механика).

## Мелочи — коротко

- **№3.** `rpc.lua:227`: та же ловушка `and/or`: `dns_ok=false` становится `null`; Python-двойник (`auto_live.py:75`)
  отдаёт `false`. Страница при работе через Lua показывает «нет данных» вместо «DNS не прошёл». Исправление — как в №1.
- **№4.** Часовой пояс `CET-1CEST,M3.5.0,M10.5.0/3` прошит в службе, мониторе и Telegram-модуле. Для владельца в
  Берлине это верно, но у пользователя в другом поясе (например, Киев) время отчётов, суточные границы статистики и час
  ежедневного Telegram-отчёта будут сдвинуты. Интерфейс тоже показывает время только в `Europe/Berlin`
  (`router/ui/core.js:189`, `fmtTime`). Если это осознанное решение — описать в README; иначе брать пояс из
  `system.@system[0].zonename`/`timezone` роутера.
- **№5.** `router-test-kit/02-install.sh` уже содержит размер и SHA выпущенного `2.1.0-alpha10-1` (совпадает с
  `VERSION.json`), а `test_unbuilt_kit_refuses_before_anything_else` и `test_substituted_identities_are_refused` ждут
  нули (`EXPECTED_SIZE=0`). Тесты устарели после записи релиза; их надо строить от текущего состояния файла.
- **№6.** `test_probe_trust.RealTls`: Python 3.13 по умолчанию включает строгую проверку X.509, тестовый CA без
  расширения `keyUsage` отвергается (`CA cert does not include key usage extension`). На роутере Python 3.9/3.11 —
  тест не про продукт, а про фикстуру. Но если владелец закрепляет собственный CA для проверочного сервера и
  прошивка обновит Python, такой CA тоже перестанет приниматься — стоит упомянуть в справке.
- **№7.** Обе реализации ищут в тексте `/etc/config/homensai_vpn` строку только с одинарными кавычками или без
  кавычек. UCI допускает и `"0"`; при ручной правке файла выключение быстрого переключения молча не сработает. Кроме
  того, опция ищется в любой секции, а не только в `main`. Лучше читать через `uci get homensai_vpn.main.fast_switch`.
- **№8.** Шаблон адреса `^([%w][%w%.%-]*)[: ]([0-9]+)$` не принимает IPv6 в квадратных скобках — такие WireGuard-серверы
  выпадают из подбора серверов (поле `switchable=false`). IPv6 пока вне приёмки, но поведение стоит описать.
- **№9.** `telegram.lua main()` вызывает `send_test` без `pcall`; если ошибка случится после того, как curl уже
  отправил сообщение, Lua ничего не напечатает, и rpcd-диспетчер повторит запрос через `agent.py` — владелец получит
  два тестовых сообщения. Исправление: обернуть в `pcall` и при ошибке печатать JSON с кодом, а не пустоту.
- **№10.** Для WireGuard «жив ли сервер» = ответил ли он на ping первого адреса. Многие VPN-серверы ICMP не отвечают;
  такой текущий сервер будет считаться мёртвым, и подбор станет переключать простаивающий резервный туннель на другой
  сервер. Ограничено: смена идёт только для туннеля, который не несёт трафик, и не чаще лимита `CHANGES` за окно.
- **№11.** Хук WireGuard обрезает журнал через общий временный файл `$file.new`; два одновременных события могут
  перетереть друг друга. Журнал — лишь подсказка датчику, вред мал.
- **№12.** `auto_control.flock_file` ждёт замок `flock -x` без ограничения времени. Если другой процесс (например,
  Python-двойник) зависнет, удерживая `native-history.lock`, Lua-процесс встанет навсегда. В hv-core ожидание
  кооперативное, но в отдельных демонах — нет. Исправление: `flock -w 10` и код отказа при истечении.
- **№13.** `test_grey_lamp_ui.js` подменяет часы страницы, но `fmtTime` сравнивает день с `V.now` — временем
  последнего снимка, сделанного ещё по реальным часам. В любой день, кроме 07.11.2026, перед временем появляется дата
  и проверка `/последний ответ 14:02:31/` падает. Продукт не ломается; тест нужно делать независимым от даты.

  hotplug, процд-перезапуски, отключение питания, переполнение tmpfs — только чтение кода.

  236 тестов пропущены штатно. Отдельные проверки выполнены через библиотеку lupa (Lua 5.1) — см. «Результаты тестов».

  (`backend.reorder/apply`), подбор серверов, диагностика WAN; прочее — поиском по шаблонам опасных конструкций.
- `docs/ERROR_CODES.md`, `docs/BUILTIN-HELP*`, `releases/` — не читались по условиям задания.

## Что проверено и ошибок не дало

- Совместимость Python-кода роутера с Python 3.9: синтаксический разбор с `feature_version=(3,9)`, аннотации `X | Y`,
  `zip(strict=)`, новые функции stdlib — нарушений нет (разбор `fromisoformat` для 3.9 уже учтён).
- `subprocess` без `timeout`: найдены только `wait()` после `SIGKILL` и `status_client.fallback` (замена процесса) —
  допустимо. `shell=True` не используется.
- Shell-строки в Lua: аргументы проходят через `quote()` с запретом `'`, NUL и перевода строки, либо через проверку
  имён; сообщения в `logger` очищаются от кавычек.
- XSS: фаззинг всех строк `status` и `inventory` (вкладки, привязки, настройки, мастер) — 87 вставок показаны как
  текст, ни одной разметки; `esc()` применяется в модальных окнах журнала решений и смены ключа.
- Токен Telegram: передаётся curl через файл конфигурации 0600, а не командной строкой; в диагностическом пакете
  маскируется по значению; `/etc/config/homensai_vpn` ставится с правами 0600.
- Модули, не входящие в пакет (`cascade_*`, `candidate_runtime`, `configuration_migrations`), нигде не импортируются;
  все `require` Lua находят свои файлы (внешний `cjson` объявлен в зависимостях пакета).
- `VERSION.json` ↔ `Makefile` ↔ `build_ipk.py` ↔ меню LuCI ↔ контроллер: версия `2.1.0-alpha10-1` и модуль
  `dashboard211` совпадают; файл `dashboard211.js` и ленивый `help211.js` существуют.
