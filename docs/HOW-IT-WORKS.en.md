## About the project

Why this project has so much mathematics, physics and biology. These experiments exist because the author, Serhii Khomenko, has always loved these sciences, even though they never came easily to him. That is why every idea is tested honestly: compared with the previous method in the simulator and on the router, and only what is really better is kept.

## In short, in plain words

- The application watches the router's two VPN channels, the primary and the reserve. If the primary stops working it moves traffic to the reserve, and when the primary is dependable again it brings traffic back.
- It does not leave the primary for every random lost packet. A small probabilistic model (an HMM) decides: leave only if the failure is likely to last longer than the switch itself costs (about 20 s). The old rule "three failed checks in a row" remains as an optional "Previous rule" mode.
- The router keeps a "diary of your network" and once a night can suggest how fast to react to failures. One slider, "Fast reaction <-> No unnecessary switches", moves all related settings together. The default mode is "Advice": you apply the suggestion. "Auto" moves the slider itself, by at most 0.1 a day; "Manual" uses your own values.
- If the router's whole internet connection is gone (not just a tunnel), Auto tells the two apart and does not bounce between channels: it shows WAN-DOWN, and after the internet returns it waits a little for the primary to prove itself.
- If a VPN server suddenly shows a different key than last time, the application warns you; only you can accept the new key.
- The first-run wizard can always be skipped with "Skip - open the interface": skipping does not start Auto, does not accept the terms for you and does not need Auto to be stopped.
- Releases are signed with the owner's key and the release history is kept as a chain in which a record cannot be replaced unnoticed (the first signed installation on the router is still ahead). This concerns installing the package, not VPN operation.

All of this belongs to the 2.1.0-alpha9 line (source and checks on a PC). **Not everything is verified on the router** - see "What is verified and what is not" at the end of this page.

## Roles, clients and traffic

Main and reserve are roles, not WireGuard/OpenVPN names. Stock firmware owns provider profiles, credentials and server selection within a tunnel. The application observes exact protocol/interface/profile generations and coordinates the saved pair of distinct clients. A country/display group such as `default` is metadata, not proof of channel membership.

The configured profile, connected tunnel, healthy router probe and selected common traffic route are different states. Both clients can be connected while one route is selected. Saving the pair edits application metadata; explicit prepared Auto Start can enable managed clients and select their policy. Normal Stop restores the managed baseline when verified, otherwise exposes the retained/unconfirmed outcome.

## Continuous Auto

The qualified prepared MT3000/4.11.0 path uses fresh router IPv4 DNS/HTTPS evidence, stable identity, policy/worker/ownership checks and bounded recovery. The decision to leave the primary is made by an HMM model (see "When Auto decides to leave and when to return"), not by "three failures in a row"; reserve successes, cooldown, dwell and budgets also prevent an immediate switch on every noisy sample. A low response time is a recommendation, not permission to move traffic.

Settings changed outside the app while Auto runs (owner decision 07.11.2026, "by risk + notification"): Auto adopts the change by itself only when it touches nothing but Wi-Fi (wireless), DHCP, the GL DNS page (gl-dns-v2) or the network interfaces/addresses outside the pair, at most three times in 15 minutes. A change of the VPN profiles (wireguard, ovpnclient), the firewall, the pair's route_policy rules or their order, any other package, or one whose class cannot be read holds the session (PAIR-OUTSIDE-CHANGE-HELD) with the LAN guard kept until the owner's Start (recorded as the owner's adoption) or Stop. Every adoption and every hold is a history event and a log line with the class and the package names, never a value.

Manual selection is an explicit command with a confirmed result, not an immediate lamp change on queue ACK. A manual switch never turns Auto off: Auto keeps watching the chosen channel and moves traffic to the other one if it fails, and after an Auto restart or package upgrade it returns to the primary when that is healthy. Automatic return follows saved policy and readiness; a hold-reserve policy does not promise return just because primary recovers: it keeps a working reserve. Since 07.11.2026 (owner decision) a pinned reserve that itself fails, proven by the failure detector and a fresh router probe, is rescued to a healthy primary after the rescue stability (rescue_stable, default 10 s) under any return policy; an unknown reserve check keeps the hold. This holds on both return paths: with an open transaction journal (the committed decision) and without one, when the session already carries traffic on the reserve after a boot or an accepted manual selection (the tick's own return). The rescue goes through the same guarded return path (journal, kernel attestation, protected configuration checks) and ignores the flap-damping return hold, so a reserve/primary ping-pong is bounded only by the attempt budget (3 failovers per 15 min, 60 s cooldown). A deliberate bounded fault test is separately labelled and can test both directions without changing the saved preference.

## Runtime layers and switching time

The router part runs on layers that share the same files and rules. Python 3.9 is the base and the last fallback. On top of it, in the 2.0.0-alpha line, Lua 5.1 runs the monitor and Auto as two services (an optional single process `hv-core` exists); a C module `canon_c.so` does the canonical JSON inside Lua, and if it fails to load or fails its self-probe the same code runs in pure Lua by itself (`HOMENSAI_CANON_C=0` forces Lua). If the Lua services fail repeatedly, Auto falls back to the Python supervisor (`LUA-AUTO-FALLBACK`). The switch history is an append-only journal.

Fast detection is on by default since alpha24 (`option lua_fast_detect '0'` turns it off): a 1 s heartbeat of both Auto channels starts a dense confirmation within about 2 s of an outage (two lost beats in a row since 03.11.2026, was three); the decision to leave is still taken by the detector (HMM by default, see below; the "failures in a row" count applies only in the "Previous rule" mode), and the live reserve and the firmware checks are unchanged. Measured on the MT3000: a manual switch is done in about 0.7 s; the automatic decision comes 26-28 s after an outage (58-88 s without fast detection) and traffic moves 1.3-1.6 s after it. [Numbers per layer](MEASUREMENTS.en.md#8-runtime-pyramid-and-switch-times).

## When Auto decides to leave and when to return

In plain words: a short hiccup is no reason to switch, because switching itself interrupts connections. Auto estimates the probability that the failure will last at least 20 s more and leaves only when that probability is high enough. In the registered simulation (simulator only, not validated on the router; this mode is experimental: chosen in simulation, not validated on hardware) the Standard mode did not leave on 15 s outages, but it still left on 20-21 s outages (noticeably less often than the old "three in a row" rule, yet not rarely), and the claim that it ignores loss up to 20 % is unproven (5 % and 10 % loss passed). On a long outage it leaves about 3 s later than the simple rule and costs more per day in the registered daily model; it does better on flapping and heavy loss. Fast leaves after about 21 s but also on most 20 s blips. This is a tendency of a probability model that weighs the evidence, not a guarantee: a short blip with unlucky evidence can still make Auto leave (the simulated rates are in the scientific guide). The safe alternative is the "Previous rule" mode.

For administrators: the detector is `failure_model` = `hmm` (default, theta 0.8, dur_B 4 s), `hmm-fast` (theta 0.7, dur_B 3 s) or `consecutive` ("Previous rule", `recovery_failures` in a row). Returning to the primary needs P(healthy) of at least 0.90 and `primary_stable`; a return from a reserve that failed itself needs only the shorter `rescue_stable` (10 s by default) instead of the full `primary_stable` (120 s by default), never zero. The rule "HMM or N probes in a row" is off and is switched on only by the slider positions t = -0.1 / -0.2; the heartbeat turbo is off and needs an explicit expert choice (its consent phrase names up to ~8 extra switches a day: an exploratory estimate, not yet measured on a router); the event wake of Auto is on; the parallel recheck is off until it is measured on a router. Details (Russian): [HMM-DETECTOR](architecture/HMM-DETECTOR-2026-11-03.ru.md), [FAST-SWITCH](architecture/FAST-SWITCH-2026-11-04.ru.md).

## Auto-adaptation and the master slider

In plain words. Every network has its own character: on a noisy line a fast reaction causes unnecessary switches, on a quiet one it can react faster. The application keeps a short diary (how many checks failed, how long outages lasted, the response by hour of day, how many times it moved to the reserve and how many of those were unnecessary) - about 3 KB a day, 30 days. Every night at 03:30, at the lowest priority, it "replays" the past days through the same decision code that really runs, for different slider positions, and reports where the total cost is lowest: seconds of downtime plus a 20 s penalty for each unnecessary switch. A suggestion appears only if it saves at least 5 % and the window held at least 5 events; otherwise it says "keep" or "not enough data". You choose the data window: 1, 7 (default) or 30 days.

Three modes: **Advice** (default) - you apply the recommendation with a button; **Auto** - the system moves the slider itself by at most 0.1 at a time, at most once per 20 h, never during an outage or a switch, and records every change with its reason; **Manual** - your own values ("Custom"), the advice is only shown. Auto will become the default for ordinary users only after a 7-day check of the advisor on the MT3000 (owner's decision). None of this starts Auto. The slider has 11 anchor points (the curve was built in a simulator; an independent check did not confirm a smooth monotone trade-off, and several positions, including 0.8 in some periods, are dominated by others: the slider position is a guide, not a guarantee); the safe limits are checked again on the router (theta 0.5-0.99, dur_B 1-15 s, P(G) 0.5-0.99, primary_stable 30-600 s, rescue_stable 0-60 s). The page shows a chart "downtime per day vs unnecessary switches per day", a table of all variables and "Fine tuning" for experts; a 5-step training is offered once and stays available in "Help and training". Details (Russian): [NETWORK-ADVISOR](architecture/NETWORK-ADVISOR-2026-11-04.ru.md).

## Where the idea comes from

Tuning a threshold from a network's own history is not our invention; it is a technique of "big" systems that ordinary home routers do not have:

- **The phi-accrual failure detector** (Hayashibara et al., 2004; Apache Cassandra, Akka, Hazelcast): a node is not declared dead by a fixed timeout but by a "suspicion level" built from the history of that very link. One phi threshold is one knob "faster <-> fewer false alarms", like our slider.
- **Anomaly detection in Amazon CloudWatch and Datadog**: the bounds of "normal" come from the metric's history, including hour of day and day of week.
- **cake-autorate** (OpenWrt, for LTE and Starlink links): the shaper rate follows the measured delays of that link.
- **TUF and Sigstore** (signed metadata, backup and revocable keys, a log that cannot be rewritten) for signing releases. We took the idea, not their implementation: ours is a simple signed release chain `CHAIN.jsonl`, with no servers or external services (except the public OpenTimestamps calendars).

Ordinary home routers switch a VPN on static thresholds ("N failures in a row" or a timeout). Here the threshold is chosen from the history of your own network, but only inside a curve verified by the study and with the same safety limits.

**Honestly.** Every method on its own is known. The prior-art search (offline, open sources; the report itself is kept privately and is not in the repository) did not find a ready combination of "probabilistic detector + sensors + Bayesian server pick + state-space checking of the supervisor + one slider + a simulator checked against a test bench + a signed release chain" in one home device; but "not found" does not mean "does not exist", and the search did not cover closed corporate material or full-text databases. We do not claim academic novelty for any single element and we do not say nobody has done this. Some ideas are close to Cisco patents on threshold adaptation (this is not legal advice). Our depth is smaller than the literature's: one test bench, small samples, no peer review.

## Sensors: the router's internet, WireGuard events, server keys

In plain words. Before, every check went through the tunnels, so when the router's own internet failed both channels looked "bad". Now the router has its own check that bypasses the VPN. If it and other evidence say "no internet", Auto shows **WAN-DOWN** and does not try to jump to the reserve, and after the internet returns it waits up to 30 s more for the primary to prove healthy (**WAN-RECOVERING**), so it does not move to the reserve because of a race between tunnels coming up. If the reserve answers, WAN-DOWN is not declared. WAN-RECOVERING is a separate short wait (up to 30 s, until the primary proves healthy) that applies even when the reserve is healthy.

For administrators. The verdict is a small Bayesian model over the evidence: the router's own echo through the WAN port (`wan_sensor`; needs calibration and 3 failures in a row on two targets), the GL firmware's kmwan verdict, the repeater's captive-portal flag, the WAN link, the probes of both channels and WireGuard events (`wg_events`). A hold happens only when P(WAN) >= 0.95 with hard evidence; "unknown" always means the previous behaviour. The "tx grows, rx stands still" sensor (`stall_sensor`) and its veto of lost heartbeat echoes (`stall_veto`) only raise suspicion; they never prove a failure. The "2 of 3 targets" quorum (`heartbeat_quorum`) is off by default: it was not better on every metric. The per-target probe log (`probe_target_log`) only records in router memory how each target answered, does not influence decisions and is not written to flash. Details (Russian): [GL-SENSORS](architecture/GL-SENSORS-2026-11-04.ru.md), [PER-TARGET-PROBE-LOG](architecture/PER-TARGET-PROBE-LOG-2026-11-04.ru.md).

**Three optional heartbeat signals.** `cusum_trigger` (off) lets a CUSUM of lost heartbeats start the dense checks past the suspicion rest; the HMM still makes the decision. It stays off because the registered simulation check of false alarms was not passed (and with only 60 simulated worlds that check cannot be passed even with 0 alarms, so it is too conservative to confirm an acceptable rate either way); it also needs a router check. `rtt_watch` (off) is a Kalman filter over heartbeat round trips that only shows the soft signal `CHANNEL-CONGESTED` and changes no decision. `heartbeat_rtt_log` (on) keeps a per-minute RTT log in RAM. Design: [CUSUM-TRIGGER](architecture/CUSUM-TRIGGER-2026-11-04.ru.md); all its figures are simulator figures.

**Server key pinning (TOFU).** On the first good look the application remembers the server's key (the WireGuard peer public key, or the certificate fingerprints of the OpenVPN CA) for the pair "profile + host name". If the same server later shows a different key, the event `SERVER-KEY-CHANGED` appears, and Settings -> System and diagnostics -> Sensors has an "Accept new key" button (RPC `server_key_accept`). The default mode is `warn` - a warning only; `enforce` refuses a move onto such a channel, leaving it stays allowed; `off` stops watching. A server change inside a provider pool is a new "first use", not an alarm. This protects against server substitution; it does not encrypt traffic.

## Release signing, chain, OpenTimestamps, recovery codes, age

In plain words. So that a substituted package cannot reach the router, releases are signed with the owner's key (Ed25519, the router's stock `usign`). Every release is entered in a common log `releases/CHAIN.jsonl` in which each record carries the fingerprint of the previous one, so history cannot be deleted or rewritten unnoticed. The record's hash is also anchored in Bitcoin through OpenTimestamps - a public proof of the date (confirmation arrives after hours). Signing needs a TOTP code from the owner's phone; without the phone there are 10 one-time recovery codes on paper (format `XXXX-XXXX-XXXX-XXXX-CCCC`; the last 4 characters catch a typo). Secrets can move to a new computer in an encrypted archive in the age format. All of this concerns the project owner and the release process; an ordinary user only needs to check the package hash and signature following the [installation guide](INSTALL.en.md).

For administrators: there are two keys (main and reserve, both trusted on the router), a revocation is written as `<key>:<record number>`; the router remembers the verified chain and rejects a rollback and a "fork" (`CHAIN-DOWNGRADE`, `CHAIN-FORK`). Limits, honestly: the first installation trusts the keys in the kit, so compare fingerprints with an independent source; TOTP and DPAPI live in one Windows session, which is procedural rather than absolute protection; a router that has not yet received a release with the revocation will accept a record signed by the stolen key. Details (Russian): [SIGNING](architecture/SIGNING-2026-11-03.ru.md), [SIGNING-LAB](architecture/SIGNING-LAB-2026-11-04.ru.md), [AGE-TOFU](architecture/AGE-TOFU-2026-11-04.ru.md).

## P95 of the recovery time: estimate and upper bound

In plain words. The page shows "P95 (estimate)": the 95th percentile of the recorded sample itself, which is not a guarantee. At n = 60, 100 and 300 the sample's own P95 covers the true P95 in only about 35 %, 38 % and 43 % of cases, so it is never a bound. A separate "P95 upper bound, 95 % confidence" (valid for independent measurements) appears only at n >= 59 and is computed on its own (the smallest ranked value that bounds the true P95 with 95 % confidence, see `scripts/honest_stats.py`). With a smaller n the page shows "~P95" (an estimate; at n <= 19 just the maximum) and the maximum with the share of cases it covers with 95 % confidence. The number of measurements n is always shown next to it, and an empty value is shown as "-", not as zero. The "Recovery time" panel covers a day, a week and a month; the same rules serve the page and the reports (`scripts/honest_stats.py`).

## What is verified and what is not

Verified on a PC (tests in Linux containers, both runtimes - Lua and Python): the decision rules, the slider, the advisor, the sensors, key pinning, signing and the chain (on test keys), age, the "wave 3" items. The simulator's figures (downtime, unnecessary switches, probe counts) are a model, not a measurement on the router.

**Not verified on the router (MT3000):** the advisor and the "Auto" mode over 7 days; the CUSUM trigger and the RTT signal; the slider at positions beyond those measured earlier; the WAN-DOWN sensor (cutting only the router's uplink), WireGuard events, the format of `/proc/gl-kmwan/config`; key pinning on real provider profiles; the fast edge (t < 0, turbo) and all figures from the FAST-SWITCH measurement plan; the first installation of a signed package with real keys; a 24-hour soak and a physical power cut. An external LAN client, IPv6 and MT6000 continuous mode remain separate acceptance areas. Current state: [CURRENT-STATUS](CURRENT-STATUS.md), [ROADMAP](ROADMAP.md).
