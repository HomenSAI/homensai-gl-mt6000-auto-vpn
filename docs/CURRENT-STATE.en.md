**Runtime layers (2.0.0-alpha line).** Python 3.9 is the base and the last fallback layer (`agent.py` monitor, `native_switch.py` Auto). On top of it Lua 5.1 runs the monitor and Auto as two services, the installed default since 2.0.0-alpha24 (`option lua_monitor '0'` / `option lua_auto '0'` return to Python; an optional single process `hv-core` with `option lua_core_process '1'`). Inside Lua a C module `canon_c.so` does the canonical JSON: it is used only if it loads and agrees with the Lua code on a self-probe, otherwise the same code runs in pure Lua automatically (`HOMENSAI_CANON_C=0` forces Lua). If a Lua service fails repeatedly, the work moves one layer down: `HV-CORE-FALLBACK` to two Lua processes, `LUA-AUTO-FALLBACK` (3 errors in 600 s) to the Python supervisor until the service restarts. Journal, rollback, the VPN-only guard and Auto resume work on every layer. The switch history is an append-only journal (schema 2): a small state file `native-history.json` plus `native-history.events.jsonl`; rollback to an older package: `cp /etc/homensai-vpn/native-history.v1.json /etc/homensai-vpn/native-history.json` (events recorded after the migration are lost). Since alpha24 fast detection is on by default (`option lua_fast_detect '0'` turns it off): the 1 s heartbeat of both Auto channels starts a dense confirmation within about 3 s; during it the monitor's HTTPS check waits 3 s instead of 6 s; the vendor settle period is at most 45 s. Measured on the MT3000: manual switch done in about 0.7 s (traffic about 0.5 s); automatic decision 26-28 s after an outage with fast detection at probe level 1 (58-88 s before), traffic moves 1.3-1.6 s after the decision; a power cut (simulated by an instant reboot) in the middle of a switch recovers by itself. The 3 s wait and the 45 s settle period are not yet measured on the router. A physical power cut and a 24-hour soak of this build remain separate acceptance. Per layer: [MEASUREMENTS, section 8](MEASUREMENTS.en.md#8-runtime-pyramid-and-switch-times).

The displayed response uses one measurement chosen in Settings → Router load → How response is measured (Console: Auto tab): by default a ping through each VPN to 1.1.1.1 (or 8.8.8.8 / 9.9.9.9); optionally the complete three-site HTTPS mean (Google, Cloudflare, Wikipedia). The option "Measure all methods (comparison)" makes every check also ping the other DNS addresses and open the three websites; the page shows the chosen method, while switching still uses only the chosen method. The delay chart and statistics follow the chosen metric (a separate ping history exists). A website request includes DNS, TCP, TLS and HTTP headers; it does not time a full rendered page or inspect personal browsing. Only 3/3 supplies a number. Period averages weight complete measurements by their count with consistent rounding; old ICMP and health-probe HTTPS measurements remain separate. [Formula](WEBSITE-RESPONSE.md). Manual actions remain visible with an explanation when blocked; primary is shown above reserve.

**Indication.** The rules are the same in both views. Channel lamp: green = the channel works (the chip "Traffic here" marks the one carrying your traffic, "Standing by" the other); yellow = a check or a switch; red = it does not respond or its tunnel is off (with the code); grey = no fresh data. Big status lamp: green = the VPN works on the primary; yellow = the reserve is in use, a switch or a check; red = the current channel or both fail; grey = no fresh data. The Auto switch states its state in words (Auto is on, Turning Auto on…, Auto is off and so on).

**Manual switching.** The "Switch here" button on a channel card (Home, or the Channels tab of the Console). A manual channel switch never turns Auto off, and there is no "Resume Auto" button. Auto keeps watching the manually chosen channel and moves traffic to the other one if it fails. After an Auto restart (or a package upgrade) Auto returns to the primary when it is healthy.

**Probe level and boost.** Settings → Router load (Console: Auto tab) has a probe level 1-5: the health check runs every 60/30/20/15/10 s and the response is measured every 300/120/60/45/30 s; a failure is confirmed after 3 failed checks. The "Automatic boost" checkbox: when a selected channel fails one check while Auto watches, checks run every 10 s (response every 30 s) for 10 minutes from the last failure, at most 20 minutes; the boost ends when Auto switches or the failure is confirmed, then 10 minutes of rest follow, and the same channel cannot start a new boost until it passes a check. Every episode goes to the decision log ("Decision log: levels and boost"; Console: Log tab). If the router refuses a level change, the settings are not saved and a window shows the code.

The status call on the MT3000 is cheaper (a shared 15 s kernel attestation).

Speed tests now request a bounded cooperative pause from the Auto controller and background monitor. Measurement starts only after both active processes acknowledge a safe loop boundary. VPN connections, routing, Auto intent and service settings are preserved. CPU admission uses fresh CPU accounting after the pause, not minute load average. Normal completion, failure, cancellation or worker loss withdraw the pause; monitoring obtains a fresh observation before Auto continues. A manual Stop is never undone. Manual switching is refused during the quiet window. Both selected speed tests completed on the installed alpha33 with a verified pause and automatic restoration; see the physical receipt.


Both views remain accessible with Auto off, unknown data or errors and show the real Auto state, confirmed traffic channel and independent reserve health. Moving between views and sections does not run command RPCs.

Start requests are pending until the controller confirms them. A preflight refusal consumes only the matching accepted request and reports FAILED plus the specific BLOCKED reason, allowing retry without indefinite Starting. A late failure cannot overwrite a newer Start or Stop. Stop retains the existing recovery contract. Auto that the owner started comes back by itself after a reboot or power cut, with every Start check; a Stop cancels that.

The pair uses exact, distinct selected vendor tunnel identities, including a second OpenVPN client slot after channels have been removed. Readiness, startup preparation, firmware-zone checks and network compare-and-swap use those identities. Disabled historical profiles do not consume the active-probe limit. A healthy standby is not a failed traffic path; old observations cannot confirm current selection.

Preparation is performed when the owner turns Auto on (the page has no separate preparation buttons) and applies to the exact selected source/target interface. It changes only bounded startup/acceleration settings, record original values and verify readback. They never restart the network or force-unload acceleration. Runtime blockers and restart requirements remain enforced. [Control effects](CONTROL-AND-SETUP.md) · [Codes](ERROR_CODES.md).

Existing monitoring, history, speed tests, terms, Telegram, training, keyboard focus and scroll behavior remain. Speed and fault tests never run on navigation. Artificial fault injection remains in test tooling. Terms acceptance belongs to the person and is preserved when the terms version is unchanged. Secrets stay on the router.

Continuous router-probed IPv4 Auto remains qualified only for the documented dedicated MT3000 / GL.iNet 4.11.0 arrangement. Router DNS/HTTPS success is not external LAN, IPv6, physical failover or unattended endurance acceptance. [Client trial](CLIENT-TRIAL.md) · [Recovery](../router-test-kit/EMERGENCY.md).

[History and retention / История и сроки хранения](HISTORY-RETENTION.md).

Diagnostics distinguish a partial HTTPS quorum failure from zero validated HTTPS responses and unavailable detail. Per-endpoint status is recorded without raw exceptions or credentials; an unsupported HTTP endpoint is a check-endpoint fault. Old incidents are never explained with today's profile state. Same-measurement incident/monitor rows are correlated only with retained matching timestamps. Vendor-worker contention is a temporary wait; an accepted Start with an old STOPPED observation is shown as pending Start. The diagnostic reference table wraps codes, descriptions and open explanations within the viewport, with a stacked mobile layout.

The final alpha33 observer preserves a bounded allowlist of endpoint diagnostics through the identity check and discards them with the rest of old-identity health on a rebind.

Settings → How fast to switch (Console: Auto tab; presets Calm, Normal, Fast and Custom values) combines the check interval, source failure and reserve-success thresholds, cooldown, minimum reserve dwell, rolling forward-attempt limit/window, primary return successes/stability and return policy. Defaults for new configuration: 10 s, 3 failures, 2 reserve checks, 60 s cooldown/dwell, 3 attempts per 15 minutes, 2 primary checks over at least 30 s, automatic healthy-primary return. Saved existing values are preserved on upgrade. User values are range checked. The rules change with Auto off: saving offers "Stop Auto and save"; saving never starts Auto. Attempt history for the entire maximum 15-minute window is retained across policy changes and shared with manual forward selection; Stop and return remain available.
